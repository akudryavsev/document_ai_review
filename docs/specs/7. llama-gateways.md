## 1. Назначение и границы

**Назначение.** Описать, как процесс приложения получает эмбеддинги, скоры реранка и текст ответа от одного контейнера `llama-server`, и как фаза A1 переносит байты вектора в `ArtifactStore`.

**Делает:**

- Фиксирует три класса: `LlamaEmbeddingGateway`, `LlamaRerankerGateway`, `LlamaLlmGateway`.
- Фиксирует HTTP-контракт к пресету. Имя пресета — имя файла GGUF из списка роли ([10. model-lists.md](10.%20model-lists.md)).
- Фиксирует, что на границе фазы вектор — непрозрачные байты float16 и размерность.
- Фиксирует, кто пишет `vectors.f16`, `embed_cache` и кэш вопросов.

**Не делает:**

- Не грузит веса внутри процесса `app` и не добавляет `torch` в образ `python:3.11-slim`.
- Не пишет в `ArtifactStore`. Кэш по `text_sha256` делает фаза.
- Не ретраит один `infer`. Повторы ответа остаются в `AnswerGenerator`.
- Не считает BM25 и косинус поиска. Это `HybridSearcher`.
- Не поднимает боевой сервер в unit-тестах.
- Не возвращает `AnswerVerifier` в прогон.

Образ приложения и список зависимостей остаются как в репозитории: `pydantic`, `pyyaml`, `pytest`, `python-docx`, `pypdf`, `pymorphy3`. HTTP-клиент — класс на стандартной библиотеке. Новая строка в `requirements.txt` для этих шлюзов не требуется.

До реализации `Application.build` собирал `FakeEmbeddingGateway`, `FakeRerankerGateway`, `FakeLlmGateway` и `FakeHybridRetriever`, а `IndexingPhase` не вызывал `save_chunk_vectors`. Целевая сборка — раздел 8; после утверждения она и есть код `Application.build`.

## 2. Контейнер и одна модель на GPU

Сервис compose `inference`, профиль `poc`, образ `ghcr.io/ggml-org/llama.cpp:server-cuda`. Команда и тома — как в `docker-compose.yml` репозитория:

- `--models-preset /etc/llama/models.ini`
- `--models-max 1`
- `--host 0.0.0.0`, `--port 8080`
- тома `./models` → `/models` и `deploy/llama/models.ini` → `/etc/llama/models.ini`

`deploy/llama/models.ini` собирает приложение из списков конфига. Заголовок секции равен имени файла. Строка `model` в секции равна `/models/<имя файла>`. Флаги секции задаёт роль списка, скаляры конкретной модели берутся из её `params`. Канонический текст, запись из `run` при расхождении и команда `write-models-ini` — [10. model-lists.md](10.%20model-lists.md).

Имя секции — значение поля `model` в HTTP. Путь GGUF приложение не открывает: файл читает только `llama-server`.

`--models-max 1` означает одну загруженную модель в контейнере. Вторая появляется только после выгрузки первой. `GpuLease` на стороне приложения вызывает `load`/`unload` шлюза; шлюз переключает пресет запросами раздела 4. Два шлюза одновременно не бывают в состоянии `loaded = true`.

Порядок одной комбинации A1 → A2 → B: файл эмбеддера, затем файл реранкера, затем файл ответа. Несколько имён дают несколько таких проходов ([10. model-lists.md](10.%20model-lists.md)). Пропущенная фаза свой пресет не загружает. Косинус `eval` берёт первый файл из `embedding.models` уже после фаз прогона, отдельной командой ([8. eval.md](8.%20eval.md)).

Оценка гигабайт зависит от квантизации положенного GGUF и от контекста 4096. Процесс `app` видеопамять не занимает. Карты хоста использует контейнер `inference`.

## 3. Конфигурация

Целевые поля. Отсутствие секции `inference` в YAML допустимо: действуют значения по умолчанию, CLI без этой секции не ломается.

```yaml
inference:
  base_url: "http://inference:8080"
  request_timeout_sec: 120
  poll_interval_sec: 0.5

embedding:
  models:
    - bge-m3-q8.gguf      # имя файла в models/
  batch_size: 8
  dtype: "fp16"           # на диске всегда float16; см. соответствие ниже

reranker:
  models:
    - bge-reranker.gguf

answer:
  models:
    - Qwen3-8B-Q4_K_M.gguf
  temperature: 0
```

Соответствие имён:

| Класс | `gateway.name` для `GpuLease` | Пресет | Файл, который держит сервер |
|---|---|---|---|
| `LlamaEmbeddingGateway` | `embedding` | имя файла из `embedding.models` | `/models/<это имя>` |
| `LlamaRerankerGateway` | `reranker` | имя файла из `reranker.models` | `/models/<это имя>` |
| `LlamaLlmGateway` | `llm` | имя файла из `answer.models` | `/models/<это имя>` |

`gateway.name` и имя пресета — разные строки. В `meta.embedding_model`, в строке ответа и в сводке пишется имя пресета, то есть имя файла из списка роли.

Ключ `embed_cache` и поле `embedding_dtype` хранилища используют строку `float16`. Значение YAML `fp16` отображается на неё. Другое значение `embedding.dtype` для этих шлюзов — ошибка конфигурации до первого `infer`.

`embedding.device`, `reranker.device`, `answer.device` шлюзы не читают: устройство выбирает процесс сервера. `answer.max_output_tokens` по-прежнему не ставится генератором в запрос; шлюз передаёт `max_tokens` на сервер только если в `GenerateRequest.max_output_tokens` передано число. В целевом прогоне там `null`, и поля в JSON нет.

`--embedding-model`, `--reranker-model`, `--answer-model` подменяют список своей роли одним именем файла на этот запуск. Имя должно быть файлом в `models/` и секцией собранного `models.ini`. Неизвестное имя — ошибка до фаз ([10. model-lists.md](10.%20model-lists.md)).

Пример `config.yaml` в репозитории до утверждения спеки 10 хранит одиночные имена секций. Вместе с кодом по спеке 10 он перечисляет имена файлов. Строка, которой нет в собранном ini, для сервера — неизвестный пресет.

Замена байтов GGUF на том же пути без смены имени пресета не меняет `chunking_hash`. Повторный прогон с тем же именем фазу A1 не пересчитывает. Оператор в этом случае передаёт `--force-phase A1`.

## 4. HTTP-контракт

Базовый URL — `inference.base_url` без завершающего слэша. Тело — JSON, UTF-8, `Content-Type: application/json`. Ключ авторизации compose-сервер не требует, клиент заголовок `Authorization` не шлёт.

Клиент — класс `LlamaHttpClient`. Методы: отправить JSON и вернуть разобранный объект, либо бросить `LlamaServerError`. Таймаут одного вызова — `request_timeout_sec`. Свободных функций нет.

Идентификатор модели в теле совпадает с секцией пресета. Маршрутизатор сервера выбирает инстанс по полю `model`.

### 4.1. Загрузка и выгрузка пресета

`load` пресета `P`:

1. `POST {base_url}/models/load` с телом `{"model": "P"}`.
2. Успех шага — HTTP 200 и JSON `{"success": true}`. Иначе `LlamaServerError`.
3. `GET {base_url}/models`. В `data` ищется элемент с `id`, равным `P`, и `status.value`, равным `loaded`.
4. Пока статус `loading`, клиент повторяет шаг 3 не чаще чем раз в `poll_interval_sec`, в пределах того же `request_timeout_sec`. Это ожидание готовности `load`, не повтор `infer`.
5. Статус `failed` или иной конечный статус, а также истечение таймаута: шлюз один раз вызывает выгрузку того же пресета и затем бросает `LlamaServerError`. Флаг `loaded` остаётся `false`.

`unload` пресета `P`:

1. `POST {base_url}/models/unload` с телом `{"model": "P"}`.
2. HTTP 200 и `success: true` — пресет снят, `loaded = false`.
3. HTTP 400 или 404 — пресет уже был снят. Для приложения это успешная выгрузка, `loaded = false`. Точный текст тела при этом не нормируется (допущение раздела 12).
4. Сеть, таймаут и прочие коды — `LlamaServerError`. Флаг `loaded` при такой ошибке не меняется на `true`.

`GET /v1/models` для готовности не используется: статус загрузки описан у маршрутизатора на `GET /models`.

### 4.2. Эмбеддинги

`POST {base_url}/v1/embeddings`

Запрос:

```json
{
  "model": "bge-m3-q8.gguf",
  "input": ["первый текст", "второй текст"],
  "encoding_format": "float"
}
```

`input` — массив строк длины от 1 до `embedding.batch_size`. Одна строка вместо массива не отправляется: шлюз всегда шлёт массив, даже из одного элемента.

Ответ, который шлюз обязан разобрать:

```json
{
  "object": "list",
  "data": [
    {"object": "embedding", "index": 0, "embedding": [0.1, -0.2]},
    {"object": "embedding", "index": 1, "embedding": [0.0, 0.3]}
  ],
  "model": "bge-m3-q8.gguf",
  "usage": {"prompt_tokens": 4, "total_tokens": 4}
}
```

Правила разбора:

- Число элементов `data` равно числу строк `input`.
- Поле `index` — позиция в `input`. Ответ может прийти не по порядку; шлюз раскладывает по `index`.
- Пропуск, повтор или индекс вне диапазона — `LlamaServerError` на весь вызов.
- `embedding` — массив JSON-чисел. Пустой массив — ошибка «пустой вектор».
- Длины массивов внутри одного `infer` (все батчи этого вызова) совпадают. Иначе ошибка «разная размерность», частичный ответ наружу не отдаётся.
- Число вне конечного диапазона float16 (модуль больше 65504), а также нечисловое значение — `LlamaServerError`. `inf` и `nan` на диск не пишутся.
- Каждое число переводится в IEEE 754 binary16, little-endian, округление к ближайшему чётному. Длина байтов одного вектора — `dim * 2`.

Поле `encoding_format: "base64"` не используется. Нативный путь `POST /embedding` не используется.

Сервер по своей документации нормирует эмбеддинг евклидовой нормой. Шлюз норму второй раз не считает и байты не переписывает.

### 4.3. Реранк

`POST {base_url}/v1/rerank`

Один вызов сервера — один текст запроса и список пассажей. У `RerankRequest` пары могут отличаться текстом `query` (категория и синонимы). Шлюз группирует пары по точному тексту `query`, сохраняя порядок первого появления группы и порядок пар внутри группы.

Запрос группы (форма Jina, ключ `documents`):

```json
{
  "model": "bge-reranker.gguf",
  "query": "текст варианта",
  "documents": ["пассаж 1", "пассаж 2"]
}
```

Поле `top_n` не отправляется: сервер возвращает скоры всех документов (в документации значение по умолчанию — все).

Ответ:

```json
{
  "model": "bge-reranker.gguf",
  "results": [
    {"index": 0, "relevance_score": 0.91},
    {"index": 1, "relevance_score": 0.12}
  ]
}
```

`index` — позиция в `documents` этой группы. `relevance_score` — число, вероятность совпадения в диапазоне, который отдаёт сервер. Шлюз порог не применяет.

Каждая пара исходного запроса получает скор. Пропущенный индекс — `LlamaServerError` на весь `infer`.

`rank` в `RerankResponse` считает шлюз, не сервер: по всем парам вызова, скор по убыванию, при равенстве скора раньше та пара, что раньше стояла в `RerankRequest`. Ранг плотный и начинается с 1. Фаза A2 для отбора использует скор; ранг всё равно заполнен.

Ключ `texts` и голый массив TEI не отправляются и не разбираются.

### 4.4. Чат

`POST {base_url}/v1/chat/completions`

```json
{
  "model": "Qwen3-8B-Q4_K_M.gguf",
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."}
  ],
  "temperature": 0,
  "stream": false
}
```

- Непустой `GenerateRequest.messages` уходит как есть, роли и тексты без переписывания. Поле `prompt` при этом не добавляется.
- Если `messages` пуст и `prompt` задан — одно сообщение `user` с этим текстом.
- Оба пусты — `LlamaServerError` до HTTP.
- `stream` всегда `false`. Поток не разбирается.
- `max_tokens` есть в JSON только при непустом `max_output_tokens`.
- `temperature` берётся из запроса.

Ответ:

- Текст — `choices[0].message.content`, строка. Пустой список `choices`, отсутствие `content` или `content` не строка — `LlamaServerError`.
- `prompt_tokens` — `usage.prompt_tokens`, `completion_tokens` — `usage.completion_tokens`. Нет блока `usage` или поля — `LlamaServerError`, нули вместо пропуска не подставляются.
- `latency_ms` — время этого HTTP-вызова на клиенте, в миллисекундах. Поле `timings` сервера в ответ шлюза не копируется.

Один `infer` — один HTTP-вызов. Код 500 не запускает второй запрос внутри шлюза.

## 5. Классы шлюзов

Общий предок по-прежнему `EmbeddingGateway` / `RerankerGateway` / `LlmGateway`: методы `load`, `unload`, `infer`.

| Класс | `load` / `unload` | `infer` |
|---|---|---|
| `LlamaEmbeddingGateway` | пресет — имя файла эмбеддера | `EmbedRequest` → `EmbedResponse` |
| `LlamaRerankerGateway` | пресет — имя файла реранкера | `RerankRequest` → `RerankResponse` |
| `LlamaLlmGateway` | пресет — имя файла ответа | `GenerateRequest` → `GenerateResponse` |

Конструктор каждого шлюза получает `LlamaHttpClient`, имя пресета и таймаут. Эмбеддер дополнительно получает `batch_size`. Ссылки на `ArtifactStore` в конструкторе нет.

`load` при уже истинном `loaded` того же пресета не шлёт второй запрос. `unload` при `loaded = false` всё равно шлёт `POST /models/unload` (идемпотентность раздела 4.1) и оставляет флаг ложным. Так `GpuLease.release` на уже свободной аренде не обязан звать шлюз: сам lease при пустом `current` выходит сразу. Повторный `unload` шлюза безопасен.

`infer` при `loaded = false` бросает `LlamaServerError` и HTTP не открывает.

### 5.1. Ответ эмбеддера

Закрывает пункт про поля `EmbedResponse`. Тензора, массива numpy и объекта torch в модели нет.

В текущем коде у `EmbedResponseItem` только `item_id`, `success` и `cache_key`. Поля `dim` и `vector` входят в контракт вместе с реализацией этого документа.

`EmbedResponseItem`:

| Поле | Смысл |
|---|---|
| `item_id` | Тот же идентификатор, что в запросе |
| `success` | `true`, только если байты вектора есть |
| `dim` | Число компонент. При `success = false` поле равно 0 |
| `vector` | Байты little-endian float16 длины `dim * 2`. При неуспехе — пустые байты |
| `cache_key` | Эхо `EmbedItem.cache_key`, если фаза его передала. Шлюз по хешу ничего не ищет |

Порядок `items` совпадает с порядком `EmbedRequest.items`.

`EmbedRequest` не меняется: список `EmbedItem` (`item_id`, `text`, необязательный `cache_key`).

Пустой список `items`: пустой `EmbedResponse`, HTTP нет.

Шлюз режет список на последовательные группы по `batch_size`. Последняя группа короче. `batch_size` меньше 1 — ошибка конфигурации при создании шлюза.

### 5.2. Реранк и генерация

`RerankResponseItem` остаётся тройкой `pair_id`, `score`, `rank`. `score` — `relevance_score` сервера. Шлюз не знает `top_n`, `score_threshold` и `ContextBundle`.

`GenerateResponse` остаётся полями `text`, `prompt_tokens`, `completion_tokens`, `latency_ms`.

## 6. Как байты попадают в хранилище

Шлюз хранилище не вызывает. Пишет фаза A1, уже после возврата из `infer`. Это уточняет порядок вызовов в [3a](3a.%20artifact-store.md) §5: оба `save_*` выполняются только когда векторы документа уже собраны. Сборка байтов — обязанность шлюза, как и требовал §6 спеки хранилища; образ `app` при этом остаётся без torch и numpy.

`text_sha256` — SHA-256 от UTF-8 байтов текста, который уходит в эмбеддер, в нижнем регистре hex. Тот же алгоритм, что у хранилища. Повторной нормализации нет.

Ключ кэша фаза берёт у store: `embedding_cache_key(preset, "float16", text_sha256)`.

### 6.1. Чанки одного документа

1. Для каждого чанка посчитать `text_sha256` и спросить `get_cached_embedding`.
2. Попадание: байты из кэша, в список на `infer` чанк не входит. Счётчик `embed_cache_hit` даёт store.
3. Промах: чанк входит в `EmbedRequest`. После успешного `infer` фаза вызывает `put_cached_embedding` этими байтами. Счётчик `embed_cache_miss` даёт store.
4. Собрать ряды в порядке чанков: пара `(chunk_id, text_sha256)` и склейка байтов векторов. `dim` у всех рядов документа один.
5. Только после этого: `save_chunks`, затем `save_chunk_vectors(doc_id, rows, dim, payload)`. Store сам проверяет размер и связку.

`payload` — склейка векторов в порядке рядов. Длина `n * dim * 2`.

Если `infer` или проверка `dim` бросает исключение, фаза не вызывает ни `save_chunks`, ни `save_chunk_vectors`. Уже лежавший кэш отдельных текстов может остаться: он ключуется текстом, не документом. Новый `meta.json` документа при этом сбое не появляется, и следующий запуск не получает `skip` из-за полузаписи.

Длина кэшированных байтов не равна `dim * 2` или `dim` ряда отличается от остальных — исключение, документ `failed`, файлы документа не пишутся.

### 6.2. Варианты вопросов

Те же шаги для `item_id` `{question.id}:category` и `{question.id}:syn:{i}`. Успех заканчивается `save_questions_cache` и `save_question_vectors`. Сбой — ни один из этих двух методов не вызывается.

Нет вопросов в контексте — шаг не выполняется, как в спеке классов.

### 6.3. Индекс для поиска

`HybridSearcher` уже принимает `EmbeddingIndex` и читает вектор по `item_id`. Класс `StoreEmbeddingIndex` реализует этот индекс:

- Метод `activate(doc_id, chunk_matrix, question_matrix)` заменяет карту текущего документа. Матрицы — оболочки store (`payload` bytes, список id, `dim`) после `load_*`, который сам делает verify.
- `get_vector(item_id)` декодирует ряд little-endian float16 в последовательность обычных чисел либо возвращает `None`, если ключа нет.
- Чанки предыдущего документа в карте не остаются. Идентификатор `c_0001` у разных документов не смешивается.
- Шлюз из индекса не вызывается. Поиск эмбеддинги заново не считает.

`RetrievalPhase` перед вопросами документа, после успешной загрузки векторов, вызывает `activate`. Алгоритм `search` не меняется.

## 7. GpuLease

Контракт lease тот же: `acquire` выгружает предыдущий шлюз и загружает следующий; `release` выгружает текущий. Для этих шлюзов выгрузка — `POST /models/unload`, загрузка — раздел 4.1. Процесс `app` после `release` не занимает GPU.

Полный прогон даёт порядок имён `embedding` → `reranker` → `llm`. Одновременно `loaded` истинен только у одного шлюза. На сервере этому соответствует не больше одной модели из-за `--models-max 1` и явного `unload` перед следующим `load`.

Ошибка `load` вылетает из `acquire` до присваивания текущего шлюза. Ошибка `infer` внутрь lease не заворачивается.

## 8. Сборка Application

Целевой `Application.build` после утверждения и реализации:

- `LlamaHttpClient` с `base_url` из конфига;
- три шлюза раздела 5;
- `FileArtifactStore` как сейчас;
- `StoreEmbeddingIndex` и `HybridSearcher` с `RetrievalConfig` прогона;
- `GpuLease` на тех же шлюзах.

`AnswerVerifier` в граф не входит.

Фейковые шлюзы и `FakeHybridRetriever` остаются в тестах верхнего уровня спеки классов. Эти тесты собирают фазы сами и HTTP не открывают. Боевой сервер в unit-тесты шлюзов не входит: ответы HTTP подставляет поддельный клиент.

## 9. Сбои

Исключение шлюза — `LlamaServerError`.

| Ситуация | Где возникает | Что происходит с прогоном |
|---|---|---|
| Сервер недоступен, обрыв, таймаут | `load`, `unload` или `infer` | Исключение |
| HTTP не 200, кроме оговорённых 400/404 на `unload` | тот же вызов | Исключение, в тексте есть код и не длиннее 500 символов тела |
| Имя пресета серверу неизвестно | `load` или `infer` | Исключение «нетот модели» |
| Пустой вектор, битый `index`, разная размерность в одном `infer` | `infer` эмбеддера | Исключение, `EmbedResponse` нет |
| `infer` эмбеддера или реранкера внутри документа | фаза | Как сейчас: документ этой фазы `failed`, исключение наружу из документа не выходит, следующие документы идут |
| `load` / `unload` | фаза целиком | Фаза прерывается: модель для неё не готова. Отдельные документы «успехом» не помечаются |
| Ошибка чата на одной паре | `AnswerGenerator` | Шлюз одну попытку не повторяет. Генератор тратит `runtime.retries` отдельных `infer`, как в спеке ответа |

Реранкер и эмбеддер свои HTTP-вызовы не повторяют. Пауза `retry_pause_sec` к ним не относится.

## 10. Крайние случаи

- Пустой `EmbedRequest` и пустой `RerankRequest` не ходят в сеть и возвращают пустые ответы.
- `batch_size` больше числа промахов кэша — один POST.
- Ответ эмбеддинга с `index` не по порядку собирается в порядок запроса.
- Два чанка с одним текстом во втором документе берут кэш и не вызывают сервер.
- Все тексты документа найдены в кэше — `infer` не вызывается, `save_chunk_vectors` всё равно вызывается собранными байтами. `load` эмбеддера при этом нужен, только если есть хотя бы один промах или вопросы без кэша. Если считать нечего, фаза шлюз не арендует ради пустого HTTP. Векторы из кэша на диск документа пишутся.
- Нулевая длина байтов при `success = true` наружу не отдаётся: это ошибка разбора.
- Повторный `unload` уже снятого пресета для приложения успешен.
- `HybridSearcher` при отсутствии ключа в индексе ведёт себя по спеке поиска: пустой пакет и событие в трассе. Шлюз тут ни при чём.

## 12. Допущения

Сверено с описанием сервера llama.cpp (репозиторий ggml-org, `tools/server/README.md`) на момент написания:

1. Пути `POST /v1/embeddings`, `POST /v1/rerank`, `POST /v1/chat/completions`, `POST /models/load`, `POST /models/unload`, `GET /models` существуют у образа `server-cuda` с `--models-preset` и `--models-max`.
2. Поле `model` маршрутизируется в секцию ini. Имя секции — имя файла GGUF из списка роли.
3. Ответ `/v1/embeddings` при `encoding_format = float` имеет вид OpenAI: `data[].embedding` — массив чисел, `data[].index` — позиция входа. В README тело ответа не приведено, оно отсылает к схеме OpenAI. Это допущение контракта.
4. `/v1/rerank` с ключом `documents` возвращает объект с `results[].index` и `results[].relevance_score`. Опущенный `top_n` не отбрасывает строки. Это прямо сказано в README.
5. `/v1/chat/completions` отдаёт строку в `choices[0].message.content` и счётчики в `usage`. README называет маршрут совместимым с OpenAI и показывает блок `usage`; точное имя `content` — допущение этой совместимости.
6. `POST /models/load` возвращает `{"success": true}` до или в момент, когда `GET /models` уже может показать `loading` либо `loaded`. Опрос до `loaded` поэтому входит в `load`.
7. Выгрузка отсутствующего пресета отвечает 400 или 404. Иной код при «уже снят» будет считаться сбоем, пока наблюдение на боевом сервере это не поправит.
8. Образ в compose запущен без `--api-key`.

Если путь или имя поля на образе разойдётся с этим списком, это дефект относительно спецификации. Запасного вызова `POST /embedding` или `POST /reranking` шлюз не делает.

## 13. Вне этой спецификации

- Формула `confidence` не задаётся. Поле ответа остаётся пустым.
- `source_sha256` по-прежнему не влияет на skip.
- Выбор файла GGUF (какая квантизация лежит по пути пресета) делает оператор. Репозиторий файлы моделей не хранит.
- `AnswerVerifier` не вызывается и вторую модель не загружает.
