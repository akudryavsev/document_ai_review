# Спецификация: сборка контекста — v1.0

Статус: **утверждена**. Можно писать тесты и код по этому документу.

Связанные документы: [0. spec.md](0.%20spec.md) (разделы 6.8 и 7.2), [1. top-level-classes.md](1.%20top-level-classes.md) (инварианты `ContextBundle`), [4. hybrid-retriever.md](4.%20hybrid-retriever.md), [6. answer-verifier-generator.md](6.%20answer-verifier-generator.md).

Закрыты Q-CTX-1, Q-CTX-2, Q-CTX-4, Q-CTX-5, Q-CTX-6, Q-CTX-7. Открытых вопросов нет.

## 1. Назначение и границы

**Назначение.** Класс `ContextAssembler` по отобранным после реранка чанкам собирает один `ContextBundle` на пару «документ × вопрос». Режим по умолчанию — расширение до секции. Флаг пустого поиска приходит с фазы; сборщик его не пересчитывает.

**Границы ответственности.**

| Делает | Не делает |
|---|---|
| Группирует хиты по секции и собирает текст фрагментов | Не ищет и не реранжирует; пороги уже применены |
| Соблюдает бюджеты `max_section_tokens` и `max_total_tokens` | Не вызывает LLM и не фильтрует «да/нет/частично» — это `AnswerVerifier` |
| Формирует пустой бандл при `empty_search=true` | Не нумерует фрагменты префиксом `[1] стр. …` в поле `text` бандла |
| | Не пишет файл и не сжимает JSON. Боевой файл и отладочный дамп пишет фаза (раздел 3). Поле `context.compression` не читает |

*Пример: в спеке поведения префикс `[1] стр. 12–13, разд. 3.2.1` появляется при описании промпта. В примере JSON бандла поле `text` — чистый текст секции. Поэтому префикс добавляет генератор ответа, а не сборщик.*

**Публичный метод:** `assemble(doc_id, question, candidates, empty_search, chunks) -> ContextBundle`.

`chunks` — `ChunkBatch` документа. Конструктор получает `ContextConfig`, имена моделей эмбеддинга и реранкера и `retrieval.top_k` — они нужны полям бандла; в метод фаза их сейчас не передаёт.

## 2. Полный текст секции

Раздел 6.8 спеки поведения требует весь текст секции (все её чанки), а не только хиты реранка. Для обрезки и для `section_path is None` нужны соседи по `prev_id` / `next_id`. Ни того, ни другого в `CandidateRecord` нет.

`RetrievalPhase` к моменту `assemble` уже загрузила чанки документа и передаёт их пятым аргументом `chunks: ChunkBatch`. Сборщик сам в `ArtifactStore` не ходит.

`chunk_id` каждого хита при `empty_search=false` обязан быть в `chunks`. Чужого id нет — `ValueError`. При `empty_search=true` пакет `chunks` не читается (фаза может передать пустой или уже загруженный батч).

## 3. Выход

И пустой поиск, и непустой дают один и тот же тип. Меняются поля (разделы 3.4 и 4.6), не маршрут. Это ещё не запрос в модель: префикс `[n] стр. …` и инструкции дописывает генератор на фазе B.

### 3.1. Память

`assemble` возвращает pydantic-модель `ContextBundle`. Это объект в памяти того же прогона, не строка промпта и не файл.

`ContextAssembler` сам ничего не записывает: ни боевой JSON, ни дамп, ни событие трассы.

### 3.2. Диск, боевой файл

`RetrievalPhase` после успешного `assemble` проставляет на объекте `chunking_hash`, `retrieval_config_hash`, `reranker_config_hash` и вызывает `ArtifactStore.save_context`.

Файл: `{contexts_dir}/{doc_id}/{question_id}.json`. Кодировка UTF-8, отступ 2, несжатый JSON этой модели. Пустой поиск пишется так же: фаза B читает его с диска.

`context.compression=gzip` файл не сжимает. Сжатие остаётся будущей доработкой хранилища.

Исключение из `assemble` — файла нет. Пустой бандл вместо исключения не подставляется.

### 3.3. Диск, отладочный дамп

Тот же приём, что у extract/clean и у дампа поиска. Флаг по умолчанию выключен. Каталог — `debug/` под `runtime.cache_dir`. Это не зона `ArtifactStore`: дамп не участвует в `ArtifactGate`, его можно удалить, прогон остаётся валидным. На контракт `assemble` он не влияет.

Флаг — `retrieval.debug_dump` (по умолчанию `false`), тот же, что включает `{question_id}.retrieval.json`. При `true` фаза после успешной записи боевого JSON пишет соседний файл:

`{runtime.cache_dir}/debug/{doc_id}/{question_id}.context.md`

Пишет класс `ContextDebugDump`: `render` возвращает строку, `write` записывает файл. Его вызывает `RetrievalPhase`. Сборщик разметку не собирает.

При `false` файл не создаётся. При исключении из `assemble` или из `save_context` дампа нет: ошибка фазы не маскируется.

В `TraceEvent.debug_payload` тело дампа не кладётся — максимум путь или короткий summary.

Дамп для глаз. Фаза B его не читает: она читает боевой JSON.

```markdown
# context: reglament.docx · Q001

- empty_search: false
- reason: null
- category: Срок хранения персональных данных
- budget_used_tokens: 4210
- top_k: 20
- after_rerank: 5
- sections_used: 3.2.1. Сроки
- chunking_hash: …
- retrieval_config_hash: …
- reranker_config_hash: …

## Синонимы

- период хранения ПДн
- retention period for personal data

## Фрагменты

### Фрагмент 1 · rank 1 · score 0.87 · стр. 12–13 · truncated false
path: 3. Регламент / 3.2. Хранение / 3.2.1. Сроки
chunks: c_0412, c_0413, c_0414

…текст фрагмента как в поле text…
```

Правила разметки:

- шапка — поля бандла; пустая причина пишется `reason: null`; пустой `sections_used` — строка `sections_used: —`;
- синонимы — секция `## Синонимы`; каждый элемент `used_synonyms` строкой `- …` в исходном порядке; `category` туда не добавляется; пустой список — одна строка `- —`;
- фрагмент — секция `### Фрагмент {n}` в порядке `rank_after_rerank`, `n` с 1; это заголовок дампа, не префикс внутри `text`;
- `path:` — элементы `section_path` через ` / `, либо `path: —`;
- страницы — `стр. {from}–{to}`, если их несколько; `стр. {page}`, если одна; `стр. —`, если список пуст;
- `chunks:` — `chunks_included` через `, ` в порядке списка;
- тело — поле `text` как есть, без экранирования Markdown;
- при `candidates=[]` после синонимов идёт `## Фрагменты` и строка `Фрагментов нет.`

### 3.4. Поля при пустом поиске

`empty_search=true`. В объекте из раздела 3.1:

- `doc_id`, `question_id=question.id`, `category=question.category`;
- `used_synonyms` — копия `question.synonyms` в том же порядке (`category` в список не добавляется);
- `empty_search=true`, `reason="no_relevant_chunks"`, `candidates=[]`;
- `budget_used_tokens=0`;
- `retrieval_meta` содержит `top_k` и `after_rerank=0`.

Аргумент `candidates` при истинном флаге обязан быть пустым. Непустой список — `ValueError` (тот же инвариант, что у валидатора `ContextBundle`).

`empty_search=false` и пустой список — тоже `ValueError`. Фаза так не вызывает: пустой отбор она помечает `empty_search=true`. Сборщик флаг не «исправляет».

## 4. Непустой поиск, режим `section`

Куда кладётся бандл — раздел 3. Ниже только состав непустого объекта.

`context.expansion=section` — единственный режим этой итерации. Отдельных алгоритмов у значений `neighbors` и `none` нет. Соседи включаются сами в двух случаях: у хита нет раздела (раздел 4.3) или секция длиннее `max_section_tokens` (раздел 4.2). Иное значение `expansion` — `ValueError`, режим `section` вместо него не подставляется.

Входные кандидаты уже отобраны после реранка; у каждого задан `rerank_score`. `None` в этом поле при `empty_search=false` — `ValueError`.

Хит — чанк из `candidates`. Сосед — чанк, который попал во фрагмент только расширением (остальной текст секции или шаг окна `neighbors_fallback`) и сам хитом этого фрагмента не является.

### 4.1. Группы

Чанки с одним и тем же непустым `section_path` — одна секция. Ключ — весь список, не только последний заголовок.

Чанк с `section_path is None` в эту группировку не входит: для него строится окно соседей (раздел 4.3). Все «беспутевые» чанки одной секцией не становятся — иначе в контекст уехал бы весь неструктурированный текст.

Порядок секций — по лучшему `rerank_score` хита секции, по убыванию. Лучший скор — максимум среди отобранных хитов этой секции, не среди соседних чанков вне реранка.

### 4.2. Текст секции

Берутся все чанки документа с тем же `section_path`, в порядке `chunk_index`. Тексты соединяются одним `\n`, как в чанкере.

Если токенов секции больше `max_section_tokens`, полный текст не кладётся. В секцию входят только хиты реранка этой секции плюс `neighbors_fallback` чанков в каждую сторону **внутри той же секции**. Сосед за границей секции не добавляется. Повтор чанка в окне нескольких хитов одной секции — один раз, в порядке `chunk_index`.

`truncated=true`, если секция сокращена правилом `max_section_tokens` или позже правилом общего бюджета (раздел 4.4). Секция с хитом из бандла не исчезает целиком: хит остаётся.

Счётчик токенов — тот же `WhitespaceTokenCounter`, что в спецификации чанкинга (§4.3): пробельные фрагменты, без ML-токенизатора. Тест состава: короткая секция входит целиком; длинная не заменяется одним хитом без соседей, если соседи внутри секции есть и бюджет их вмещает. Числовые проверки бюджета считают токены этим же счётчиком.

### 4.3. Нет `section_path`

Окно хита — `neighbors_fallback` чанков по цепочке `prev_id` / `next_id` в каждую сторону (по умолчанию 2). Края документа окно обрезают.

Граница именованного раздела окно не останавливает. Чанк с непустым `section_path` входит, если он лежит на этой цепочке в пределах числа шагов. `section_path` самого фрагмента остаётся `None` (путь хита). Заголовок соседнего раздела в `sections_used` не добавляется; его текст в `text` есть.

Каждый хит без пути — отдельный фрагмент со своим окном. Пересекающиеся окна не сливаются: общий чанк может войти в несколько фрагментов, и его текст будет в бандле больше одного раза. Ранг у каждого фрагмента свой, по скору своего хита. Слияние пересечений в этой итерации не делается (раздел 10).

Внутри одного окна `chunks_included` без повторов. У фрагмента окна `truncated=false`, пока его не режет бюджет раздела 4.4. Отдельного лимита «как `max_section_tokens`» для окна спека поведения не задаёт.

### 4.4. Общий бюджет

Секции и окна сортируются по лучшему скору, по убыванию.

Каждый хит из `candidates` входит в бандл. Чтобы уложиться в `max_total_tokens`, снимаются только соседи.

Если сумма токенов больше бюджета:

1. Фрагменты обходятся от худшего скора к лучшему.
2. Внутри фрагмента на каждом шаге снимается сосед с наибольшим расстоянием по `chunk_index` до ближайшего хита этого фрагмента. При равном расстоянии снимается больший `chunk_index`.
3. После каждого снятия `text`, `pages` и `chunks_included` пересобираются. Фрагмент без чанков не появляется: у него остаётся хотя бы хит.
4. Остановка, когда сумма ≤ `max_total_tokens` или соседей больше нет.

`budget_used_tokens` — число токенов текстов, реально вошедших в `candidates[].text`. Префикса `[n]` в тексте нет, в бюджет он здесь не входит. Повтор одного и того же чанка в двух окнах без пути считается дважды, пока обе копии на месте.

Если после снятия всех соседей хиты всё ещё длиннее бюджета, хиты остаются. Так бывает у сверхдлинного чанка (чанкер допускает одно слово длиннее `max_tokens`) и у ничьей на границе `top_n`, когда хитов больше, чем заложено в проверку конфигурации ниже. `budget_used_tokens` тогда больше `max_total_tokens`.

**Проверка конфигурации.** При загрузке конфига `max_total_tokens >= reranker.top_n * chunking.max_tokens`, иначе `ValueError`, фазы не стартуют. `top_n` — число хитов, которое реранк обязан уметь отдать (в примере конфига 5). `chunking.max_tokens` — номинальный размер чанка (в примере конфига 800). Произведение 4000 при бюджете 6000 проходит. Сборщик эту арифметику не повторяет: он считает, что номинальные хиты влезают, и режет соседей.

### 4.5. Поля одного `ContextCandidate`

Один элемент `candidates` — одна секция или одно окно, не один исходный чанк.

| Поле | Правило |
|---|---|
| `rank_after_rerank` | Место фрагмента после сортировки по лучшему скору, с 1, без пропусков |
| `rerank_score` | Лучший реранк-скор хитов, из которых фрагмент вырос |
| `section_path` | Путь секции; при `None` у хита — тоже `None`, не пустой список, даже если окно зашло в именованный раздел. Тип после утверждения спецификации извлечения — `list[str] \| None` |
| `pages` | Уникальные номера страниц вошедших чанков по возрастанию; нулевые страницы не кладутся |
| `text` | Текст фрагмента без префикса `[n]` |
| `chunks_included` | `chunk_id` без повторов, в порядке `chunk_index` |
| `truncated` | `true`, если из фрагмента убран хотя бы один чанк секции или окна |

### 4.6. Поля бандла

- `doc_id`, `question_id`, `category`, `used_synonyms` — как в разделе 3.4.
- `empty_search=false`, `reason=None`.
- `retrieval_meta.top_k` — из конфигурации.
- `retrieval_meta.after_rerank` — число входных кандидатов `assemble` до расширения секциями.
- `retrieval_meta.sections_used` — последний элемент `section_path` каждого вошедшего фрагмента в порядке ранга; у пути `None` вклад не добавляется.
- `retrieval_meta.embedding_model` и `retrieval_meta.reranker_model` — имена из конструктора.
- Хеши `chunking_hash`, `retrieval_config_hash`, `reranker_config_hash` проставляет фаза после `assemble`, до записи файла (раздел 3.2).

## 5. Инварианты

- `empty_search=true` ⇔ пустые `candidates` и `reason="no_relevant_chunks"`.
- `empty_search=false` ⇒ в бандле есть хотя бы один кандидат, `reason is None`.
- `category` — канонический вопрос; синонимы только в `used_synonyms`.
- Внутри фрагмента `chunks_included` без повторов и в порядке документа.
- Каждый `chunk_id` из входных `candidates` входит хотя бы в один фрагмент бандла.
- Две секции с разными путями не склеены в один `text`.
- `rank_after_rerank` плотный и совпадает с убыванием `rerank_score`.
- Сборщик не меняет текст чанка: склейка только вставляет `\n` между чанками.
- Сборщик не вызывает `HybridRetriever`, `RerankerGateway`, `LlmGateway` и не читает `ArtifactStore`.
- Сборщик не сжимает бандл и не пишет файл. JSON и дамп пишет фаза (раздел 3).

## 6. Ошибки

| Ситуация | Поведение |
|---|---|
| `empty_search=true` и непустые `candidates` | `ValueError` |
| `empty_search=false` и пустые `candidates` | `ValueError` |
| `empty_search=false` и `rerank_score is None` | `ValueError` |
| `empty_search=false` и `chunk_id` хита нет в `chunks` | `ValueError` |
| `expansion` не равен `section` | `ValueError`. Запасной выход к соседям уже внутри `section` |
| `max_total_tokens < reranker.top_n * chunking.max_tokens` | `ValueError` при загрузке конфига, до `assemble` |

Сбой сборки — исключение в `execute` фазы A2. Документ помечается `failed`, остальные продолжаются. Пустой бандл с `no_relevant_chunks` вместо исключения не подставляется.

## 7. Граница с фазой B

Боевой JSON из раздела 3.2 читает `AnsweringPhase` без повторной сборки секций. Отладочный Markdown фаза B не читает. Верификация может выкинуть часть `candidates`, но заново секции не нарезает. Префикс `[n] стр. …` появляется в промпте генератора по уже лежащему в бандле тексту.

`used_synonyms` из бандла — список, который генератор вправе показать в блоке «искали по …».

| T-CTX-14 | `expansion` не равен `section` | `ValueError` |
| T-CTX-15 | `chunk_id` хита нет в `chunks` | `ValueError` |
| T-CTX-16 | `retrieval.debug_dump=false`, сборка прошла | `{cache}/debug/{doc_id}/{question_id}.context.md` не создаётся. Боевой JSON пары на месте |
| T-CTX-17 | `retrieval.debug_dump=true`, пустой поиск, два синонима | Файл `.context.md` есть. В нём `no_relevant_chunks`, `category`, оба синонима по порядку и строка `Фрагментов нет.` |
| T-CTX-18 | `retrieval.debug_dump=true`, один фрагмент | В дампе есть `text` фрагмента, `path` и `chunk_id`. В теле нет префикса `[1] стр.` |

Бюджетные тесты считают токены через `WhitespaceTokenCounter`.

Счётчик токенов бюджета не дублируется отдельной формулой: это `WhitespaceTokenCounter` из спецификации чанкинга.

## 9. Закрытые вопросы

| ID | Решение |
|---|---|
| Q-CTX-1 | Пятый аргумент `chunks: ChunkBatch`. Фаза пакет уже держит. Сборщик в `ArtifactStore` не ходит |
| Q-CTX-2 | Соседи — не отдельный режим. Нет раздела — окно `neighbors_fallback` (§4.3). Секция длиннее `max_section_tokens` — хиты и соседи внутри неё (§4.2). `expansion` кроме `section` — `ValueError` |
| Q-CTX-4 | Сжатия в этой итерации нет. Сборщик `compression` не читает. `gzip` остаётся доработкой хранилища, бандл на диске — обычный JSON |
| Q-CTX-5 | Хиты реранка не выбрасываются. Соседи снимаются под `max_total_tokens`. На загрузке конфига `max_total_tokens >= reranker.top_n * chunking.max_tokens` |
| Q-CTX-6 | Окно хита без пути заходит в соседний именованный раздел. Путь фрагмента остаётся `None` |
| Q-CTX-7 | Пока по фрагменту на хит без пути. Пересекающиеся окна не сливаются, текст может повториться. Слияние — раздел 10 |
