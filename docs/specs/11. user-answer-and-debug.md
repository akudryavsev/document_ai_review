## 1. Назначение

Два разных результата прогона.

| Кому | Куда | Что внутри |
|---|---|---|
| Пользователь | `results/<doc_id>.md` | Вопрос, ответ и пояснение. Пишется при любом `runtime.log_level` |
| Отладка | `{runtime.cache_dir}/debug/` | Промежуточные результаты. Полный набор — только при `runtime.log_level: DEBUG` |

`results/<doc_id>.jsonl` остаётся машинной строкой для eval. Это не текст для чтения. Промпт и сырой ответ модели в jsonl не пишутся.

## 2. Ответ пользователю

Файл: `{runtime.results_dir}/<doc_id>.md`. Кодировка UTF-8, в конце перевод строки.

`ResultSink` пересобирает файл из строк jsonl этого документа после каждой записи ответа. Порядок блоков совпадает с порядком строк файла. Строка другой тройки моделей остаётся и в jsonl, и в md.

Один блок на строку jsonl:

```markdown
## {category}

{текст ответа}

{explanation}
```

Между блоками одна пустая строка. Заголовка с именем документа нет. Нет цитат, синонимов отдельным списком, токенов, причин, имён моделей и промпта.

Текст ответа:

| Условие | Абзац |
|---|---|
| `answer` непустой | Текст `answer` как есть |
| `answer` пустой и `reason=missing_context` | `Контекст для ответа не собран.` |
| `answer` пустой и `reason=model_unavailable` | `Модель недоступна.` |
| `answer` пустой в остальных случаях | `Ответа нет.` |

Поле `answer` в jsonl эта подстановка не меняет. Для `model_unavailable` jsonl уже содержит «Модель недоступна.», в md попадает оно же.

Пояснение — следующий абзац после ответа. Если `explanation` после `strip` непустой, печатается эта обрезанная строка. Пустой `explanation` абзаца не даёт: пустой строки после ответа нет, блок заканчивается абзацем ответа. Подпись вроде «Пояснение:» не ставится. Текст поля jsonl эта печать не меняет.

Системные фразы в `explanation` идут в md так же, как текст модели: «Искали по: …» при пустом поиске и «Найденные фрагменты — в prepared_context.» при `model_unavailable`. Цитаты, промпт и `reason` по-прежнему не печатаются.

Один и тот же `category` в файле больше одного раза (две тройки моделей): под заголовком, перед абзацем ответа, отдельная строка с `answer_model`. При одной строке на этот `category` строки модели нет. Пояснение остаётся после ответа, не перед именем модели.

При `log_level`, отличном от `DEBUG`, md всё равно пишется.

## 3. Что уходит из jsonl

`prepared_context` в `AnswerRecord` всегда `null`.

Промпт, который раньше попадал в это поле при `model_unavailable`, пишется только в файл раздела 4 и только при `DEBUG`. Пояснение записи остаётся «Найденные фрагменты — в prepared_context.» до отдельной правки текста фразы; в md оно попадает как обычный непустой `explanation`.

Это заменяет в [6. answer-verifier-generator.md](6.%20answer-verifier-generator.md) абзац про `prepared_context` в разделе 6, строку T-GEN-06 и Q-ANS-9: промпт в записи ответа больше не хранится.

## 4. Отладочная папка

Корень: `{runtime.cache_dir}/debug/`. Та же папка, что у extract, clean, retrieval и context.

Полный набор пишется, когда `runtime.log_level` равен `DEBUG`. Тогда файлы ниже создаются даже при `extraction.debug_dump: false` и `retrieval.debug_dump: false`.

При другом уровне новые файлы этого раздела не создаются. Уже описанные дампы extract, clean, retrieval и context по-прежнему пишутся, если их собственный флаг включён. Форматы этих четырёх файлов не меняются.

| Файл | Когда при `DEBUG` | Содержимое |
|---|---|---|
| `{doc_id}.extract.md` | после extract | как в спецификации извлечения |
| `{doc_id}.clean.md` | после clean | как в спецификации очистки |
| `{doc_id}.chunks.md` | после нарезки, в том числе при нуле чанков | см. ниже |
| `{doc_id}/{question_id}.retrieval.json` | после поиска пары | как в спецификации поиска |
| `{doc_id}/{question_id}.context.md` | после сборки контекста | как в спецификации сборки |
| `{doc_id}/{question_id}.prompt.txt` | модель для пары вызывалась | точный текст промпта, который ушёл в шлюз |
| `{doc_id}/{question_id}.attempts.jsonl` | модель для пары вызывалась | одна строка на попытку |
| `{doc_id}/{question_id}.pair.json` | фаза B обработала пару, включая отказ до модели | итог пары |

Пустой поиск модель не вызывает: `prompt.txt` и `attempts.jsonl` для этой пары нет. `pair.json` и `context.md` есть.

Нет бандла (`missing_context`): есть только `pair.json`. Промпта и попыток нет.

### 4.1. Чанки

`{doc_id}.chunks.md`:

```markdown
# chunks: {doc_id}

## {chunk_id}

- pages: {page_from}–{page_to}
- section: {путь через « / » или null}

{text}
```

Чанки идут по `chunk_index`. Между секциями одна пустая строка. Ноль чанков: заголовок и строка `Чанков нет.`

### 4.2. Попытки модели

Строка `attempts.jsonl` — один JSON-объект:

| Поле | Смысл |
|---|---|
| `attempt` | Номер с 1 |
| `outcome` | `exception`, `empty`, `invalid_json`, `invalid_schema`, `citation_range` или `ok` |
| `text` | Сырой текст ответа. При исключении до ответа — пустая строка |
| `error` | Короткий текст ошибки или `null` при `ok` и при `empty` |

`invalid_json` хранит сообщение `JSONDecodeError`. `invalid_schema` — сообщение ошибки pydantic. `citation_range` — `номер цитаты вне диапазона`. `exception` — текст исключения.

Успешный разбор останавливает повторы, как и раньше. В файле есть и неудачные попытки, и последняя успешная со `outcome=ok`.

### 4.3. Итог пары

`pair.json`:

```json
{
  "doc_id": "...",
  "question_id": "...",
  "status": "ok",
  "reason": null,
  "found": false,
  "answer": "..."
}
```

Промпта и сырого текста модели в этом файле нет.

## 5. Классы

Логика в классах, не в функциях модуля.

| Класс | Делает |
|---|---|
| `UserAnswerReport` | Собирает текст md из списка `AnswerRecord` и пишет файл. `ResultSink` вызывает его после записи jsonl |
| `ChunkDebugDump` | Пишет `chunks.md`. Вызывает фаза A1, не `Chunker` |
| `AnswerDebugDump` | Пишет `prompt.txt`, `attempts.jsonl` и `pair.json`. Генератор отдаёт данные попыток, фаза B пишет файлы |

Флаг «писать отладку» эти классы получают как `enabled`. Сборка приложения ставит `enabled=true` при `runtime.log_level == DEBUG` и передаёт `runtime.cache_dir`. При `enabled=false` методы записи возвращают `None` и файлов не создают.

`AnswerGenerator` по-прежнему не пишет на диск. Он возвращает в записи ответа список попыток для дампа. В jsonl этот список не сериализуется: поле попыток в `AnswerRecord` не добавляется. Фаза забирает попытки отдельным значением рядом с записью.

## 7. README

После реализации README говорит: ответ для чтения — `experiments/results/<имя файла>.md`, в нём вопрос, ответ и пояснение; при `runtime.log_level: DEBUG` промежуточные файлы лежат в `experiments/debug/`.
