# Спецификация: чанкинг — v1.0

Статус: **утверждена**. Можно писать тесты и код по этому документу.

Связанные документы: [0. spec.md](0.%20spec.md) (разделы 6.3 и 7.2, `chunking_hash`), [1. top-level-classes.md](1.%20top-level-classes.md) (фаза A1), [2. extractor.md](2.%20extractor.md), [2a. cleaner.md](2a.%20cleaner.md), [3a. artifact-store.md](3a.%20artifact-store.md).

## 1. Назначение и границы

**Назначение.** Класс `Chunker` превращает `CleanedDocument` в `ChunkBatch`: сначала режет текст по разделам (`section_path`), затем длинный раздел — по `max_tokens` с перекрытием `overlap_tokens`. Полностью совпадающие тексты дедуплицируются.

**Границы ответственности.**

| Делает | Не делает |
|---|---|
| Нарезает очищенный документ на чанки с путями и страницами | Не читает файл и не очищает текст |
| Строит цепочку `prev_id` / `next_id` и сплошные `chunk_index` | Не считает эмбеддинги; векторного поля в `ChunkRecord` нет |
| Дедуплицирует одинаковые тексты внутри одного документа | Не вычисляет `chunking_hash` и не ставит `embedding_model` — это `IndexingPhase` |
| | Не обращается к сети и не пишет артефакты |

**Публичный метод:** `chunk(document: CleanedDocument) -> ChunkBatch`.

Параметры нарезки (`ChunkingConfig`) передаются в конструктор реализации, а не в метод `chunk`.

## 2. Вход

Источник текста — `CleanedDocument.blocks`. Плоское поле `text` повторно не разбирается.

Блоки `header` и `footer` до чанкера не должны доходить: их снимает `Cleaner`. Если они всё же присутствуют, `Chunker` их пропускает.

**Раздел** — максимальная подряд идущая группа блоков с одним и тем же `section_path`. `None` и непустой список — разные разделы. Два непустых списка сравниваются как последовательности строк без смены регистра.

В текст раздела входят все его блоки, включая заголовок, в порядке документа, соединённые одним `\n`. Тот же разделитель использует сборка контекста, чтобы склейка чанка и секции не расходилась.

## 3. Как хранится результат чанкинга

`chunk` возвращает один объект **`ChunkBatch` в памяти** (pydantic-модель). Это тот же стиль, что у `Extractor` / `Cleaner`: список записей внутри объекта, **не файл**.

```text
ChunkBatch
├── doc_id: str
├── chunks: list[ChunkRecord]    ← единственное содержимое нарезки
├── chunking_hash: str           ← Chunker оставляет ""; пишет IndexingPhase
└── embedding_model: str | None  ← Chunker оставляет None; пишет фаза
```

**Чанкер сам на диск ничего не пишет** и никаких библиотек сериализации не тянет: ни parquet, ни pyarrow, ни pandas. Только нарезка текста → список `ChunkRecord`.

Кто сохраняет файл — позже, не этот класс:

1. `IndexingPhase` получает `ChunkBatch`, считает эмбеддинги, проставляет `chunking_hash` / `embedding_model`.
2. `ArtifactStore.save_chunks` (+ отдельно векторы) пишет артефакт фазы A1.  
   Векторы появляются **на шаге хранилища/эмбеддинга**; в объекте сразу после `Chunker.chunk` поля вектора ещё нет.

Формат на диске — контракт [3a. artifact-store.md](3a.%20artifact-store.md) (JSONL + `vectors.f16` + `meta.json`, без pyarrow). На `Chunker` это не влияет.

Пример объекта сразу после `chunk` (упрощённо):

```json
{
  "doc_id": "reglament.docx",
  "chunking_hash": "",
  "embedding_model": null,
  "chunks": [
    {
      "chunk_id": "c_0000",
      "text": "3.2.1. Сроки\nСрок хранения составляет 5 лет.",
      "section_path": ["3.2.1. Сроки"],
      "page_from": 0,
      "page_to": 0,
      "chunk_index": 0,
      "prev_id": null,
      "next_id": "c_0001"
    }
  ]
}
```

| Поле `ChunkRecord` | Правило |
|---|---|
| `text` | Непрерывный фрагмент текста своего раздела; перекрытие — тоже подстрока этого раздела |
| `section_path` | При `preserve_section_path=true` — путь раздела (включая `None`). При `false` — у всех чанков `None` |
| `page_from`, `page_to` | Минимум и максимум `page` у блоков, давших текст чанка; если номеров нет — оба `0` |
| `chunk_index` | С 0, без пропусков, в порядке документа после дедупликации |
| `prev_id` / `next_id` | У первого / последнего — `None`, иначе `chunk_id` соседа |
| `chunk_id` | `c_{chunk_index:04d}` (например `c_0000`, `c_0412`); уникален внутри документа; после дедупликации индексы и id перенумеровываются сплошняком |

Цепочка `prev_id` / `next_id` идёт по всему документу и может соединять разные разделы. Окно соседей при обрезке секции эту цепочку дополнительно фильтрует — это сборка контекста, не чанкер.

Отладочный Markdown `{cache}/debug/{doc_id}.chunks.md` пишет фаза при `runtime.log_level: DEBUG`, не `Chunker`. Условие и формат — [11. user-answer-and-debug.md](11.%20user-answer-and-debug.md). На контракт `chunk` это не влияет.

## 4. Алгоритм

Параметры: `max_tokens`, `overlap_tokens`, `min_chunk_tokens`, `preserve_section_path`. Хеш этих четырёх значений уже считает `AppConfig.chunking_hash`; чанкер формулу хеша не дублирует.

### 4.1. Проверка конфигурации

`ValueError` без построения чанков, если:

- `max_tokens` < 1;
- `overlap_tokens` < 0;
- `min_chunk_tokens` < 0;
- `overlap_tokens` ≥ `max_tokens`.

*Пример: при `overlap_tokens=512` и `max_tokens=512` окно не сдвигается вперёд, разрез зацикливается. Поэтому перекрытие должно быть строго меньше лимита.*

### 4.2. Разрез по разделам

Каждый раздел обрабатывается отдельно. Текст одного чанка не содержит тексты двух разных `section_path`.

Короткий документ из одного абзаца без заголовка — один раздел с `section_path is None`.

### 4.3. Как считаются токены

В конфиге лимиты заданы в «токенах», но **модель эмбеддинга в `Chunker` не загружается**. Счётчик для чанкинга (и тот же — для бюджета контекста) — лёгкий локальный класс `WhitespaceTokenCounter`:

- текст режется по пробельным символам (`str.split()` без аргументов);
- каждый получившийся фрагмент = 1 токен;
- пустая строка = 0 токенов.

*Зачем так: окно эмбеддера в PoC — 4096, чанк по умолчанию — 512. Запас большой, расхождение с subword-токенизатором модели не выталкивает чанк за окно. Тянуть `transformers`/sentencepiece в чанкер незачем. Если позже понадобится точный токенизатор модели — подменяется только реализация счётчика, алгоритм нарезки тот же.*

Все сравнения с `max_tokens`, `overlap_tokens`, `min_chunk_tokens` идут через этот счётчик.

### 4.4. Разрез длинного раздела

Если раздел укладывается в `max_tokens` — один чанк с полным текстом раздела, без искусственного перекрытия.

Если не укладывается — последовательные чанки с перекрытием `overlap_tokens` (токены перекрытия входят в `max_tokens`). Объединение чанков **покрывает весь текст раздела без потерь**.

Границы реза, от мягких к жёстким (рекурсивно):

1. Разрывы между исходными блоками (символ `\n`, которым блоки склеены в текст раздела).
2. Границы предложений внутри куска: после `.`, `!`, `?`, `…`, если за ними пробел или конец строки.
3. Границы whitespace-токенов (слова).

Алгоритм набора чанка: жадно добавлять следующие куски текущего уровня, пока сумма токенов не превысит `max_tokens`; если очередной кусок не влезает целиком — спуститься на более мелкий уровень только для него. Следующий чанк начинается с хвоста в `overlap_tokens` токенов предыдущего.

Кусок, который сам не длиннее `max_tokens`, но не помещается в остаток текущего окна, не разрезается. Окно закрывается перед ним, и этот кусок начинает следующий чанк. Так абзац короче лимита остаётся на границе `\n`, даже если в предыдущем чанке ещё остались свободные токены.

Кусок длиннее `max_tokens` режется изнутри. Для блока: пока от начала окна до конца блока больше `max_tokens`, окно забирает не больше `max_tokens` токенов. Внутри окна целиком берутся предложения, которые помещаются. Предложение длиннее `max_tokens` добирается по словам до лимита. Предложение, которое само не длиннее лимита, но не входит в остаток, оставляет чанк на предыдущей границе предложения.

Когда от начала окна до конца блока остаётся не больше `max_tokens`, хвост блока входит в чанк целиком. Следующие блоки того же раздела дописываются следом, пока сумма не превысит `max_tokens`.

Если длина чанка не больше `overlap_tokens`, вычитать перекрытие значило бы оставить начало на месте и повторить почти тот же текст со сдвигом на слово. Тогда следующее окно начинается с конца текущего чанка, без перекрытия.

*Про «неразделимый кусок»: отдельной сущности нет. Крайний случай — одно слово длиннее `max_tokens` (длинный URL без пробелов). Его нельзя разрезать по правилам выше, и его нельзя выбросить. Такой фрагмент становится отдельным чанком и может превысить `max_tokens`. На обычных регламентах это редкость.*

### 4.5. `min_chunk_tokens` — без потери текста

Текст документа **никогда не удаляется** из‑за минимума. `min_chunk_tokens=0` означает «не сливать хвосты». При значении по умолчанию (80) действует правило слияния:

После нарезки раздела, если последний чанк раздела короче `min_chunk_tokens` и в этом разделе есть предыдущий чанк — **присоединить хвост к предыдущему** (даже если сумма чуть превысит `max_tokens`). Если чанк в разделе один и он короткий — оставить как есть: это весь раздел, выбрасывать нечего.

Склеивать чанки **разных** `section_path` ради минимума нельзя.

*Почему не обнулять параметр: мелкие хвостовые обрезки плохо ищутся эмбеддингом. Слияние с предыдущим сохраняет весь текст и убирает «обрывки». Обнуление допустимо в конфиге, если нужно увидеть сырую нарезку.*

### 4.6. `preserve_section_path`

При `true` чанк копирует `section_path` раздела, включая `None`.

При `false` у всех чанков `section_path is None` (путь для цитаты тогда пойдёт через страницу или номер абзаца на более поздних стадиях, если он проброшен; чанкер путь не выдумывает).

### 4.7. Дедупликация

После разреза чанки с полностью одинаковым `text` (посимвольно, с учётом регистра) считаются дублями. В пакете остаётся **первое** вхождение в порядке документа; у него свои страницы и путь. Затем `chunk_index`, `chunk_id` и `prev_id`/`next_id` перенумеровываются сплошняком.

Дедупликация не сравнивает чанки разных документов: на входе один документ. Дедупликация не удаляет уникальный текст: только полностью совпадающие копии.

### 4.8. Пустой вход

Нет блоков основного текста — `ChunkBatch` с `chunks=[]`, без исключения. `IndexingPhase` помечает документ `failed` / `zero_chunks` и продолжает прогон (случай T-RUN-02 верхнего каталога). Здесь фиксируется только выход чанкера.

## 5. Инварианты

- `chunk_index` идёт 0, 1, 2, … в порядке чтения.
- У первого `prev_id is None`, у последнего `next_id is None`; соседи ссылаются друг на друга.
- `chunk_id` уникальны внутри пакета.
- При `preserve_section_path=true` путь чанка равен пути раздела, из которого он нарезан.
- Нет чанка, чей текст содержит куски двух разделов.
- Каждый `text` — подстрока текста своего раздела.
- Объединение текстов чанков раздела (с учётом перекрытий) покрывает весь текст раздела; из‑за `min_chunk_tokens` текст не выбрасывается.
- На границе класса нет векторов и нет зависимости от ML-токенизатора модели.
- Повторный `chunk` на том же входе и конфигурации даёт те же `chunk_id`, тексты и порядок.

## 6. Ошибки

| Ситуация | Поведение |
|---|---|
| Негодная конфигурация (раздел 4.1) | `ValueError` |
| Пустой документ | Пустой пакет, без исключения |

## 7. Взаимодействие с соседними классами

```
CleanedDocument
    → Chunker.chunk → ChunkBatch          # только память, без файла
        → IndexingPhase: hash + embedding_model
        → EmbeddingGateway.infer(chunk_id, text)
        → ArtifactStore.save_chunks (+ vectors)  # .cache/emb/<doc_id>/…
```

Ключ эмбеддинга — `chunk_id`. Его же читает гибридный поиск. Схему id между чанкером и эмбеддером не менять: фаза A1 передаёт `EmbedItem(item_id=chunk.chunk_id, text=chunk.text)`.

| T-CHK-17 | Предложение не длиннее `max_tokens`, но не помещается в остаток окна | Чанк заканчивается перед этим предложением; следующее окно начинается с перекрытия, предложение не разрезано |

## 9. Закрытые решения этой редакции

- Счётчик токенов — `WhitespaceTokenCounter` (§4.3); тот же для бюджета контекста.
- `min_chunk_tokens` — порог слияния хвоста с предыдущим в том же разделе; текст не удаляется (§4.5).
- Границы реза: абзацы → предложения → слова; сверхдлинное слово — чанк длиннее лимита (§4.4).
- Блок длиннее `max_tokens` режется окнами изнутри; кусок короче лимита, не влезший в остаток, не дробится. Чанк не длиннее `overlap_tokens` не порождает сдвиг на слово (§4.4).
- При `preserve_section_path=false` путь у чанков — `None`; `chunk_id = c_{chunk_index:04d}`; из дублей остаётся первое вхождение.
