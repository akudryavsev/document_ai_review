# Спецификация: списки моделей — v1.2

Статус: **утверждена**. Тесты и код пишутся по этому документу. v1.0 описывала списки строк без параметров пресета. v1.1 сверяла `models.ini` в `run` без записи. v1.2: расходящийся файл пишет сам `run` и останавливается, пока оператор не пересоздаст `inference`.

Связанные документы: [0. spec.md](0.%20spec.md) (конфиг, CLI, сводка), [3a. artifact-store.md](3a.%20artifact-store.md) (корни каталогов), [6. answer-verifier-generator.md](6.%20answer-verifier-generator.md) (`AnswerRecord`), [7. llama-gateways.md](7.%20llama-gateways.md) (пресет и HTTP-поле `model`), [8. eval.md](8.%20eval.md) (группа метрик).

## 1. Назначение и границы

**Назначение.** Пользователь кладёт файлы GGUF в каталог `models/` и в `config.yaml` перечисляет эти файлы вместе с параметрами пресета llama-server. У эмбеддера, реранкера и модели ответа список может содержать несколько записей. Прогон проходит комбинации по очереди и записывает в результат, какая тройка его посчитала.

**Делает:**

- Задаёт поля `embedding.models`, `reranker.models`, `answer.models` как списки записей «имя файла + параметры секции».
- Проверяет имена и параметры до фаз.
- Собирает один `deploy/llama/models.ini` из всех записей трёх списков.
- Гоняет декартово произведение списков при одной загруженной GGUF.
- Раскладывает артефакты по именам файлов и пишет три имени в строку ответа и в сводку.
- Описывает, как eval группирует строки по тройке.

**Не делает:**

- Не выбирает карточки Hugging Face и не качает файлы.
- Не поднимает две GGUF одновременно. В контейнере `inference` остаётся `--models-max 1`.
- Не переписывает `models.ini` и не перезапускает контейнер `inference` внутри цикла комбинаций.
- Не подбирает параметры по карточке модели. В секцию попадают только скаляры, которые пользователь записал в `params`.
- Не добавляет список моделей верификации. Поле `verification.model` в этот цикл не входит.
- Не меняет формулы метрик. Меняется только ключ группы и путь к кандидатам и контекстам, см. раздел 10 и [8. eval.md](8.%20eval.md).

## 2. Запись модели в конфиге

Имя модели — имя файла в каталоге `models/` на хосте. В контейнере `inference` тот же файл лежит как `/models/<имя>`. Имя включает суффикс `.gguf`. Это один сегмент пути: без `/`, без `\`, не `.` и не `..`.

Роль задаёт список, в котором стоит запись. Элемент списка — объект с полем `name` и необязательным объектом `params`. Строка вместо объекта — ошибка конфигурации.

```yaml
embedding:
  models:
    - name: bge-m3-q8.gguf
      params:
        pooling: cls

reranker:
  models:
    - name: bge-reranker.gguf
      params:
        pooling: rank
    - name: qwen-reranker.gguf
      params:
        pooling: rank

answer:
  models:
    - name: Qwen3-8B-Q4_K_M.gguf
    - name: Llama-3.1-8B-Q4_K_M.gguf
      params:
        ctx-size: 8192
```

Порядок записей в списке — порядок цикла. Один элемент списка — обычный прогон из одной комбинации.

Ключ `model` в той же секции допустим и означает список из одной записи того же вида. Одновременно заданные `model` и `models` — ошибка конфигурации до фаз. Строка в `model` тоже ошибка: у одной модели те же поля `name` и `params`.

`params` — набор скаляров, которые llama-server читает из секции пресета. Ключ: строчные латинские буквы, цифры и дефис, начинается с буквы (`pooling`, `ctx-size`). Значение: строка, целое, конечное число или логическое. Список, вложенный объект, пустая строка и строка с переводом строки не допускаются. Нет ключа `params` — пустой набор.

Обязательные параметры:

| Роль | Обязательный ключ | Допустимые значения |
|---|---|---|
| Эмбеддер | `pooling` | `mean`, `cls`, `last` |
| Реранкер | `pooling` | `rank` |
| Ответ | нет | — |

Ключи, которые пишет роль, пользователь в `params` не задаёт: `model`, `embedding`, `reranking`. У модели ответа в `params` нет и `pooling`. Повтор ключа внутри `params` — ошибка конфигурации.

Пресет llama-server, поле `model` в HTTP, каталоги артефактов и поля тройки в результате используют `name` — имя файла. Параметры пресета в эти поля не входят. Отдельное короткое имя секции пользователь не задаёт.

## 3. Проверка до фаз

`run` и `write-models-ini` проверяют все три списка до фаз и до записи ini. Нарушение — ненулевой код, фазы не стартуют, ini не переписывается.

- Список роли отсутствует или пуст.
- Элемент не объект с `name`, либо имя не проходит правила раздела 2.
- Нет обязательного параметра роли или значение вне таблицы раздела 2.
- В `params` запрещённый ключ, повтор ключа или значение не скаляр.
- В одном списке имя повторяется.
- Одно и то же имя стоит в двух ролях.
- Файла `models/<имя>` нет. Каталог — `models` в корне репозитория; внутри контейнера `app` это `/models`, тот же том, что у `inference`.

## 4. Файл models.ini

Класс `LlamaModelsIni` строит текст пресета и сравнивает его с файлом `deploy/llama/models.ini`.

Команда:

```bash
python main.py write-models-ini --config config.yaml
```

Она перезаписывает этот файл каноническим текстом всех записей конфига. Секция `[*]` содержит `ctx-size = 4096`. Дальше секции идут в порядке ролей: эмбеддеры, реранкеры, модели ответа, внутри роли — в порядке списка. Заголовок секции и поле HTTP `model` равны `name`. Строка `model` внутри секции равна `/models/<name>`.

Строки секции, по порядку:

1. `model = /models/<name>`.
2. Флаги роли. Эмбеддер: `embedding = true`. Реранкер: `embedding = true`, затем `reranking = true`. Модель ответа этих флагов не получает.
3. Ключи `params` в порядке записи в YAML. Целое пишется десятичным числом, логическое — `true` или `false`, число — десятичной дробью без экспоненты, строка — как есть.

Ключ секции перекрывает одноимённый ключ `[*]`. Поэтому `ctx-size` в `params` задаёт контекст только этой модели, а у секции без этого ключа остаётся 4096 из `[*]`. Это поведение llama-server; приложение вторую проверку перекрытия не делает.

Пример для списков раздела 2:

```ini
[*]
ctx-size = 4096

[bge-m3-q8.gguf]
model = /models/bge-m3-q8.gguf
embedding = true
pooling = cls

[bge-reranker.gguf]
model = /models/bge-reranker.gguf
embedding = true
reranking = true
pooling = rank

[qwen-reranker.gguf]
model = /models/qwen-reranker.gguf
embedding = true
reranking = true
pooling = rank

[Qwen3-8B-Q4_K_M.gguf]
model = /models/Qwen3-8B-Q4_K_M.gguf

[Llama-3.1-8B-Q4_K_M.gguf]
model = /models/Llama-3.1-8B-Q4_K_M.gguf
ctx-size = 8192
```

`run` до фаз сравнивает файл с текстом полного конфига, до сужения списков флагами CLI. Текст совпадает — фазы стартуют, файл не трогают. Расхождение — `run` перезаписывает файл каноническим текстом, фазы не стартуют, код выхода ненулевой. Сообщение говорит, что файл уже обновлён, и просит пересоздать контейнер `inference`, затем повторить `run`:

```text
models.ini обновлён по спискам конфига.
Пересоздайте контейнер inference, чтобы он перечитал пресет, затем повторите run:

  docker compose --profile poc up -d --force-recreate inference
```

`run` контейнер не перезапускает и образы не пересобирает: процесс llama-server читает пресет только при старте, а из контейнера `app` Docker недоступен. Пересоздание нужно, потому что обычный `up -d` не следит за содержимым bind-mount.

Команда `write-models-ini` остаётся: она пишет тот же канонический текст и сразу завершается. Её вызывает оператор, которому нужен файл до первого `up` сервиса `inference`.

Ручная правка ini расходится с каноническим текстом: тот же `run` перезаписывает файл и останавливается.

Контейнер пересоздают один раз, когда `run` переписал ini: другое имя, другие `params` или другой порядок записей. Пока текст тот же, уже запущенный `inference` держит все секции, и следующий `run` файл не трогает.

## 5. Цикл прогона

Комбинация — тройка `(эмбеддер, реранкер, модель ответа)`. Их число — произведение длин трёх списков. Пример раздела 2 даёт четыре комбинации.

Порядок:

```text
для каждого эмбеддера из embedding.models:
    фаза A1 этим пресетом, если A1 запрошена
    для каждого реранкера из reranker.models:
        фаза A2 этой парой, если A2 запрошена
        для каждой модели ответа из answer.models:
            фаза B этой тройкой, если B запрошена
```

`--phase` по-прежнему выбирает, какие фазы входят в прогон. Незапрошенная фаза свой пресет не грузит. Запрошенная B без A2 в этом запуске читает уже лежащие контексты пары «эмбеддер × реранкер». Нет бандла вопроса — та же отсутствующая связка, что и сейчас у одной модели.

На GPU контейнера одновременно одна GGUF. Следующий пресет загружается после выгрузки предыдущего. Пропущенная по хешам фаза шлюз не арендует.

Все секции уже лежат в `models.ini`, прочитанном при старте процесса `inference`. Цикл файл не меняет и контейнер не перезапускает: у каждого имени свои строки секции, а смена модели — `load`/`unload` пресета из [7. llama-gateways.md](7.%20llama-gateways.md). Два эмбеддера с разным `pooling` в одном запуске дают две секции в том же файле; между ними перезапуска нет.

Смена файла на диске при том же имени не меняет хеш чанкинга. Повтор такого эмбеддера требует `--force-phase A1`, реранкера — `--force-phase A2`, модели ответа — `--force-phase B`. Флаг силы действует на все комбинации запрошенных фаз этого запуска.

## 6. Каталоги артефактов

Корни `cache_dir`, `index_dir`, `contexts_dir` и `results_dir` остаются полями конфига. Под корнями каталог называется именем файла модели. Раскладка [3a](3a.%20artifact-store.md) живёт внутри этого префикса. Префикс есть и при списке из одного имени.

```text
{cache_dir}/emb/{embedding_model}/{doc_id}/
{cache_dir}/questions/{embedding_model}/
{index_dir}/{embedding_model}/{reranker_model}/{doc_id}/
{contexts_dir}/{embedding_model}/{reranker_model}/{doc_id}/{question_id}.json
{cache_dir}/answers/{embedding_model}/{reranker_model}/{answer_model}/{doc_id}/meta.json
```

`embed_cache` по-прежнему один на `cache_dir`. Ключ кэша уже включает имя модели, здесь это имя файла эмбеддера.

Разные эмбеддеры не делят векторы чанков. Разные реранкеры не делят кандидатов и контексты. Разные модели ответа не делят meta фазы B, поэтому вторая модель ответа не пропускается из-за meta первой.

`results/<doc_id>.jsonl` общий для всех комбинаций прогона.

## 7. Строка результата и сводка

В `AnswerRecord` три поля — имена файлов комбинации, которая посчитала строку:

| Поле | Значение |
|---|---|
| `embedding_model` | Имя файла эмбеддера |
| `reranker_model` | Имя файла реранкера |
| `answer_model` | Имя файла модели ответа |
| `model` | То же значение, что `answer_model` |

Поля заполняются и у ответа модели, и у строки пустого поиска.

`ResultSink` пишет jsonl так: строки с тем же `question_id` и той же тройкой заменяются новой строкой, остальные строки файла сохраняют порядок, новая строка встаёт в конец. Пропуск фазы B файл ответов не переписывает.

`RunSummary` хранит список `combinations`. Элемент:

| Поле | Значение |
|---|---|
| `embedding_model`, `reranker_model`, `answer_model` | Тройка |
| `phases` | Счётчики `computed` / `skipped` / `failed` по фазам, которые для этой тройки запрашивались |

Порядок элементов — порядок цикла раздела 5. Верхние счётчики фаз сводки — суммы по комбинациям. В `model_versions` три списка имён в порядке конфига, без повторов внутри списка: все эмбеддеры, все реранкеры и все модели ответа, которые этот запуск обошёл.

`run_summary.json` по-прежнему один файл в `results_dir`.

## 8. Повторный прогон

Повтор с теми же списками и теми же хешами пропускает готовые фазы. Строка ответа той же тройки при пропуске B остаётся на диске.

Новое имя в списке — отсутствующий каталог этой комбинации, фаза считается. Старые комбинации при валидных хешах пропускаются.

`--force-phase` пересчитывает указанную фазу у каждой комбинации этого запуска.

## 9. CLI

Полный цикл — одна команда `python main.py run --config config.yaml`. Отдельный цикл по shell и отдельные каталоги результатов на каждую модель не требуются.

`--embedding-model`, `--reranker-model` и `--answer-model` оставляют в своей роли одну запись на этот запуск. Имя должно уже быть в списке конфига: параметры берутся из этой записи, а не из флага. Имени нет в списке — ошибка до фаз. Остальные роли берутся из конфига целиком. Канонический ini при этом не сужается: сверка идёт с текстом всех записей файла конфига, флаг только выбирает, какие пресеты этот `run` загружает.

`--results-dir`, `--index-dir`, `--contexts-dir` и `--cache-dir` остаются корнями. Префиксы раздела 6 добавляются под ними. `--cache-dir` задаёт `runtime.cache_dir`, корень чанков, вопросов, `embed_cache` и meta ответов.

## 10. Eval

`gt.json` общий для всех троек. В эталоне имён моделей нет.

Eval делит строки предсказаний по тройке `embedding_model`, `reranker_model`, `answer_model`. Внутри тройки пара `(doc_id, question_id)` уникальна. Та же пара в другой тройке — отдельное предсказание. Строка без любого из трёх полей — ошибка eval до метрик.

Один запуск `python main.py eval` пишет в stdout JSON-массив отчётов, по отчёту на тройку, в порядке первого появления тройки в jsonl. Формулы отчёта — [8. eval.md](8.%20eval.md). В отчёте те же три имени.

Кандидаты и бандл контекста этой тройки читаются по путям раздела 6. Поисковые метрики совпадают у моделей ответа с одним эмбеддером и одним реранкером. Exact match, косинус, цитаты и `found_e2e` считаются по строкам своей тройки.

Косинус всех отчётов считает первый эмбеддер из `embedding.models` конфигурации eval. Его имя пишется в каждый отчёт как `cosine_embedding_model`.

Токены и latency блока стоимости берутся из строк тройки. Счётчики фаз этого блока копируются из элемента `combinations` в `run_summary.json`, если сводка есть и тройка в ней найдена. Иначе поле фаз — `null`.

## 11. Каталог тестов

Сеть и GPU не используются. Имена файлов в тестах — строки, наличие файла подменяется портом проверки.

| ID | Случай | Ожидание |
|---|---|---|
| T-MDL-01 | Два имени в `answer.models`, по одному в остальных | Одна A1, одна A2, две B. На вопрос две строки jsonl с разными `answer_model` |
| T-MDL-02 | Пустой `models` или оба ключа `model` и `models` | Ошибка до фаз |
| T-MDL-03 | Имени нет среди файлов `models/` | Ошибка до фаз, ini не изменён |
| T-MDL-04 | Одно имя в двух ролях или дважды в одном списке | Ошибка до фаз |
| T-MDL-05 | `model` — одна запись без `models` | Список из одного имени с его `params` |
| T-MDL-06 | `write-models-ini` на списках раздела 2 | Текст раздела 4 |
| T-MDL-07 | `run` при ini, отличном от канонического текста | Файл переписан каноническим текстом, ошибка до фаз, в тексте есть команда пересоздать `inference` |
| T-MDL-08 | Вторая модель ответа при уже посчитанной первой | B второй считается. Meta лежат в разных каталогах `answers/` |
| T-MDL-09 | Повторная запись той же тройки | В jsonl одна строка этой тройки и вопроса, это новая запись |
| T-MDL-10 | Пустой поиск | В строке заполнены три имени, `model` равен `answer_model` |
| T-MDL-11 | `--answer-model` с именем из списка конфига | В этот запуск входит только эта модель ответа. Канонический ini остаётся полным текстом конфига |
| T-MDL-12 | Eval двух троек и одного эталона | Два отчёта. Пара эталона сопоставлена в каждом. Путь кандидатов содержит имена эмбеддера и реранкера |
| T-MDL-13 | Две строки одной тройки с одним `(doc_id, question_id)` | Ошибка eval до отчёта |
| T-MDL-14 | Две тройки с разными эмбеддерами | `cosine_embedding_model` в обоих отчётах — первое имя `embedding.models` |
| T-MDL-15 | Два эмбеддера с `pooling` `mean` и `cls` | Один ini, две секции, в каждой свой `pooling`. Между комбинациями файл ini не меняется |
| T-MDL-16 | Эмбеддер без `pooling`, с `pooling: none` или реранкер с `pooling`, отличным от `rank` | Ошибка до фаз, ini не изменён |
| T-MDL-17 | В `params` ключ `model`, `embedding`, `reranking` или у ответа `pooling` | Ошибка до фаз |
| T-MDL-18 | Элемент списка — строка, а не объект с `name` | Ошибка до фаз |
| T-MDL-19 | `--answer-model` с именем, которого нет в списке конфига | Ошибка до фаз |

## 12. Вне этой спецификации

- Верификатор и его модель.
- Параллельная загрузка нескольких GGUF и изменение `--models-max`.
- Перезапуск контейнера `inference` из `run`. `run` пишет расходящийся ini и останавливается; контейнер пересоздаёт оператор.
- Автоматическое скачивание весов.
- Выбор квантизации под объём конкретной видеокарты. Пользователь кладёт файл, который помещается на GPU один.
