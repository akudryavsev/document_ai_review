# Спецификация: извлечение текста — v1.0

Статус: **утверждена**. Можно писать тесты и код по этому документу.

Связанные документы: [0. spec.md](0.%20spec.md) (раздел 6.1), [1. top-level-classes.md](1.%20top-level-classes.md) (фаза A1), [2a. cleaner.md](2a.%20cleaner.md), [3. chunker.md](3.%20chunker.md).

## 1. Назначение и границы

**Назначение.** Прочитать один файл `.docx` или `.pdf` и вернуть упорядоченные блоки текста с данными, достаточными для цитирования ответа: страница и раздел, а если их нет — номер абзаца.

**Делает:** разбор файла в блоки, построение пути заголовков, нумерация абзацев, встраивание текста сносок в абзацы, где они упомянуты.

**Не делает:** очистку колонтитулов и нормализацию пробелов (`Cleaner`); чанкинг; OCR в этой итерации; эмбеддинги и поиск; решение о продолжении прогона (`IndexingPhase`).

**Публичный метод** (контракт фазы A1): `extract(document: DocumentRef) -> ExtractedDocument`.

Порядок в фазе: `extract` → при отказе очистка и чанкинг документа пропускаются → иначе `clean` → `chunk`.

## 2. Иерархия классов и кто принимает решения

Фаза и фасад зависят только от абстрактного `Extractor`. Внутри — два разных уровня выбора; их нельзя смешивать.

```
Extractor (абстрактный)
├── DocxExtractor              # .docx
├── PdfExtractor               # PDF: текстовый слой + (позже) решение об OCR по страницам
│       └── использует PdfPageOcr  # не наследник Extractor; сервис страницы
└── FormatAwareExtractor       # только выбор по расширению файла
```

| Класс | Роль |
|---|---|
| `Extractor` | Объявляет `extract`. Общая логика **без** выбора формата и **без** решения «нужен ли OCR»: сборка `section_path`, нумерация абзацев, склейка `text`/`pages`, встраивание сносок |
| `DocxExtractor` | Читает пакет DOCX |
| `PdfExtractor` | Владеет PDF целиком: читает текстовый слой **по страницам**, решает, какие страницы считать пустыми, и когда подключать OCR |
| `PdfPageOcr` | (будущее) Распознаёт **одну** страницу-изображение → текст. Не знает про DOCX и не вызывается фазой напрямую |
| `FormatAwareExtractor` | По `DocumentRef.suffix` выбирает `DocxExtractor` или `PdfExtractor`. Неизвестный суффикс — `ValueError`. **Не** выбирает «PDF обычный vs OCR» |

### 2.1. Что решает `FormatAwareExtractor`

Только тип контейнера файла: `.docx` или `.pdf`. На этом его работа заканчивается.

Он **не** смотрит внутрь PDF и **не** решает, нужен ли OCR. Иначе при смешанном документе (текст + сканы) пришлось бы либо ошибочно слать весь файл в OCR, либо ошибочно считать его «текстовым».

### 2.2. Что решает `PdfExtractor`

Весь жизненный цикл одного PDF. Алгоритм решения (норма на будущее; в итерации 1 OCR ещё нет — см. раздел 5.3):

1. Для каждой страницы извлечь текст слоя.
2. Страница **пустая**, если после удаления пробельных символов текста нет (типичный скан или чистый бланк).
3. Непустые страницы оставить как есть.
4. Пустые страницы:
   - итерация 1 — OCR нет: если пусты **все** страницы → `no_text_layer`; если пуста **часть** → в этой итерации пустые страницы дают пустой вклад в `pages`, документ не падает целиком только из‑за одного скана в конце (*осознанное упрощение; см. раздел 8*);
   - после появления OCR — для каждой пустой страницы вызвать `PdfPageOcr`, подставить распознанный текст, затем уже строить блоки по всему документу.

*Пример проблемы: титул и последняя страница — скан, середина — нормальный текст. Решение «весь файл → PdfOcrExtractor» в `FormatAwareExtractor` по расширению `.pdf` было бы неверным: середina уже есть, OCR нужен только двум страницам. Поэтому развилка «текст / OCR» живёт внутри `PdfExtractor`, постранично.*

### 2.3. Чего нет в базовом `Extractor`

Базовый класс **не** содержит ветку «попробовать PDF, потом OCR». Ему неизвестны страницы PDF и DOCX. Иначе общая логика обрастёт форматными исключениями, а `DocxExtractor` будет тащить мёртвый код PDF.

Итог: фаза вызывает один `extract`; диспетчер знает только расширение; про сканы знает только `PdfExtractor`.

### 2.4. Библиотеки реализации (предварительный выбор)

Контракт `extract` и модель блоков от конкретной библиотеки не зависят. Пакеты подключаются только в наследниках на шаге реализации, после утверждения этой спецификации.

Предварительный стек итерации 1:

| Формат | Класс | Пакет | Лицензия |
|---|---|---|---|
| DOCX | `DocxExtractor` | `python-docx` | MIT |
| PDF (текстовый слой) | `PdfExtractor` | `pypdf` | BSD |

Критерии выбора (их же применять при замене):

- открытая разрешительная лицензия (MIT / BSD / Apache-2.0);
- работа полностью локально, без сетевых API;
- без GPU и без тяжёлых ML-зависимостей на этапе извлечения;
- небольшой граф зависимостей, установка в PoC-образ без нативных «комбайнов».

`FormatAwareExtractor`, `Cleaner` и фаза A1 эти пакеты напрямую не импортируют. OCR, если появится, выбирается отдельно и в эту таблицу не входит.

*Если на реальных регламентах `pypdf` даст слишком бедный текстовый слой, замена допускается только на пакет с теми же критериями лицензии и веса; контракт блоков не меняется. Смена пакета — отдельное утверждение, не «тихо в коде».*

## 3. Как хранится результат извлечения

`extract` возвращает один объект `ExtractedDocument` (pydantic-модель **в памяти**). На диск извлекатель ничего не пишет: объект идёт в `Cleaner` → `Chunker`; фаза сохраняет уже чанки.

Текст документа хранится **один раз** — в списке `blocks`. Отдельных полей-копий всего текста в модели нет.

```text
ExtractedDocument
├── doc_id: str
├── source_sha256: str              ← отпечаток исходного файла (раздел 3.0)
├── has_text_layer: bool
├── failure_reason: str | None
└── blocks: list[ExtractedBlock]    ← единственное хранилище текста
```

`blocks` — **список** (не словарь), в порядке чтения. Каждый элемент — заголовок, абзац, таблица или колонтитул; у элемента своё поле `text`.

*Почему не держать ещё `text` и `pages` как поля: на документе ~300 страниц это было бы три копии одних и тех же строк в RAM. Для отладки и редких нужд достаточно методов, которые собирают строку из `blocks` на лету и не хранят результат в модели.*

Методы документа (не поля):

| Метод | Что возвращает |
|---|---|
| `joined_text()` | Все `blocks[].text` через `\n` |
| `page_texts()` | Список строк по страницам: индекс 0 = страница 1; блок с `page is None` в раскладку по страницам не входит; если ни у одного блока основного текста нет `page` — список из одного элемента `[joined_text()]` |

### 3.0. Отпечаток исходного файла (`source_sha256`)

`doc_id` обычно равен имени файла и **не** доказывает, какой байтовый файл обработали: файл могли заменить под тем же именем. Для наблюдаемости и повторных прогонов нужен отдельный отпечаток содержимого.

| Поле | Правило |
|---|---|
| `source_sha256` | Нижний регистр, hex-строка SHA-256 от **сырых байтов файла** на диске (`DocumentRef.path`), до разбора DOCX/PDF |

Кто считает: конкретный извлекатель (`DocxExtractor` / `PdfExtractor`) в начале `extract`, один раз при чтении файла. Базовый `Extractor` может дать общий метод хеширования потока; диспетчер хеш не пересчитывает. При `no_text_layer` и при пустом DOCX поле всё равно заполняется — отказ извлечения не отменяет знание «какой файл смотрели».

Это **не** `chunking_hash` и не прочие хеши конфигурации: те отвечают на вопрос «не устарели ли параметры пайплайна», а `source_sha256` — на вопрос «тот же ли исходник».

Куда уходит дальше (после утверждения — обязанность фазы A1 и meta, не самого `Cleaner`):

1. `CleanedDocument.source_sha256` — копия без пересчёта.
2. `index/<doc_id>/meta.json` (`ArtifactMeta`) — поле `source_sha256`.
3. События `Observed` / `TraceEvent` на стадии извлечения — то же значение в `counters` или рядом с `doc_id` (точное имя поля события — при реализации наблюдаемости; смысл: по логу прогона можно сопоставить артефакты с файлом).

`ArtifactGate` в итерации 1 по-прежнему смотрит на хеши конфигурации; сравнение `source_sha256` при skip/compute — отдельное усиление (раздел 8), но поле в meta пишется уже сейчас, чтобы цепочка происхождения не появилась «задним числом».

Пример результата `extract` (то, что реально лежит в объекте):

```json
{
  "doc_id": "reglament.docx",
  "source_sha256": "a3f1…c90e",
  "has_text_layer": true,
  "failure_reason": null,
  "blocks": [
    {
      "kind": "heading",
      "text": "3.2.1. Сроки",
      "page": null,
      "section_path": ["3.2.1. Сроки"],
      "heading_level": 3,
      "paragraph_index": null
    },
    {
      "kind": "paragraph",
      "text": "Срок хранения составляет 5 лет.",
      "page": null,
      "section_path": ["3.2.1. Сроки"],
      "heading_level": null,
      "paragraph_index": 1
    }
  ]
}
```

У PDF с тремя страницами те же `blocks`, у каждого своё `page` (1, 2 или 3). Вызов `page_texts()` тогда вернёт список длины 3 — это временный результат вызова, не третья копия внутри документа.

После утверждения поля `text` и `pages` убираются из `ExtractedDocument` / `CleanedDocument` (сейчас в коде они ещё есть как заглушка до блоков). `Cleaner` и `Chunker` читают только `blocks`.

### 3.1. Поля одного элемента списка (`ExtractedBlock`)

| Поле | Тип | Смысл |
|---|---|---|
| `kind` | `heading` \| `paragraph` \| `table` \| `header` \| `footer` | Роль блока |
| `text` | `str` | Текст этого блока. У таблицы — простой markdown (раздел 5) |
| `page` | `int \| None` | Номер страницы с 1, если известен |
| `section_path` | `list[str] \| None` | Путь заголовков от корня. `None` — заголовки не извлечены |
| `heading_level` | `int \| None` | Уровень заголовка с 1; только у `heading` |
| `paragraph_index` | `int \| None` | Номер абзаца с 1 среди `paragraph` и `table`; у заголовков и колонтитулов — `None` |

`None` у `section_path` значит «структура не извлечена»; пустой список недопустим. После утверждения тот же тип `list[str] | None` — у пути чанка.

### 3.2. Адрес для цитаты

Из полей блока генератор ответа потом собирает ссылку «где нашли». Приоритет:

1. Есть `page` и непустой `section_path` → страница и раздел.
2. Есть только `page` → страница.
3. Есть только `section_path` → раздел.
4. Иначе → «в N абзаце» по `paragraph_index`.

## 4. Общие правила извлечения

Действуют для всех наследников.

1. Порядок блоков — порядок чтения основного текста, не визуальных колонок.
2. Регистр и латиница не меняются.
3. Заголовок обновляет текущий `section_path`: путь обрезается до `heading_level − 1` элементов, затем добавляется текст заголовка.
4. Абзацы и таблицы наследуют текущий путь. До первого заголовка путь — `None`.
5. Блоки `paragraph` и `table` нумеруются подряд с 1 в поле `paragraph_index` после построения списка блоков (включая уже встроенные сноски).
6. Список не получает отдельный `kind`: пункт — обычный `paragraph`.
7. Рисунок без текста пропускается. Подпись обычным текстом — абзац.
8. Надписи внутри фигур и сложные текстовые рамки в этой итерации не разбираются (раздел 8).

### 4.1. Сноски

Текст сноски копируется в каждый абзац, где она упомянута.

Правило встраивания:

- в месте маркера сноски в текст абзаца добавляется фрагмент вида ` [сноска: …текст сноски…] `;
- если одна сноска ссылается из нескольких абзацев — полный текст копируется в каждый из них;
- отдельным блоком сноска в `blocks` не остаётся.

*Пример: абзац «Срок хранения¹ составляет 5 лет» и сноска «¹ С момента увольнения» → текст блока: `Срок хранения [сноска: С момента увольнения] составляет 5 лет`.*

Концевые сноски обрабатываются так же, если формат позволяет однозначно связать маркер с текстом. Если связь восстановить нельзя, маркер оставляется как есть, текст сноски не добавляется — без исключения.

## 5. Простая детализация форматов (итерация 1)

### 5.1. `DocxExtractor`

- Стили `Heading N` и `Заголовок N` (`N` = 1…9) → `kind=heading`, `heading_level=N`.
- Прочие абзацы основного текста → `paragraph`.
- Таблица → один блок `table`. Текст: строки сверху вниз, ячейки слева направо, строки разделены `\n`, ячейки в строке разделены ` | `. Объединённые ячейки и многостраничные таблицы не разбираются: берётся видимый текст ячеек в порядке обхода библиотеки.
- Колонтитулы пакета → `header` / `footer`, `section_path=None`, в основной поток не вставляются.
- Номер страницы: если в пакете есть явный разрыв страницы, блоки после разрыва получают следующий номер с 1. Иначе у всех блоков основного текста `page=None`; адрес цитаты идёт через раздел или `paragraph_index`.
- Пользовательские стили без `Heading N` / `Заголовок N` заголовками не считаются.

### 5.2. `PdfExtractor`

- Номер страницы — порядковый номер страницы файла с 1.
- Заголовок: строка, начало которой совпадает с `^\d+(\.\d+)*\.?\s+`.  
  *Пример: и `3.2.1 Сроки`, и `3.2.1. Сроки` — заголовки. Уровень = число числовых компонент.*
- В `section_path` кладётся вся строка заголовка целиком. Это первая физическая строка слоя, без дописывания переноса.
- Строка заголовка может быть перенесена на следующую. Продолжение — непустые строки сразу после неё, на той же странице, которые сами не заголовок, и при этом либо начинаются со строчной буквы, либо идут после строки, которая кончается на `-`. Пустая строка, следующий заголовок или строка с заглавной буквы (если предыдущая не оборвана `-`) продолжение обрывают.
- В `heading.text` остаётся только первая строка, как есть, включая хвостовой `-`, если он есть. Для идентификации раздела этого достаточно, вторую строку в заголовок не дописываем.
- Если продолжение было, сразу после заголовка идёт один `paragraph` с полной фразой: первая строка и все строки продолжения. Первая строка в абзаце не теряется. Если продолжения не было, отдельный абзац из заголовка не создаётся: следующий текст с заглавной буквы остаётся своим абзацем и заголовком не дополняется.
- Строки одного абзаца склеиваются одним пробелом. Исключение — перенос слова: строка кончается на `-`, следующая начинается со строчной буквы; дефис и пробел убираются, буквы сходятся (`информа-` + `ционного` → `информационного`). То же правило склейки действует для обычного абзаца, не только после заголовка.
  *Пример. Слой страницы 2, без пустой строки между строками: `1 ПОДГОТОВЛЕН Обществом «Институт развития информа-` и `ционного общества» (ООО «ИРИО») на основе перевода.` Заголовок уровня 1 — первая строка целиком, с `-` на конце. Абзац — `1 ПОДГОТОВЛЕН Обществом «Институт развития информационного общества» (ООО «ИРИО») на основе перевода.`*
  *Контрольный пример, который не склеивается: `3.2.1. Сроки` и следом `Срок хранения составляет 5 лет.` Заголовок — первая строка. Абзац — только `Срок хранения составляет 5 лет.`*
  *В текст раздела чанкер кладёт и заголовок, и абзац, поэтому первая строка встретится дважды: усечённая в заголовке и целая внутри абзаца. Так и задумано: путь раздела короткий, цитируемый абзац полный.*
  *Ограничение. Составной дефис, если строка оборвана сразу после него (`информационно-` / `коммуникационных`), тоже склеится без дефиса. Словарь переносов в этой итерации не подключаем. Перенос через границу страницы не склеивается: блоки собираются постранично.*
- Жирный шрифт и крупный кегль **без** нумерации в этой итерации заголовками не считаются.
- Если ни один заголовок не найден, у блоков основного текста `section_path is None`, `paragraph_index` всё равно заполняется.
- Обычные строки PDF как `header`/`footer` не помечаются; повторяющиеся колонтитулы снимает `Cleaner`.
- Таблица на уровне PDF в этой итерации не восстанавливается: текст строк страницы идёт как `paragraph` (или несколько абзацев по пустым строкам).

### 5.3. Пустой текстовый слой (итерация 1)

Решение принимает `PdfExtractor` после обхода **всех** страниц (раздел 2.2), не диспетчер.

| Ситуация | Поведение |
|---|---|
| Все страницы пусты после снятия пробелов | `has_text_layer=false`, `failure_reason="no_text_layer"`, `text=""`, `pages=[]`, `blocks=[]`, исключения нет. OCR не запускается |
| Часть страниц пуста, часть с текстом | Документ принимается: блоки и `pages` строятся по непустым страницам; пустые дают пустую строку в `pages`. Отдельного `failure_reason` нет |
| `pdf_text_layer_required=false`, все страницы пусты | Тот же `no_text_layer`: OCR в итерации 1 отсутствует, иного исхода нет |

Пустой DOCX — не `no_text_layer`: `has_text_layer=true`, `failure_reason=None`, `blocks=[]`.

Флаг `pdf_text_layer_required` в итерации 1 фактически означает «без OCR падать, если текста нет ни на одной странице». Когда появится OCR, при `false` пустые страницы уйдут в `PdfPageOcr`, при `true` смешанный/пустой документ по-прежнему можно отвергать политикой фазы — это уточняется вместе с внедрением OCR (раздел 8).

### 5.4. Ошибки

| Ситуация | Поведение |
|---|---|
| PDF без текстового слоя | Поля из раздела 5.3, исключения нет |
| Файл не читается или повреждён | Исключение; фаза помечает документ `failed` |
| Суффикс не `.docx` и не `.pdf` | `ValueError` в диспетчере |

### 5.5. Инварианты

- Блоки основного текста идут в порядке чтения.
- У `heading` заполнены `heading_level` и непустой `section_path`, последний элемент равен `text` заголовка.
- У `paragraph` и `table` путь равен пути предыдущего заголовка или `None`; `paragraph_index` ≥ 1 и уникален в документе.
- `header` и `footer` не стоят между блоками основного текста и не меняют путь.
- Латиница сохраняется.
- Класс не обращается к сети и не принимает тензоры.

## 6. Взаимодействие с соседями

```
DocumentRef
    → FormatAwareExtractor.extract
        → DocxExtractor | PdfExtractor
            → ExtractedDocument
                → Cleaner.clean
```

`Extractor` не вызывает `Cleaner`. При `no_text_layer` фаза `clean` не вызывает.

## 6.1. Отладочный дамп в Markdown

Для ручной проверки извлечения на больших документах нужен человекочитаемый снимок блоков. Формат — **один `.md` на документ**.

**Справится ли Markdown с 300+ страницами.** Да: это обычный текстовый файл. На регламенте ~300 стр. типичный объём порядка единиц мегабайт (зависит от плотности текста), а не сотен. Ограничение не у Markdown, а у удобства открытия в редакторе: подсветка синтаксиса на очень большом файле может тормозить, но `less`/поиск по файлу и diff между «до/после очистки» остаются рабочими. В `TraceEvent.debug_payload` такой объём **не** кладём — только путь к файлу или короткий summary.

**Когда пишется.** Флаг конфигурации `extraction.debug_dump` (по умолчанию `false`). При `true` после успешного `extract` (в том числе при пустых `blocks`, но не вместо исключения на повреждённом файле) создаётся файл:

`{runtime.cache_dir}/debug/{doc_id}.extract.md`

При `no_text_layer` файл всё же пишется: в шапке `failure_reason`, список блоков пуст — чтобы было видно, какой `source_sha256` отвергли.

**Кто пишет.** Отдельный класс `BlockDocumentDebugDump` (общий для extract и clean): умеет `render(...) -> str` и `write(...)`. Его вызывает `IndexingPhase` сразу после `extract` / `clean`, либо тот же объект передаётся в конструктор извлекателя как необязательная зависимость. Сами `DocxExtractor` / `PdfExtractor` формат Markdown не дублируют. Боевой путь артефактов (`chunks.parquet`) от дампа не зависит: дамп можно удалить, прогон остаётся валидным.

**Структура файла:**

```markdown
# extract: reglament.docx

- source_sha256: a3f1…c90e
- has_text_layer: true
- failure_reason: null
- blocks: 842

## Блоки

### [1] heading · lvl 1 · стр. 3 · абз. —
path: Регламент

Регламент обработки персональных данных

### [2] paragraph · стр. 3 · абз. 1
path: Регламент

Текст абзаца…

### [3] table · стр. 4 · абз. 2
path: Регламент / Сроки

| ячейка | … |
```

Правила разметки:

- шапка YAML-подобным списком (без обязательного front matter);
- каждый блок — секция `###` с порядковым номером в файле, `kind`, страницей (`—`, если `None`), номером абзаца (`—`, если `None`);
- строка `path:` — элементы `section_path` через ` / `, либо `path: —`;
- тело блока — его `text` как есть; у `heading` уровень также дублируется в заголовке секции (`lvl N`);
- экранирование Markdown в тексте блока не делается: дамп для глаз и поиска, не для повторного парсинга как источника истины.

## 8. Будущие доработки

Не входят в итерацию 1; контракт `extract` и роль `FormatAwareExtractor` не ломают.

### 8.1. OCR внутри `PdfExtractor`

1. Ввести сервис `PdfPageOcr.recognize(page_image) -> str` (не наследник `Extractor`).
2. В `PdfExtractor`: для каждой пустой страницы вызывать OCR, подставлять текст, затем строить блоки по объединённому результату.
3. Политика флага `pdf_text_layer_required` после появления OCR:
   - `true` — не вызывать OCR; пустой документ целиком → `no_text_layer`; смешанный — по отдельному правилу (отвергать или принимать только текстовые страницы);
   - `false` — пустые страницы распознавать через OCR.
4. Не вводить выбор «весь PDF → OCR» в `FormatAwareExtractor` и не выносить развилку в базовый `Extractor`.
5. Опционально: порог «страница почти пустая» (мало символов при большой площади изображения), чтобы ловить сканы с мусорным текстовым слоем из одного пробела или номера страницы.

### 8.2. Прочее

1. Определение заголовков PDF по жирности и кеглю.
2. Восстановление таблиц из PDF.
3. Объединённые ячейки и таблицы на несколько страниц в DOCX.
4. Пользовательские стили заголовков по outline-уровню.
5. Текст надписей в фигурах и текстовых рамках.
6. Более точная пагинация DOCX через layout/rendering.
7. Отдельная модель «абзац → список сносок», если встраивание в текст начнёт мешать очистке или эмбеддингам.
8. Учёт `source_sha256` в `ArtifactGate`: смена файла при том же `doc_id` и тех же хешах конфигурации → пересчёт A1, а не `skip`.
9. Опциональный второй отпечаток — хеш канонического текста после очистки (проверка «логическое содержимое»), отдельно от байтового `source_sha256`.
10. Нарезка отладочного Markdown по страницам (`…/{doc_id}.extract.page-012.md`), если единый файл станет неудобно листать в IDE; контракт блоков не меняется.
11. Опциональное HTML-превью с якорями по `paragraph_index` для кликабельной навигации.
