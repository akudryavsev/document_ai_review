# Спецификация: очистка текста — v1.1

Статус: **утверждена**. Можно писать тесты и код по этому документу.

Связанные документы: [0. spec.md](0.%20spec.md) (раздел 6.2), [1. top-level-classes.md](1.%20top-level-classes.md) (фаза A1), [2. extractor.md](2.%20extractor.md), [3. chunker.md](3.%20chunker.md).

Изменения относительно v1.0:

- пробелы: схлопывается любой Unicode-пробельный символ (`isspace`), а не только ` `, tab, `\n`, `\u00a0`;
- точки: четыре и более подряд идущих `.` схлопываются в `...` (лидеры оглавления и подобные «дорожки»).

## 1. Назначение и границы

**Назначение.** Привести успешно извлечённый документ к виду, пригодному для чанкинга: убрать колонтитулы и повторяющуюся нумерацию страниц, нормализовать пробелы и типовые знаки пунктуации, не трогая смысл и регистр.

**Делает:** удаление `header`/`footer` и эвристических колонтитулов PDF; схлопывание пробелов (включая нестандартные Unicode-пробелы); схлопывание длинных рядов точек; замена кавычек и тире по таблице ниже; удаление мягких переносов.

**Не делает:** извлечение из файла; чанкинг; смену регистра и вырезание латиницы; перестройку иерархии заголовков; вызов сети.

**Публичный метод:** `clean(document: ExtractedDocument) -> CleanedDocument`.

Конструктор реализации параметров формата не требует: правила очистки фиксированы этой спецификацией. При появлении флагов в конфигурации они добавляются отдельным утверждением.

Класс один: `Cleaner`. Наследование по форматам не нужно — на входе уже унифицированные блоки из `Extractor`.

## 2. Вход и выход

Вход — `ExtractedDocument` успешного извлечения (`failure_reason is None`, обычно `has_text_layer=true`). Выход — `CleanedDocument` с тем же `doc_id` и полем `blocks`.

Текст по-прежнему хранится один раз: очистка меняет или удаляет элементы списка `blocks`, отдельных полей-копий всего текста нет. Методы `joined_text()` / `page_texts()` при необходимости считают строку из оставшихся блоков (см. спецификацию извлечения).

`source_sha256` копируется с входа на выход без пересчёта: очистка не читает файл с диска. `Cleaner` не ставит `failure_reason`. Пустой вход даёт пустой `CleanedDocument` без исключения; ноль чанков потом фиксирует фаза.

## 3. Правила очистки

Порядок применения к документу:

1. Удалить все блоки `kind=header` и `kind=footer`.
2. Удалить эвристические колонтитулы и голые номера страниц (раздел 3.1).
3. Внутри каждого оставшегося блока нормализовать текст (раздел 3.2).
4. Удалить блоки, у которых после нормализации `text` пуст.

Порядок, `kind`, `page`, `section_path`, `heading_level` и `paragraph_index` у оставшихся блоков не меняются. Заголовок не удаляется только потому, что он короткий. Отдельные поля всего документа с копией текста не создаются и не обновляются.

### 3.1. Колонтитулы без `header`/`footer`

Типичный случай — PDF, где колонтитул пришёл обычной строкой.

Удаляется блок `paragraph`, если выполняется хотя бы одно условие:

- его `text` после обрезки краёв целиком совпадает с десятичной записью номера своей страницы (`page`), например `"12"` на странице 12;
- длина текста ≤ 80 символов, и тот же текст (посимвольно) встречается как первый или последний блок основной текста на ≥ 3 различных страницах документа — тогда все такие совпадающие блоки удаляются.

*Пример: на страницах 1…10 первая строка — «Регламент 2024». Это не `header` из пакета, но повторяется на ≥3 страницах → все десять копий снимаются. Короткий содержательный абзац «Срок: 5 лет», встретившийся один раз, остаётся.*

Блоки `heading` и `table` этой эвристикой не трогаются.

### 3.2. Нормализация текста внутри блока

Порядок внутри блока:

1. Удалить мягкие переносы.
2. Заменить кавычки и тире по таблице.
3. Схлопнуть пробелы и обрезать края блока.
4. Схлопнуть длинные ряды точек.

Пустой текст после этих шагов → блок удаляется на шаге 4 документа (см. §3).

| Правило | Действие |
|---|---|
| Пробелы | Любая последовательность символов, для которых `str.isspace()` истинно (обычный пробел, tab, `\n`, `\r`, `\f`, `\v`, `\u00a0`, en/em space `U+2002`/`U+2003`, узкий `U+202F`, ideographic `U+3000` и прочие категории Zs) → один обычный пробел ` `; края блока обрезаются. У таблицы то же схлопывание внутри ячейки; разделители строк таблицы и ` \| ` между ячейками сохраняются |
| Точки | Последовательность из **четырёх и более** символов `.` → ровно `...`. Три точки и меньше не трогаются. Символ многоточия `…` (U+2026) в этой итерации не заменяется и не участвует в схлопывании |
| Мягкий перенос | `\u00ad` удаляется |
| Кавычки | `«»“”„` → `"`; `‘’` → `'` |
| Дефисы и тире | U+2010, U+2011, U+2013, U+2014 → `-` |
| Регистр | Не меняется |
| Латиница | Не удаляется |

Иных замен в этой итерации нет.

*Пример пробелов: `"слово -  слово"` (дефис между обычным пробелом и en space U+2002) → `"слово - слово"`.*

*Пример точек (оглавление): `Содержание..........5` → `Содержание...5`.*

Встроенный текст сносок вида ` [сноска: …] ` очищается теми же правилами (пробелы, кавычки, точки), но сам маркер сноски не вырезается.

## 4. Инварианты

- Множество оставшихся непустых блоков основного текста — подмножество входа (минус колонтитулы и опустевшие), в том же относительном порядке.
- Документ без колонтитулов и без символов из таблицы замен, уже с нормальными пробелами, после очистки совпадает с входом по блокам основного текста.
- `paragraph_index` у выживших блоков не перенумеровывается: номер абзаца — стабильный адрес из извлечения.
- Очистка не вызывает `Extractor`, `Chunker` и сеть.

*Пример: если извлекатель присвоил абзацу номер 20, а абзацы 3 и 7 оказались колонтитулями и сняты, в ответе по-прежнему «в 20 абзаце», а не «в 18». Перенумерация сломала бы ссылку на исходный документ.*

## 5. Ошибки

| Ситуация | Поведение |
|---|---|
| Пустой `blocks` | Пустой `CleanedDocument`, исключения нет |
| Повреждённые поля модели | Ошибка валидации pydantic на входе; `Cleaner` сам её не чинит |

Сбой очистки — исключение в `IndexingPhase`; документ `failed`, следующие продолжаются.

## 6. Взаимодействие с соседями

```
ExtractedDocument
    → Cleaner.clean → CleanedDocument
        → Chunker.chunk
```

При `no_text_layer` фаза `clean` не вызывает. `Chunker` читает уже очищенные блоки; блоки `header`/`footer` до него не доходят. Если они всё же попали во вход чанкера, чанкер их пропускает (страховка в спецификации чанкинга).

## 6.1. Отладочный дамп в Markdown

Тот же режим и тот же класс `BlockDocumentDebugDump`, что в спецификации извлечения (§6.1). Флаг `extraction.debug_dump` (по умолчанию `false`).

При `true` после `clean` пишется:

`{runtime.cache_dir}/debug/{doc_id}.clean.md`

Формат файла тот же (шапка + секции блоков), заголовок документа: `# clean: {doc_id}`. В шапке обязательны `source_sha256` и число блоков после очистки.

*Зачем два файла в одном каталоге: `diff debug/{doc_id}.extract.md debug/{doc_id}.clean.md` сразу показывает снятые колонтитулы и нормализацию на реальном регламенте, без отладчика. Стадия в суффиксе имени — без лишних подпапок.*

Дамп не влияет на чанкинг и не заменяет `blocks` в памяти. При выключенном флаге `Cleaner` файлов не создаёт.

Markdown на полный документ после очистки так же допустим по объёму, как после извлечения: это текстовый снимок, не первичный артефакт индекса.

## 8. Будущие доработки

1. Флаги включения/выключения отдельных правил очистки в конфигурации.
2. Расширение таблицы замен (символ многоточия `…`, неразрывные конструкции, единицы измерения).
3. Более аккуратная детекция колонтитулов PDF по геометрии страницы (координаты top/bottom), а не только по повтору текста.
4. Опциональное удаление или вынесение встроенных сносок в отдельное поле, если они начнут мешать эмбеддингам.
5. Нормализация списков и нумерации пунктов без потери маркеров смысла.
6. Бок о бок в одном Markdown «до / после» по блокам (сейчас достаточно двух файлов и внешнего diff).
7. Схлопывание «точек с пробелами» вида `. . . .` в оглавлениях, если такие лидеры встретятся на практике.
