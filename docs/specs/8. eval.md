# Спецификация: оценка качества — v1.0

Статус: **проект, ждёт утверждения**. Тесты и код по этому документу не писать, пока пользователь его не утвердил.

Связанные документы: [0. spec.md](0.%20spec.md) (§2.2 и раздел 10), [1. top-level-classes.md](1.%20top-level-classes.md) (`EvaluationRun`, `EvalRequest`, `EvalReport`), [3a. artifact-store.md](3a.%20artifact-store.md) (пути кандидатов и контекстов), [4. hybrid-retriever.md](4.%20hybrid-retriever.md) (ранг до реранка, косинус), [7. llama-gateways.md](7.%20llama-gateways.md) (эмбеддер и bytes float16), [10. model-lists.md](10.%20model-lists.md) (тройка имён и префиксы каталогов).

Раздел 10 спеки поведения называет метрики. Здесь — формулы, входы и поля отчёта. `confidence` не участвует: формулы уверенности нет, поле в предсказании не читается.

## 1. Назначение и границы

**Назначение.** `EvaluationRun` по ground truth и уже записанным предсказаниям считает `EvalReport`. Команда — `python main.py eval`.

**Делает:**

- Читает `gt.json`, строки `results`-подобных jsonl, кандидатов до реранка и бандлы контекста.
- Считает метрики раздела 5.
- Для косинуса всех групп один раз арендует первый файл из `embedding.models`.

**Не делает:**

- Не запускает фазы A1, A2, B и не переписывает их артефакты.
- Не пишет `embed_cache` и не вызывает `save_chunk_vectors`.
- Не ходит в сеть, кроме шлюза эмбеддера, который уже описан спекой 7. Unit-тесты подставляют подделку шлюза.
- Не проектирует отдельную модель «для похожести».
- Не считает метрики по `expected_sections`. Поле загружается и в формулах не используется.
- Не подставляет латентность фаз: в `AnswerRecord` её нет.

Факт кода: `DocumentAnalysisService.evaluate` бросает `NotImplementedError`, `CliApp._eval` печатает текст и выходит с кодом 1, `InlineJobExecutor` для `kind=eval` тоже бросает `NotImplementedError`. После реализации этого документа `evaluate` возвращает список `EvalReport`, по отчёту на тройку моделей, а `wait` для eval — тот же список.

## 2. Входы

### 2.1. Ground truth

Файл — JSON-массив, как в спеке поведения §2.2. Элемент — `GroundTruthItem`:

| Поле | Смысл |
|---|---|
| `doc_id` | Имя документа, как в предсказании |
| `question_id` | Идентификатор вопроса |
| `expected_found` | Эталон класса `found` |
| `expected_answer` | Эталонный текст ответа. Пустая строка допустима |
| `expected_pages` | Страницы, которые считаются верными |
| `expected_sections` | Загружается, в метриках не участвует |

`GroundTruthSource.load` возвращает этот список. `FileGroundTruthSource` читает путь из `EvalRequest.ground_truth_path`.

Проверки `EvaluationRun` до метрик, при нарушении — ошибка и ненулевой код, отчёта нет:

- корень файла — массив;
- пара `(doc_id, question_id)` встречается один раз;
- пустой массив ошибкой не является: отчёт с нулевыми знаменателями и пустыми средними (`null`, не ноль).

Строка, у которой `expected_found = true` и `expected_pages` пуст, в покрытие входит как несогласованная. Страничные метрики её пропускают. Класс `found` по концу прогона её учитывает. Список таких пар попадает в `coverage`.

### 2.2. Предсказания

`EvalRequest.predictions_dir`. Читаются только файлы `*.jsonl` в этом каталоге, без вложенных папок. Строка — `AnswerRecord`. Пустая строка пропускается. Неразобранная строка или запись, которая не проходит проверку модели, — ошибка всего eval до метрик.

Строки делятся на группы по тройке `embedding_model`, `reranker_model`, `answer_model`. Строка без любого из этих полей — ошибка до метрик. Внутри группы пара `(doc_id, question_id)` уникальна. Та же пара в другой группе — отдельное предсказание. Повтор пары внутри группы — ошибка до метрик.

`run_summary.json` в том же каталоге предсказанием не является. Если файл есть и разбирается как `RunSummary`, блок стоимости группы берёт счётчики фаз из элемента `combinations` с той же тройкой. Нет файла, нет элемента или сводка без этой тройки — поле фаз в отчёте группы `null`. Битый `run_summary.json` — ошибка eval.

Файлы `*.md` не читаются.

### 2.3. Откуда страницы кандидатов

Метрики поиска (Recall, MRR, nDCG) читают **кандидатов до реранка**, не бандл контекста.

Путь кандидатов группы: `{index_dir}/{embedding_model}/{reranker_model}/{doc_id}/candidates.jsonl`. Строка — `CandidateRecord`. В расчёт пары входят строки с этим `question_id`. Порядок — по полю `rank` по возрастанию. Ранг плотный с 1, как у выхода `search`. Страница кандидата — множество положительных целых из `pages`. Ноль и отрицательные числа страницей не являются.

Бандл `{contexts_dir}/{embedding_model}/{reranker_model}/{doc_id}/{question_id}.json` используется **только** для решения `empty_search`. Страницы `ContextCandidate` в Recall, MRR, nDCG и в классификацию A2 не входят: после сборки это уже секции, а не список top-k.

Корни `index_dir` и `contexts_dir` берутся из конфига запроса. Имена файлов в префиксе берутся из тройки строки, не из `predictions_dir`. Префикс совпадает с раскладкой прогона ([10. model-lists.md](10.%20model-lists.md) §6).

`persist_candidates = false` оставляет файл отсутствующим. Пара тогда не входит в знаменатель поисковых метрик.

## 3. Классы

| Класс | Роль |
|---|---|
| `GroundTruthSource` | Загрузка списка эталонов. Уже есть как порт |
| `EvaluationRun` | Сверка, метрики, аренда эмбеддера для косинуса |
| `EvalReport` | Поля раздела 6 |

Конструктор `EvaluationRun` получает `GroundTruthSource` (или уже прочитанный путь и источник), каталоги из `EvalRequest`, `EmbeddingGateway`, `GpuLease`. Сам HTTP не создаёт: шлюз приходит снаружи, в тесте — подделка.

`DocumentAnalysisService.evaluate` создаёт `EvaluationRun` и возвращает список отчётов, по одному на тройку. Порядок — первое появление тройки в jsonl. `CliApp._eval` печатает по короткой строке на отчёт и при успехе выходит с кодом 0. Состав строки: три имени файлов, число сопоставленных пар и `found_e2e.f1`, если он есть. Полный список отчётов команда пишет JSON-массивом в stdout. Одна тройка — массив из одного элемента. Файл рядом с предсказаниями eval не создаёт.

## 4. Сопоставление

Ключ пары внутри группы — `(doc_id, question_id)`. Эталон один на все группы: в `gt.json` имён моделей нет.

Метрики считаются на пересечении эталона и предсказания. Эталон без предсказания и предсказание без эталона в знаменатели не входят. Их количества видны в `coverage`. Пропуск предсказания не подменяется на `found = false`.

Дальше «пара» значит сопоставленная пара, если не сказано иное.

Несогласованный эталон (`expected_found` и пустые страницы) остаётся в `found_e2e` и в стоимости, если есть предсказание. Из Recall, MRR, nDCG, `empty_search`, цитат и `found_a2` он исключён.

## 5. Формулы

Средние — арифметическое среднее по парам, которые вошли в знаменатель этой метрики. Знаменатель 0 — поле `null`, не 0. Деление — обычное вещественное. Сравнение в тестах: допуск `1e-6` для nDCG и косинуса, точное совпадение для дробей из нулей и единиц в таблицах, где значение — конечная двоичная дробь (`0.5`, `1`, `0`).

Множества страниц не содержат дубликатов.

### 5.1. Recall@5, Recall@10, Recall@20

В знаменатель входят пары, у которых `expected_pages` непуст и файл кандидатов этой пары разобран (ранги уникальны, начинаются с 1 и идут без дыр). Иначе пара в `coverage.n_bad_candidates` и в Recall не входит.

Для порога `k` берутся кандидаты с `rank <= k`.

`Recall@k` пары = `|страницы этих кандидатов ∩ expected_pages| / |expected_pages|`.

В отчёте — среднее по парам знаменателя. Поля: `recall_at_5`, `recall_at_10`, `recall_at_20`.

### 5.2. MRR

Тот же знаменатель, что у Recall.

Релевантный кандидат — тот, чьи страницы пересекают `expected_pages`. `rr` пары = `1 / rank` первого релевантного кандидата в порядке ранга. Если релевантных нет, `rr = 0`.

`mrr` — среднее `rr`.

### 5.3. nDCG@10

Тот же знаменатель.

Позиция `i` — ранг кандидата, с 1. `rel_i = 1`, если кандидат релевантен, иначе 0. Релевантность двоичная, повтор страницы у второго кандидата снова даёт 1: единица стоит на кандидате, не на новой странице.

`DCG@10 = Σ rel_i / log2(i + 1)` по кандидатам с рангом от 1 до `min(10, n)`. `n` — число кандидатов пары.

`R` — число релевантных кандидатов во всём сохранённом списке пары, не только в первой десятке.

`IDCG@10 = Σ_{i=1..min(10, R)} 1 / log2(i + 1)`. Если `R = 0`, nDCG пары равен 0.

`nDCG@10` пары = `DCG@10 / IDCG@10`. В отчёте — среднее. Логарифм — по основанию 2.

Ограничение, которое формула не скрывает: список — это сохранённый пул до реранка, а не все чанки документа. Кандидат вне файла в `R` не входит. Полноту страниц показывает Recall, порядок внутри пула — nDCG.

### 5.4. Точность решения empty_search

В знаменатель входят пары с разобранным бандлом и с согласованным эталоном.

`expected_empty = (expected_pages пуст)`.

`predicted_empty = ContextBundle.empty_search`.

Пара верна, если значения равны. `accuracy = число верных / число пар знаменателя`.

Нет файла бандла — пара в `coverage.n_missing_context` и в accuracy не входит. Подставлять `empty_search = false` нельзя.

### 5.5. Класс found, конец прогона и отдельно A2

Положительный класс — `found = true` на эталоне (`expected_found`).

Для каждой матрицы:

- `precision = tp / (tp + fp)`, если `tp + fp > 0`, иначе `null`;
- `recall = tp / (tp + fn)`, если `tp + fn > 0`, иначе `null`;
- `f1 = 2 * precision * recall / (precision + recall)`, если оба сомножителя не `null` и сумма больше 0, иначе `null`.

**Конец прогона** (`found_e2e`). Предсказание — поле `AnswerRecord.found`. В знаменатель входят все сопоставленные пары, включая `status = failed` и несогласованный эталон. `status` сам по себе метку не подменяет.

**A2** (`found_a2`). Предсказание истинно, если среди кандидатов пары есть хотя бы один релевантный. Пустые `expected_pages` дают предсказание «ложь» (пересечь не с чем) и остаются в матрице, когда эталон согласован: `expected_found = false` и пустые страницы — истинно отрицательная, если файл кандидатов есть. Несогласованные сюда не входят. Нет файла или битый ранг — пара не входит, это `n_missing_candidates` или `n_bad_candidates`.

Так A2 отвечает на вопрос «попала ли размеченная страница в пул до генерации», а конец прогона — «какой `found` записан в ответе».

### 5.6. Exact match и косинус

Обе метрики смотрят пары, где `expected_found = true`, предсказание сопоставлено, `status = ok`, `found = true`.

**Exact match.** Дополнительно оба текста после обрезки краёв непусты. Иначе пара в этот знаменатель не входит (`n` отчёта её не считает).

Нормализация каждого текста: `casefold`, обрезка краёв, любая непрерывная цепочка пробельных символов схлопывается в один пробел. Знаки препинания остаются.

Пара совпала, если нормализованные строки равны. `exact_match` — доля таких пар.

**Косинус.** Те же пары, но пустой `expected_answer` или пустой `answer` после обрезки краёв исключается отдельно (в exact он и так не входит). Текст для эмбеддера — исходные поля `answer` и `expected_answer`, без нормализации exact match.

Косинус — определение спеки поиска: скалярное произведение, делённое на произведение длин. Нулевая длина или разная размерность двух векторов пары: пара исключается, счётчик `n_cosine_excluded` растёт, остальные пары считаются.

`cosine_mean` — среднее по парам, где косинус посчитан.

Вызов шлюза — раздел 7. В отчёте нет векторов, только среднее и счётчики.

### 5.7. Цитаты

Страницы одной цитаты — все целые от меньшего из `page_from` и `page_to` до большего включительно, если хотя бы один конец больше 0. Оба конца равны 0 — цитата не добавляет страниц. Предсказанные страницы пары — объединение по всем цитатам.

В знаменатель precision/recall входят сопоставленные пары с непустым `expected_pages` и согласованным эталоном.

`precision` пары = `|пересечение| / |предсказанные страницы|`, если предсказанные страницы есть, иначе 0.

`recall` пары = `|пересечение| / |expected_pages|`.

В отчёте — средние этих величин.

**Доля ответов с хотя бы одной верной цитатой.** Знаменатель: `expected_found = true`, непустые `expected_pages`, `status = ok`. Числитель: пересечение страниц непустое. Поле `answers_with_correct_citation`. Знаменатель 0 — `null`.

### 5.8. Токены и latency

По всем сопоставленным `AnswerRecord`, включая `found = false` и `status = failed`:

- `mean_prompt_tokens` — среднее `tokens.prompt`;
- `mean_completion_tokens` — среднее `tokens.completion`;
- `mean_latency_ms` — среднее `latency_ms`.

`phases` — копия счётчиков `computed` / `skipped` / `failed` элемента `combinations` из `run_summary.json` с той же тройкой, если сводка прочитана и элемент найден. Иначе `null`. Отдельной латентности фазы в отчёте нет. Верхние счётчики сводки, сложенные по всем комбинациям, в отчёт группы не копируются.

## 6. Поля EvalReport

Отчёт сериализуется в JSON без байтов и без тензоров.

| Поле | Содержание |
|---|---|
| `embedding_model`, `reranker_model`, `answer_model` | Тройка этой группы |
| `cosine_embedding_model` | Первый файл `embedding.models`, общий для всех отчётов запуска |
| `ground_truth_path`, `predictions_dir`, `contexts_dir`, `index_dir` | Пути этого запуска. `contexts_dir` и `index_dir` — корни; префикс тройки задают три имени выше |
| `coverage` | `n_ground_truth`, `n_predictions`, `n_matched`, `n_unmatched_ground_truth`, `n_unmatched_predictions`, `n_inconsistent_ground_truth`, `n_missing_context`, `n_missing_candidates`, `n_bad_candidates`, `n_bad_prediction` (последнее резервируется 0: битая строка валит eval раньше отчёта) |
| `retrieval` | `n`, `recall_at_5`, `recall_at_10`, `recall_at_20`, `mrr`, `ndcg_at_10` |
| `empty_search` | `n`, `correct`, `accuracy` |
| `found_e2e`, `found_a2` | `n`, `tp`, `fp`, `fn`, `tn`, `precision`, `recall`, `f1` |
| `answers` | `n_exact`, `exact_match`, `n_cosine`, `cosine_mean`, `n_cosine_excluded` |
| `citations` | `n`, `precision`, `recall`, `n_citation_rate`, `answers_with_correct_citation` |
| `cost` | `n`, `mean_prompt_tokens`, `mean_completion_tokens`, `mean_latency_ms`, `phases` |
| `notes` | Короткие пояснения пропусков: нет бандла, нет кандидатов, несогласованный эталон. Не тексты документов |

`n` блока — размер знаменателя этого блока.

## 7. Косинус и GpuLease

Шаг выполняется после того, как посчитано всё, чему шлюз не нужен.

Если пар для косинуса нет, эмбеддер не арендуется.

Если пары есть:

1. `GpuLease.acquire` на `EmbeddingGateway` с пресетом — первым именем `embedding.models`. Аренда одна на все группы и сама снимает другой пресет, если он ещё удерживался. Имя пишется в `cosine_embedding_model` каждого отчёта.
2. Тексты уходят в `infer` батчами `embedding.batch_size`. Ответ — байты float16 и `dim` спеки 7. Прогон eval эти байты на диск не пишет.
3. Косинус считается по декодированным числам.
4. `release` вызывается и при успехе, и при исключении шага.

Сбой шлюза (сервер недоступен, пустой вектор, разная размерность внутри одного ответа) прерывает eval: отчёта нет, код выхода ненулевой. Это не исключение одной пары. Исключение одной пары — только нулевая длина уже разобранного вектора или разная размерность именно двух векторов этой пары.

В unit-тесте шлюз — подделка, которая по тексту возвращает заранее заданные байты. Боевой сервер в каталог тестов не входит. Тест с вызовом шлюза помечен отдельно.

## 8. Крайние случаи

- Пустой `gt.json` — пустой отчёт, код 0, средние `null`.
- Эталон есть, jsonl нет — `n_matched = 0`, метрики `null`, `n_unmatched_ground_truth` равен числу эталонов.
- Два эталона с одним ключом — ошибка до метрик.
- `rank` с дырой или с нулём — пара выпадает из поиска и из `found_a2`.
- Кандидат без страниц не бывает релевантным.
- `page_from = 12`, `page_to = 13` даёт страницы 12 и 13. `page_from = 13`, `page_to = 12` — те же.
- `expected_found = false` и непустые страницы: поиск и цитаты считаются, exact match не считается.
- `found = true` при пустых цитатах до отчёта не доходит: такая строка не проходит модель `AnswerRecord` и валит eval.
- Повторный eval на тех же файлах даёт те же числа. Косинус детерминирован при тех же байтах шлюза.

## 9. Каталог тестов

Числа заданы здесь. Сеть не используется. Строка про косинус вызывает поддельный шлюз и проверяет, что `acquire` был на эмбеддере и после шага был `release`.

| ID | Случай | Ожидание |
|---|---|---|
| T-EV-01 | Одна пара, эталонные страницы `{1,2,3}`, ранги 1..3 со страницами `{9}`, `{1}`, `{2}` | `recall_at_5 = 2/3`, `recall_at_10 = 2/3`, `recall_at_20 = 2/3`, `mrr = 0.5` |
| T-EV-02 | Два эталона с одним ключом | Ошибка до отчёта |

| T-EV-04 | Те же кандидаты, что в T-EV-01, релевантны ранги 2 и 3 | `ndcg_at_10` равен `(1/log2(3) + 1/log2(4)) / (1/log2(2) + 1/log2(3))` с допуском `1e-6` |
| T-EV-05 | Три бандла, два с верным `empty_search` относительно пустоты страниц | `accuracy = 2/3` |

## 10. Допущения

- Имя файла предсказания не обязано совпадать с `doc_id`: идентификатор берётся из строки JSONL. Расхождение имени и поля ошибкой не считается.
- Один документ — один jsonl, но несколько jsonl с разными парами допустимы.
- Ранг в файле кандидатов уже плотный с 1 на каждый `question_id`. Eval порядок по `fused_score` не восстанавливает.
- Поддельный шлюз в T-EV-09 возвращает float16 байты так же, как боевой контракт спеки 7. Проверка перевода числа в байты живёт в каталоге спеки 7, здесь проверяется среднее косинуса.

## 11. Вне этой спецификации

- Формула `confidence` не задаётся и на метрики не влияет.
- `expected_sections` не сравниваются с `section_path`.
- Латентность по фазам из артефактов не восстанавливается.
- Порог «не ниже baseline» из раздела 11 спеки поведения числом здесь не фиксируется: отчёт отдаёт метрики, порог в код выхода не зашит.
