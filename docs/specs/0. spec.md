# Спецификация: Document Q&A Service — v1.1

Изменения относительно v1.0: модели считает отдельный контейнер llama.cpp (`llama-server`), на GPU одна GGUF. Смена модели между фазами — смена пресета этого контейнера. Имена в конфигурации — секции `embed`, `rerank`, `answer`. Формулы метрик — в [8. eval.md](8.%20eval.md), шлюзы — в [7. llama-gateways.md](7.%20llama-gateways.md), очередь — в [9. job-api.md](9.%20job-api.md).



## 1. Назначение и границы

**Делает:** CLI-сервис для локального анализа больших документов (DOCX и текстовые PDF, до ~300+ страниц) по списку вопросов-категорий с ручными синонимами. Для каждой пары «документ × вопрос» выдаёт структурированный JSON-ответ с цитатами (страница, раздел) и признаком `found` / `not_found`. Всё выполняется в локальном периметре, без внешних API. Веса моделей считает соседний контейнер llama-server; процесс приложения ходит к нему по HTTP.

**Не делает (ограничения v1):**
- **Нет OCR.** PDF должны иметь текстовый слой. При его отсутствии документ помечается `status=failed, reason=no_text_layer`.
- **Нет UI.** Точка входа PoC — CLI. Контракт API и воркера описан в [9. job-api.md](9.%20job-api.md) и в первый запуск не входит.
- **Нет инкрементальной обработки документов.** Каждый запуск читает всю папку.
- **Документы обрабатываются последовательно** (без параллелизма между документами).

**Целевой режим эксплуатации:** ночной пакетный прогон на сервере с 2×NVIDIA T10 (по 16 ГБ).

## 2. Входные данные

### 2.1. Файл вопросов — JSON

```json
{
  "version": "1.0",
  "questions": [
    {
      "id": "Q001",
      "category": "Срок хранения персональных данных",
      "synonyms": [
        "период хранения ПДн",
        "сколько хранятся персональные данные",
        "retention period for personal data"
      ],
      "expected_answerable": true
    }
  ]
}
```

- `category` — каноническая формулировка: ключ результата и **единственный текст вопроса для LLM** (верификация и ответ).
- `synonyms` — **задаются вручную** (автогенерация не требуется). Расширяют только поиск (эмбеддинги + BM25 + реранк). В промпт LLM не передаются. Могут содержать англицизмы.
- Схема валидируется (pydantic); дубликаты `id` или `category` — ошибка загрузки.

### 2.2. Ground truth — JSON

```json
[
  {
    "doc_id": "reglament_2024.docx",
    "question_id": "Q001",
    "expected_found": true,
    "expected_answer": "5 лет с момента ...",
    "expected_pages": [12, 13],
    "expected_sections": ["3.2.1. Сроки"]
  }
]
```

Используется командой `python main.py eval`.

### 2.3. Папка документов

- Расширения: `.docx`, `.pdf`. Обход рекурсивный.
- PDF считаются **текстовыми** (наличие слоя текста обязательно).

## 3. Архитектура: три фазы с явным освобождением VRAM

Ключевое проектное решение: разделение на три фазы, чтобы в каждой на GPU находилась только одна модель и была доступна максимально освобождённая память.

```
═══════════ ФАЗА A1: Индексация (GPU: пресет embed в llama-server) ═══════════

QuestionsLoader (category + synonyms)
   │
   │  ← эмбеддинги вопросов вычисляются ЗДЕСЬ и кэшируются на диск
   ▼
для каждого документа (последовательно):
   Extract → Clean → Chunk(+page, section_path)
     → Embed(chunks) → сохранить чанки и vectors.f16
     → BM25 в этой фазе не строится (поиск строит его в A2 в памяти)

после всех документов:
   снять пресет embed (GpuLease → POST /models/unload)


═══════════ ФАЗА A2: Retrieval + Rerank (GPU: пресет rerank) ═══════════

загрузить пресет rerank (на GPU по-прежнему одна модель)
для каждого документа (последовательно):
   для каждого вопроса:
      query_vec = из кэша A1 (max по синонимам)
      top_k = hybrid_search(query_vec, BM25)
      сохранить кандидатов до реранка
      top_n = rerank(top_k)
      если после порога пусто:
          contexts/<doc>/<q>.json = {empty_search: true, reason: "no_relevant_chunks"}
          continue
      bundle = section_expand(top_n, token_budget)
      # empty_search: false; синонимы уже отработали только на поиске
      сохранить contexts/<doc>/<q>.json

после всех документов:
   снять пресет rerank


═══════════ ФАЗА B: LLM-ответы (GPU: пресет answer) ═══════════

загрузить пресет answer
для каждого документа (последовательно):
   для каждого вопроса:
      # вопрос = category; синонимы только в метаданных бандла
      # первый запуск: верификатор «да/нет/частично» не вызывается
      если bundle.empty_search == true:
         # модель не спрашивают: система пишет found=false и фразу
         # «В поиске по этому вопросу ничего не найдено.»
         answer = system_answer(no_relevant_chunks, category, search_meta)
      иначе:
         prompt = assemble(bundle.candidates, category, search_meta)
         answer = llm_answer(prompt, category)
      сохранить результат
   KV-кэш принадлежит процессу llama-server и снимается вместе с пресетом
```

**Обоснование:**
- Фаза A1 — только пресет `embed` (`/models/embed.gguf`). Процесс приложения веса не держит.
- Фаза A2 — только пресет `rerank`. Эмбеддер не нужен: векторы запросов уже лежат в кэше A1.
- Фаза B — только пресет `answer`. Контейнер запущен с `--models-max 1`, поэтому предыдущий пресет к этому моменту снят.
- A1+A2 проходят для всех документов **до** старта B — одна загрузка пресета ответа на весь прогон.
- HTTP-контракт и запись байтов float16 — [7. llama-gateways.md](7.%20llama-gateways.md). Раскладка файлов — [3a. artifact-store.md](3a.%20artifact-store.md).

## 4. VRAM-карта по фазам

На GPU контейнера `inference` в каждый момент не больше одной модели (`--models-max 1`). Объём зависит от квантизации GGUF и от `ctx-size = 4096` в `deploy/llama/models.ini`. Процесс приложения видеопамять не занимает. Две карты хоста использует сам llama-server.

| Фаза | Пресет | Файл | Что на GPU после фазы |
|---|---|---|---|
| **A1** | `embed` | `/models/embed.gguf` | Пусто: пресет снят |
| **A2** | `rerank` | `/models/rerank.gguf` | Пусто: пресет снят |
| **B** | `answer` | `/models/answer.gguf` | Пусто: пресет снят |
| **eval, шаг косинуса** | `embed` | тот же файл, что в A1 | Пусто после отчёта |

Фаза B получает ту единственную модель, которая в этот момент загружена. Скоры реранка уже лежат в бандлах, пресет `rerank` для ответа не нужен.

## 5. Конфигурация (YAML)

```yaml
input:
  documents_dir: "./docs"
  questions_file: "./questions.json"

inference:
  base_url: "http://inference:8080"   # контейнер llama-server
  request_timeout_sec: 120
  poll_interval_sec: 0.5

extraction:
  pdf_text_layer_required: true          # иначе doc=failed

chunking:
  max_tokens: 512
  overlap_tokens: 64
  min_chunk_tokens: 80
  preserve_section_path: true

embedding:
  model: "embed"                         # секция [embed] в models.ini
  batch_size: 8
  dtype: "fp16"                          # байты на диске — float16
  cache_dir: "./.cache/emb"
  questions_cache: "./.cache/questions.parquet"
  persist_chunk_index: true              # эмбеддинги чанков на диск
  persist_bm25: false                    # BM25 пересчитывается за секунды

retrieval:
  top_k: 20
  score_threshold: 0.30
  query_strategy: "max_over_variants"    # max по category+synonyms
  hybrid:
    enabled: true
    bm25_weight: 0.3
    vector_weight: 0.7
  persist_candidates: true               # top_k до реранка на диск

reranker:
  enabled: true
  model: "rerank"                        # секция [rerank] в models.ini
  top_n: 5
  score_threshold: 0.4

verification:
  enabled: true
  model: "answer"                        # в первый запуск шаг не исполняется
  batch_size: 8

context:
  expansion: "section"                   # section | neighbors | none
  neighbors_fallback: 2                  # если section_path не извлечён
  max_total_tokens: 6000                 # бюджет финального промпта (защита от OOM)
  max_section_tokens: 3000               # обрезка длинных секций
  early_exit_threshold: 0.4              # max rerank < порога → empty_search=true
  compression: none                      # none | gzip

answer:
  model: "answer"                        # секция [answer] в models.ini
  temperature: 0
  require_citations: true
  # длину ответа не ограничиваем; max_output_tokens генератор не передаёт

phases:
  run_a1: true
  run_a2: true
  run_b: true
  contexts_dir: "./contexts"
  index_dir: "./index"
  skip_if_artifacts_valid: true          # хеш-валидация, пропуск пересчёта

runtime:
  retries: 2                             # всего вызовов LLM, включая первый
  retry_pause_sec: 0                     # пауза между попытками, секунды
  question_parallelism: 1                # стабильность на 16 ГБ T10
  results_dir: "./results"
  log_level: "INFO"
```

### 5.1. Выбор модели

Имя в конфиге — секция `deploy/llama/models.ini`. Файл GGUF лежит по пути этой секции и в репозиторий не входит. Какую квантизацию положить на диск, решает оператор так, чтобы одна модель помещалась на GPU контейнера. Окно контекста пресетов — 4096 (`[*]` в ini). Этого окна хватает на чанк 512 с перекрытием.

| Роль | Пресет | Файл | Когда на GPU |
|---|---|---|---|
| Эмбеддинги чанков и вопросов, косинус eval | `embed` | `/models/embed.gguf` | Фаза A1 и отдельно шаг косинуса |
| Реранк | `rerank` | `/models/rerank.gguf` | Фаза A2 |
| Ответ | `answer` | `/models/answer.gguf` | Фаза B |

Размерность эмбеддинга — та, которую вернул пресет `embed`. Она пишется в `meta` и в байты float16. Тип на диске всегда float16, даже если сервер прислал JSON-числа. Подробности — [7. llama-gateways.md](7.%20llama-gateways.md).

## 6. Функциональные требования

### 6.1. Извлечение
- **DOCX:** стили заголовков → `section_path` (иерархия).
- **PDF:** эвристика заголовков (жирный шрифт, размер, нумерация `^\d+(\.\d+)*\s`). Если структура не извлечена — `section_path = null`, активируется `neighbors_fallback`.
- Метаданные фрагмента: `page`, `section_path`, `chunk_index`, `prev_id`, `next_id`.
- Таблицы извлекаются отдельным блоком в markdown-представлении.
- Отсутствие текстового слоя в PDF → `status=failed, reason=no_text_layer`, прогон продолжается.

### 6.2. Очистка
- Удаление колонтитулов и повторяющейся нумерации страниц.
- **Латиница не вырезается** — англицизмы значимы для поиска.
- Нормализация пробелов, кавычек, дефисов. Регистр в абзацах сохраняется.

### 6.3. Чанкинг
- Сначала по заголовкам (структурно), затем рекурсивно по `max_tokens` с `overlap_tokens`.
- Каждый чанк наследует `section_path` своего раздела.
- Дедупликация полностью совпадающих чанков.

### 6.4. Векторизация (A1)
- Одна модель для чанков и запросов (обязательное условие).
- Батчинг, кэш по хешу (`sha256(model + dtype + normalized_text)`).
- Эмбеддинги вопросов вычисляются на этой же фазе и кэшируются рядом с чанками (`questions.f16` и индекс, см. [3a. artifact-store.md](3a.%20artifact-store.md)).
- После индексации пресет `embed` снимается с llama-server. Байты вектора на диск пишет фаза, не шлюз.

### 6.5. Retrieval (A2)
- Варианты запроса для поиска = `category` + все `synonyms`. Каждый вариант эмбеддится отдельно (в A1).
- Синонимы расширяют **только retrieval** (вектор + BM25 + реранк). В промпт LLM они не попадают.
- Скор чанка = **max** по вариантам (`query_strategy: max_over_variants`).
- Гибридный поиск: top-k по вектору + top-k по BM25 → слияние (RRF или взвешенный скор), отсечение по `score_threshold`.
- **Top-k кандидатов сохраняется до реранка** (`candidates.jsonl`) — база для перебора реранкеров и для метрик Recall/MRR/nDCG.

### 6.6. Rerank (A2)
- Cross-encoder по top-k → `top_n`, отсечение по `reranker.score_threshold`.
- Цитаты по всем вариантам запроса (`category` + synonyms) сливаются в **один** `ContextBundle` на пару документ×вопрос.
- Если после порога пусто (или `max_score < early_exit_threshold`) → `empty_search: true`, `candidates: []`, в бандл пишутся `category`, `used_synonyms` / варианты поиска и `reason: no_relevant_chunks`. Бандл **всё равно** идёт в фазу B.
- Иначе → `empty_search: false`, бандл с объединённым контекстом идёт в B.

### 6.7. LLM-верификация (B)

В первый запуск шаг не входит. Фильтр «да / нет / частично» и пометка «частично» отложены: в модель ответа уходит контекст, собранный в A2, без второго прохода. Подробности — [6. answer-verifier-generator.md](6.%20answer-verifier-generator.md), раздел «Отложено».

### 6.8. Сборка контекста (section-level)
1. Группировка отобранных чанков по `section_path`; секции сортируются по лучшему скору.
2. В контекст включается **весь текст секции** (все её чанки).
3. Если секция > `max_section_tokens` — включаются только чанки из `top_n` плюс `neighbors_fallback` в каждую сторону внутри секции.
4. Общий бюджет `max_total_tokens`: при превышении отбрасываются секции с наименьшим скором (с конца).
5. Фрагменты нумеруются с метаданными: `[1] стр. 12–13, разд. 3.2.1`.
6. Если `section_path = null` — fallback на `neighbors_fallback`.

### 6.9. Ответ LLM (B)

Вопрос в промпте = **`category`**. Синонимы уже отработали на поиске; в промпт как варианты запроса они попадают только в блок «искали по …», не как отдельные задания.

- Пустой поиск (`empty_search: true`): модель **не** вызывается. Система пишет `found: false`, `reason: no_relevant_chunks` и текст «В поиске по этому вопросу ничего не найдено.»
- Контекст непустой: один вызов на вопрос, ответ — JSON (`found`, `answer`, `explanation`, `reason`, `citations`). «Отвечай только по фрагментам. Если ответа нет — `found: false` и код `not_present` / `insufficient_context` / `ambiguous`.» Длину ответа не ограничиваем.
- Модель прислала `found: true` и пустой список цитат: это не найденный ответ. Запись та же, что при пустом поиске (`found: false`, `no_relevant_chunks`, фраза «В поиске по этому вопросу ничего не найдено.»). Повтор из-за пустых цитат не делается.
- Нет годного ответа модели после `runtime.retries` попыток (число включает первый вызов): `status: failed`, `reason: model_unavailable`, текст «Модель недоступна.», в записи — промпт с найденными фрагментами.

### 6.10. Формат результата (на пару документ × вопрос)

`results/<doc_id>.jsonl`, одна строка:

```json
{
  "doc_id": "reglament_2024.docx",
  "question_id": "Q001",
  "category": "Срок хранения персональных данных",
  "used_synonyms": ["период хранения ПДн", "retention period for personal data"],
  "found": true,
  "answer": "Персональные данные хранятся 5 лет с момента ...",
  "explanation": "Срок назван во фрагменте [1], другие фрагменты его не уточняют.",
  "citations": [
    {
      "chunk_ids": ["c_0412", "c_0413", "c_0414"],
      "page_from": 12,
      "page_to": 12,
      "section_path": ["3. Регламент", "3.2. Хранение", "3.2.1. Сроки"],
      "quote": "…хранятся в течение 5 лет…"
    }
  ],
  "confidence": null,
  "reason": null,
  "retrieval": {
    "candidates": 20,
    "after_rerank": 5,
    "after_verify": 3,
    "sections_used": ["3.2.1. Сроки"]
  },
  "tokens": {"prompt": 4210, "completion": 180},
  "model": "answer",
  "latency_ms": 1834,
  "status": "ok"
}
```

- `used_synonyms` — метаданные retrieval (какие варианты реально участвовали в max-over-variants); не означает, что LLM отвечал на синонимы.
- `answer` — ответ на вопрос. `explanation` — пояснение и обоснование отдельно от ответа.
- При непустом поиске и непустых цитатах `found` / `answer` / `explanation` / `reason` — разобранный JSON модели. При пустом поиске и при `found: true` без цитат их пишет система.
- У цитаты `chunk_ids` — список чанков фрагмента, на который ссылается модель. Одно поле `chunk_id` в записи ответа больше не используется.
- Если модель не дала годный ответ, в строке есть `prepared_context`: промпт с фрагментами, который готовили к вызову. При успехе и при пустом поиске поля нет (`null`).

### 6.11. Сохранение
- `results/<doc_id>.jsonl` — по строке на вопрос.
- `results/<doc_id>.md` — человекочитаемо.
- `results/run_summary.json` — агрегат: документы, вопросы, error rate, средние latency/tokens, версии моделей, статистика по фазам (`computed`/`skipped`).
- `logs/run_<timestamp>.log` — structured log.

## 7. Персистентность артефактов и инвалидация

### 7.1. Структура

Файлы PoC — JSONL, `*.f16` и `meta.json`, как в [3a. artifact-store.md](3a.%20artifact-store.md). Дерево ниже сохраняет логические поля; имена `*.parquet` в нём — прежняя схема колонок, на диске PoC их заменяют JSONL и сырой float16.

```
.cache/
  emb/
    <doc_id>/
      chunks.parquet           # chunk_id, text, page, section_path, vector
      meta.json                # {embedding_model, dtype, chunking_hash, n_chunks}
  questions.parquet            # question_id, variant, vector
  questions.meta.json          # {embedding_model, dtype, n_questions}

index/
  <doc_id>/
    candidates.parquet         # top_k до реранка
    meta.json                  # {retrieval_config_hash, top_k, hybrid}

contexts/
  <doc_id>/
    <question_id>.json         # пост-реранк + section-expansion

results/                       # см. 6.11
```

### 7.2. Форматы

**`chunks.parquet`:**

| column | type |
|---|---|
| `chunk_id` | string |
| `text` | string |
| `page_from`, `page_to` | int32 |
| `section_path` | string (json) |
| `chunk_index` | int32 |
| `prev_id`, `next_id` | string / null |
| `vector` | fixed_size_list<float16, D> |

**`candidates.parquet`:**

| column | type |
|---|---|
| `question_id` | string |
| `chunk_id` | string |
| `vector_score` | float32 |
| `bm25_score` | float32 |
| `fused_score` | float32 |
| `rank` | int32 |

**`contexts/<doc>/<q>.json`:**

```json
{
  "doc_id": "...",
  "question_id": "Q001",
  "category": "...",
  "used_synonyms": ["..."],
  "empty_search": false,
  "reason": null,
  "budget_used_tokens": 4210,
  "candidates": [
    {
      "rank_after_rerank": 1,
      "rerank_score": 0.87,
      "section_path": ["3. Регламент", "3.2. Хранение", "3.2.1. Сроки"],
      "pages": [12, 13],
      "text": "…полный текст секции (или усечённый до max_section_tokens)…",
      "chunks_included": ["c_0412", "c_0413", "c_0414"],
      "truncated": false
    }
  ],
  "retrieval_meta": {
    "top_k": 20, "after_rerank": 5,
    "sections_used": ["3.2.1. Сроки"],
    "embedding_model": "...",
    "reranker_model": "..."
  }
}
```

Если поиск ничего не дал — бандл с `empty_search: true` передаётся в B. Модель на этой паре не вызывается; система пишет `AnswerRecord` с фразой «В поиске по этому вопросу ничего не найдено.»:

```json
{
  "doc_id": "...", "question_id": "Q017",
  "category": "...",
  "used_synonyms": ["...", "..."],
  "empty_search": true,
  "reason": "no_relevant_chunks",
  "candidates": [],
  "retrieval_meta": {"top_k": 20, "after_rerank": 0}
}
```

### 7.3. Хеш-валидация и `skip_if_artifacts_valid`

- `chunking_hash` = sha256(`max_tokens + overlap + min_chunk + preserve_section_path`).
- `retrieval_config_hash` = sha256(`top_k + score_threshold + hybrid.* + query_strategy`).
- `reranker_config_hash` = sha256(`model + top_n + score_threshold`).
- Каждый `meta.json` содержит `schema_version`.

На старте каждой фазы для каждого документа:
1. Прочитать `meta.json`.
2. Сравнить `schema_version` и соответствующий хеш.
3. Совпало → фаза пропускается (лог `phase_skipped: hashes_valid`).
4. Не совпало / файла нет → фаза пересчитывается.

В `run_summary.json` по каждой фазе: `{computed: N, skipped: M}`.

### 7.4. Дисковый бюджет

Оценка на 100 документов × 300 страниц × ~1500 чанков × D-мерный float16 (D — размерность пресета `embed`; ниже порядок величины при D = 2048):

| Артефакт | На документ | На 100 документов |
|---|---|---|
| `chunks.parquet` | ~8 МБ | ~800 МБ |
| `candidates.parquet` (~50 вопросов) | ~200 КБ | ~20 МБ |
| `contexts/<doc>/*.json` | ~1–3 МБ | ~100–300 МБ |
| `questions.parquet` | — | ~1 МБ |
| **Итого** | | **~1 ГБ** |

При необходимости — `context.compression: gzip`.

## 8. CLI

```bash
# Полный прогон — A1 → A2 → B с пропуском готовых фаз по хешам
python main.py run --config config.yaml

# Только A1 — разбор на чанки (+ эмбеддинги чанков, когда шлюз боевой).
# Файл вопросов для одного A1 не обязателен; кэш вопросов пишется, только если вопросы загружены.
python main.py run --config config.yaml --phase A1

# A1+A2 один раз, артефакты на диске
python main.py run --config config.yaml --phase A1,A2

# Имена --answer-model / --reranker-model / --embedding-model —
# секции deploy/llama/models.ini. В репозитории это answer, rerank, embed.
# Другое имя допустимо, только если секция добавлена в ini.
# Замена файла GGUF без смены имени секцию хеша чанкинга не меняет: нужен --force-phase.

# Перебор ответа: A1+A2 готовы, каждый запуск — только B с пресетом секции
for m in answer; do
  python main.py run --config config.yaml --phase B \
    --answer-model "$m" \
    --results-dir "./results/$m"
done

# Перебор реранкеров: A1 готов, A2 пересчитывается из сохранённых кандидатов
for r in rerank; do
  python main.py run --config config.yaml --phase A2 \
    --reranker-model "$r" \
    --contexts-dir "./contexts/$r"
done

# Перебор эмбеддеров: инвалидация A1, полный цикл
for e in embed; do
  python main.py run --config config.yaml \
    --embedding-model "$e" \
    --cache-dir "./.cache/emb/$e" \
    --results-dir "./results/emb=$e"
done

# Оценка на gt.json
python main.py eval --config config.yaml \
  --ground-truth ./gt.json \
  --predictions ./results/answer
```

Дополнительно: `--force-phase <A1|A2|B>` для принудительного пересчёта при сомнениях в артефактах.

## 9. Нефункциональные требования

- **Локальность:** без вызовов во внешние API. HTTP разрешён только к контейнеру llama-server в сети compose. GGUF читает этот контейнер с тома `./models`.
- **Воспроизводимость:** `temperature=0`, имена пресетов фиксируются в `run_summary.json`.
- **VRAM-бюджет:** одна GGUF на GPU, батч эмбеддинга, `max_total_tokens`, между фазами пресет снимается. Процесс приложения кэш CUDA не трогает: весов в нём нет.
- **Устойчивость:** retry с backoff на LLM; graceful degradation при сбое верификации.
- **Наблюдаемость:** structured logs; в DEBUG — retrieval-скоры и финальный промпт (с флагом маскирования текста).
- **Идемпотентность:** повторный запуск с теми же параметрами ничего не пересчитывает (`skip_if_artifacts_valid`).

## 10. Оценка качества

На `gt.json` команда `python main.py eval` считает метрики ниже. Формулы, знаменатели и поля `EvalReport` — в [8. eval.md](8.%20eval.md). Страницы для Recall, MRR и nDCG берутся из кандидатов до реранка. `empty_search` читается из бандла контекста.

- **Retrieval (A2):** Recall@k (k = 5, 10, 20) по пересечению страниц, MRR, nDCG@10, точность решения `empty_search` (поиск пуст / не пуст).
- **Классификация `found`:** precision / recall / F1 по классу `found` (конец прогона и отдельно A2: попала ли эталонная страница в пул до генерации).
- **Ответ:** exact match (для коротких эталонов) + косинус эмбеддингов ответа и эталона тем же пресетом `embed`.
- **Цитаты:** precision / recall пересечения страниц цитат с `expected_pages`; доля ответов с ≥1 верной цитатой.
- **Стоимость:** средние токены и latency на вопрос; счётчики фаз из `run_summary.json`, если он лежит в каталоге предсказаний.

Раздельные метрики по фазам позволяют отличить деградацию ретривера от деградации генератора при смене пресета.

## 12. Риски и митигации

| Риск | Влияние | Митигация |
|---|---|---|
| PDF без надёжной структуры заголовков | section-expansion деградирует | `neighbors_fallback`; логировать `% чанков без section_path`; предупреждение в summary |
| GGUF ответа не помещается на GPU контейнера | Пресет `answer` не поднимается | Файл меньшей квантизации по тому же пути; `ctx-size` 4096 уже задан в ini; `max_total_tokens` и батч эмбеддинга |
| Окно пресета 4096 меньше чанка | Сервер обрежет вход эмбеддинга | Чанк в конфиге остаётся внутри этого окна; смена окна — правка ini и `--force-phase A1` |
| Мультиязычность (RU + англицизмы) | Потеря релевантности | Очистка не режет латиницу; синонимы включают EN-варианты; мультиязычная эмбеддер-модель |
| LLM-верификация «съедает» кандидатов | Ложные `not_found` | В первый запуск шаг не входит; фрагменты сборки идут в ответ как есть |
| Устаревшие артефакты после правки чанкинга/модели | Некорректный прогон | Хеши в `meta.json` + `skip_if_artifacts_valid`; в summary фиксируется факт пересчёта |
| Диск переполняется при переборе эмбеддеров | Отказ прогона | Отдельные `--cache-dir` на модель; документированная очистка |
| Переполнение `contexts/` | Дисковый бюджет | `context.compression: gzip`; удаление после B для прода |
| Вторая модель рядом с ответом | Не хватает VRAM при `--models-max 1` | В первый запуск верификатор не вызывается и второй пресет не грузится |

## 13. Открытые вопросы (не блокируют старт разработки)

1. **Файл GGUF для пресета `answer`** — кладётся оператором в `/models/answer.gguf`. Имя пресета фиксировано; какой именно файл прошёл бенч на T10, эта спецификация не выбирает.
2. **Отдельная модель верификации** — в первый запуск не загружается. Вопрос вернётся вместе с `AnswerVerifier`.
3. **Формула `confidence`** — комбинация `rerank_score` и уверенности LLM; уточняется на пилоте.
4. **`persist_bm25`** — по умолчанию `false`; включать при многократном переборе реранкеров.
5. **Сжатие `contexts/`** — по умолчанию `none`; включать по дисковому бюджету.

```
Шаг 1 (один раз):   python main.py run --phase A1
Шаг 2 (один раз):   python main.py run --phase A2
Шаг 3 (цикл):       для каждого пресета ответа (секция models.ini):
                      python main.py run --phase B --answer-model M --results-dir results/M
                      python main.py eval --predictions results/M --ground-truth gt.json
Шаг 4 (опция):      смена пресета реранкера → шаг 2 для каждого, затем шаг 3
Шаг 5 (опция):      смена пресета эмбеддера → шаг 1 (инвалидирует всё)
```

Каждый шаг идемпотентен: повторный запуск с теми же параметрами ничего не пересчитывает.
