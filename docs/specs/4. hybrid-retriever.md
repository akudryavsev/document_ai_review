# Спецификация: гибридный поиск и реранк — v1.1

Статус: **утверждена**. Можно писать тесты и код по этому документу. v1.0 скорила реранк всеми вариантами запроса. v1.1: `reranker.query_strategy` — `category` по умолчанию, `synonyms_rerank` как в v1.0.

Связанные документы: [0. spec.md](0.%20spec.md) (разделы 6.5, 6.6), [1. top-level-classes.md](1.%20top-level-classes.md) (фаза A2, `RerankerGateway`), [3a. artifact-store.md](3a.%20artifact-store.md) (`candidates.jsonl`), [5. context-assembler.md](5.%20context-assembler.md).

## 1. Назначение и границы

**Назначение.** Для одной пары «документ × вопрос» построить пул кандидатов до реранка и зафиксировать, как `RetrievalPhase` передаёт этот пул в `RerankerGateway` и что из ответа доходит до сборки контекста.

**Разделение ролей.**

| Класс | Ответственность |
|---|---|
| `HybridRetriever` | Векторный поиск и BM25, max по вариантам внутри каждой ветви, объединение лучших с обеих ветвей. Абсолютный `retrieval.score_threshold` режет только векторную ветвь и только если он больше 0. Реранкер не вызывает. При включённом дампе пишет промежуточные скоры поиска (§3.2) |
| `RerankerGateway` | Скоринг пар «запрос × пассаж». Не знает порогов отбора, BM25, политики синонимов и `ContextBundle` |
| `RetrievalPhase` | Единственный оркестратор между ними: `top_n`, опциональные `reranker.score_threshold` и `early_exit`; при `persist_candidates` пишет итоговый артефакт; при debug — дописывает блок реранка в дамп (§3.2) |

**Не входит в эти классы:** расширение секций и сборка `ContextBundle`; повторный расчёт эмбеддингов; загрузка и выгрузка модели (`load`/`unload` — шлюз и `GpuLease`); формат и атомарность `candidates.jsonl` (`ArtifactStore`); тензоры в моделях обмена.

**Публичные методы:**

| Класс | Метод | Результат |
|---|---|---|
| `HybridRetriever` | `search(doc_id, question, chunks)` | `CandidateBatch` до реранка (в памяти) |
| `RerankerGateway` | `infer(request: RerankRequest)` | `RerankResponse` со скорами и рангами |

Конструктор поиска получает `RetrievalConfig`, доступ к векторам по `item_id` и опционально `RetrievalDebugDump`. В аргументы `search` векторы не входят.

## 2. Идентификаторы векторов

Идентификаторы назначает `IndexingPhase`; поиск использует те же строки.

| Текст | `item_id` |
|---|---|
| `question.category` | `{question.id}:category` |
| `question.synonyms[i]` | `{question.id}:syn:{i}` (`i` с нуля) |
| текст чанка | `chunk.chunk_id` |

Варианты запроса для одной пары: `category`, затем все `synonyms` в исходном порядке. Пустой список синонимов допустим — тогда вариант один.

Каждый вариант — **отдельный полный текстовый запрос** (целая строка category или целый синоним), не склейка всех формулировок и не разбиение на отдельные слова сверх токенизации BM25. Векторная ветвь берёт эмбеддинг этого варианта по `item_id`; лексическая — ту же строку как запрос BM25 по текстам `chunks`.

Как байты float16 попадают из llama-server в хранилище и как поиск читает их по `item_id`, описано в [7. llama-gateways.md](7.%20llama-gateways.md). Здесь фиксируются только ключ `item_id` и запрет тензора на границе оркестрации.

Флаг `persist_bm25` на результат `search` не влияет: лексический индекс строится в памяти из `chunks` данного вызова. Дисковый BM25 — открытый вопрос спеки поведения и здесь не специфицируется.

## 3. Выход `search` и запись на диск

### 3.1. Контракт в памяти

Один вызов `search` — один вопрос. Результат — pydantic-модель `CandidateBatch`: поле `candidates` — **список** `CandidateRecord` (не файл, не таблица, не генератор). `doc_id` равен аргументу `doc_id`. В каждой записи `question_id` равен `question.id`. Длина списка — от 0 до размера объединения двух ветвей (каждая ветвь — `top_k` плюс ничьи на границе).

| Поле | Правило |
|---|---|
| `chunk_id` | Идентификатор чанка документа, не варианта запроса |
| `vector_score` | Косинус после max по вариантам. У чанка только из BM25 — тоже фактический косинус, не ноль |
| `bm25_score` | BM25 после max по вариантам. У чанка только из векторной ветви — фактический BM25, не ноль; при `hybrid.enabled=false` — 0 |
| `fused_score` | Равен `vector_score`. Это не смесь ветвей: веса `bm25_weight` / `vector_weight` на отбор не влияют |
| `rank` | Плотный ранг с 1. Порядок — лучший ранг ветви (меньшее из двух), затем меньший `chunk_index`, затем лексикографически меньший `chunk_id` |
| `rerank_score` | `None` (реранк ещё не выполнялся) |
| `text` | `ChunkRecord.text` |
| `section_path` | Путь чанка как есть, включая `None` |
| `pages` | Целые номера от `page_from` до `page_to` включительно; если оба нули — пустой список |

Пара `(question_id, chunk_id)` встречается один раз, даже если чанк попал и в векторную, и в лексическую ветвь.

`retrieval_config_hash` проставляет фаза. Поиск может оставить строку пустой.

Реранк и сборка контекста читают этот список из памяти в том же прогоне. Диск для прохождения A2→B **не обязателен**.

### 3.2. Два разных вида записи на диск

| Что | Флаг | Кто пишет | Формат | Зачем |
|---|---|---|---|---|
| Итоговые кандидаты **до** реранка по документу | `retrieval.persist_candidates` (по умолчанию `true`) | `RetrievalPhase` → `ArtifactStore` | `{index_dir}/{doc_id}/candidates.jsonl` + `meta.json` ([3a](3a.%20artifact-store.md) §3.8) | Кэш для перебора реранкеров без повторного hybrid search |
| Все **промежуточные** шаги пары документ×вопрос | `retrieval.debug_dump` (по умолчанию `false`) | поиск + фаза через `RetrievalDebugDump` | `{runtime.cache_dir}/debug/{doc_id}/{question_id}.retrieval.json` | Разбор «почему этот чанк / почему пусто»; не зона `ArtifactStore` |

Имя `candidates.parquet` из спеки поведения здесь **не используется**: норма хранилища — JSONL (UTF-8, по строке на `CandidateRecord`), без pyarrow/parquet. Объём итогового файла мал относительно эмбеддингов чанков (порядок сотен КБ на документ при десятках вопросов); тяжёлых зависимостей для кандидатов нет.

**`persist_candidates`.** Фаза после всех вопросов документа собирает один `CandidateBatch`: конкатенация выходов `search` (ещё **без** `rerank_score`). Это и есть содержимое `candidates.jsonl`. Сейчас код сохраняет уже переписанный реранком пакет — после утверждения норма: пакет **до** реранка. При `persist_candidates=false` файл кандидатов не пишется; прогон A2 в том же процессе не ломается.

**`debug_dump`.** По аналогии с `extraction.debug_dump` (extract/clean): отдельный флаг, по умолчанию выключен, пишет в `{cache_dir}/debug/…`, на контракт `search` / реранка / skip-фаз не влияет. Включённый дамп **не** заменяет `persist_candidates` и **не** участвует в `ArtifactGate`.

Файл дампа — один JSON (UTF-8, отступ 2) на пару. Пишется после успешного `search` для этой пары; блок реранка дописывается/обновляется фазой после шагов раздела 5 (в том числе когда `infer` не вызывался). При исключении из `search` или `infer` файл может отсутствовать или остаться без финального блока реранка — это не маскирует ошибку фазы.

Обязательные ключи верхнего уровня:

| Ключ | Содержимое |
|---|---|
| `doc_id`, `question_id` | Аргументы пары |
| `variants` | Список `{variant_index, item_id, text}` в порядке §2 |
| `per_variant` | Для каждого варианта: скоры по **всем** чанкам входа `{chunk_id, vector_score, bm25_score}` до max и top_k; при `hybrid.enabled=false` у всех `bm25_score=0` |
| `after_max` | После max по вариантам: `vector_top_k` и `bm25_top_k` — списки `{chunk_id, score}`. Длина ветви — `top_k` плюс чанки с тем же скором, что у границы |
| `fused_before_threshold` | Объединение двух ветвей: `chunk_id`, `vector_score`, `bm25_score`. Отдельной формулы слияния нет |
| `selected` | Итог `search`: те же поля, что у `CandidateRecord` в пакете (включая `text`, `section_path`, `pages`) |
| `rerank` | После фазы: `pairs` (`pair_id`, `query`, `passage_id`, `score`), `chunk_scores` (max по парам чанка), `early_exit` (bool), `selected_after` (список записей, ушедших в сборку, или `[]`) |

При `hybrid.enabled=false` ключ `after_max.bm25_top_k` — пустой список; в `per_variant` лексические скоры не требуются как осмысленные BM25.

Полные тексты чанков в `per_variant` / `after_max` / `fused_before_threshold` **не** дублируются (только `chunk_id` и скоры); полные `text` есть в `selected` и в `rerank.selected_after`. Так дамп остаётся читаемым JSON без раздувания на тысячах чанков × вариантах.

`RetrievalDebugDump` — узкий писатель пути и JSON (как `BlockDocumentDebugDump` для Markdown). В `TraceEvent.debug_payload` тело файла не кладётся — максимум путь или короткий summary.

## 4. Алгоритм поиска

Отбор — лучшие с каждой ветви, без общей формулы слияния. RRF и взвешенная сумма `bm25_weight` / `vector_weight` не используются: шкалы косинуса и BM25 разные, одно число из них отбор не улучшает. Веса в конфиге остаются, на пул не влияют.

1. Для каждого варианта запроса отдельно считаются косинус и BM25 по текстам чанков.
2. Скор чанка в ветви — **max по вариантам** именно этой ветви. Сначала max, потом top ветви. Слитого скора варианта нет.
3. Если `retrieval.score_threshold` **больше 0**, в векторную ветвь попадает чанк только при косинусе **строго больше** порога. Равенство порогу чанк не пропускает. Значение **0** порог выключает. На BM25 этот порог не действует: у лексического скора другая шкала.
4. Векторная ветвь оставляет `top_k` лучших по косинусу. Если у границы несколько чанков с тем же косинусом, берутся все, даже если ветвь длиннее `top_k`.
5. Ветвь BM25 так же оставляет `top_k` лучших по BM25, с той же ничьей на границе.
6. Пул — объединение двух списков. Чанк из обеих ветвей — одна запись.
7. `rank` — по лучшему месту в ветвях (меньшее из двух рангов; нет ранга ветви — ветвь не учитывается), затем меньший `chunk_index`, затем лексикографически меньший `chunk_id`.

Норма для незнакомого документа — `score_threshold: 0`. Ненулевое значение оператор ставит сам, когда шкала косинуса уже замерена.

Иная `query_strategy` — `ValueError`.

При `hybrid.enabled=false` работает только векторная ветвь: BM25 не строится, `bm25_score=0`, `fused_score` равен косинусу. Синонимы по-прежнему участвуют в max векторной ветви.

Нет чанков — пустой `CandidateBatch`, исключения нет; реранкер для этой пары не вызывается.

### 4.1. Косинус

`vector_score` — косинусное сходство вектора варианта и вектора чанка: скалярное произведение, делённое на произведение длин. Если хранилище отдаёт уже нормированные векторы, произведение совпадает с косинусом; контракт при этом остаётся косинусом.

Голое скалярное произведение без деления на длины не используется. Длинный вектор набирает большее произведение при том же направлении, и порог по такому числу с нового документа не переносится.

Нулевая длина вектора считается отсутствием вектора (§4.3).

### 4.2. BM25

Запрос ветви — целая строка варианта. Индекс строится в памяти по `chunks` этого вызова.

Токены запроса и чанка — одни и те же правила:

- текст приводится к нижнему регистру (`casefold`);
- токен — непрерывная последовательность букв или цифр (Unicode); знаки и пробелы — разделители;
- токен из одних цифр остаётся как есть;
- токен из букв заменяется леммой `pymorphy3`: `normal_form` первого разбора. Одинаковые правила у запроса и у чанка;
- стоп-слов нет.

Лемма склеивает словоформы: «модем», «модема», «модему», «модемов» — один терм «модем». Поэтому запрос «установка модема» и текст «устанавливается модем» получают общий терм «модем» и ненулевой BM25, даже если второе слово не совпало.

Лемма не склеивает разные части речи и разные глаголы: «установка» остаётся «установка», «устанавливается» — «устанавливаться», «установить» — «установить». Это не ошибка словаря. Такой разрыв закрывают ручной синоним и векторная ветвь: эмбеддинг считается по исходному тексту, не по лемме.

Стеммер Snowball для этого не используется. На коротких словах он расходится сам с собой: «модем» → «мод», «модема» → «модем».

Параметры фиксированы, в конфиг не выносятся: `k1 = 1.5`, `b = 0.75`.

`k1` — насколько повтор слова в чанке продолжает увеличивать скор. 1.5 — обычное значение Okapi: первые повторы заметны, дальше вклад быстро насыщается. `b` — штраф за длину чанка относительно средней длины в этом вызове. 0.75 слегка предпочитает более короткий чанк при тех же словах. Чанки и так нарезаны по лимиту токенов, поэтому штраф не доминирует.

Для терма `t` в чанке `D` при запросе `Q`, числе чанков `N` и числе чанков с термом `df`:

```text
idf(t) = ln(1 + (N - df + 0.5) / (df + 0.5))
tf_part(t, D) = f * (k1 + 1) / (f + k1 * (1 - b + b * len(D) / avgdl))
bm25(D, Q) = сумма по термам запроса idf(t) * tf_part(t, D)
```

`f` — число вхождений терма в чанк, `len` и `avgdl` — в токенах этих же правил. Терм запроса, которого нет в чанке, даёт 0. Пустой список токенов у варианта — BM25 этого варианта равен 0.

### 4.3. Нет вектора

Вектор варианта или чанка отсутствует, либо его длина нулевая: поиск по этой паре не из чего собрать. Подставлять нулевой вектор и молча выкидывать отдельные чанки нельзя — индекс должен был появиться раньше, на индексации и проверке связки.

Поведение `search`: событие в `TraceSink` со `status=failed` и текстом, в котором есть отсутствующий `item_id`; исключения нет; возврат — пустой `CandidateBatch`. Фаза не помечает документ A2 как `failed` из-за этого и переходит к следующему вопросу. Для этой пары дальше обычный пустой поиск: `infer` не вызывается, в сборку `empty_search=true`.

## 5. Взаимодействие с `RerankerGateway`

Норма при `reranker.enabled=true`. Ветка `enabled=false` — в конце раздела.

На одну пару «документ × вопрос»:

1. Фаза вызывает `search`.
2. Пустой пакет — `infer` не вызывается; в сборку уходит пустой пакет с `empty_search=true`.
3. Иначе фаза строит `RerankRequest`. Набор запросов задаёт `reranker.query_strategy`:
   - `category` (значение по умолчанию) — один текст: `question.category`;
   - `synonyms_rerank` — `category`, затем все `synonyms` в исходном порядке.
   Иное значение — `ValueError` при разборе конфига. Поиск по-прежнему всегда идёт по `category` и синонимам (`retrieval.query_strategy`).
   Для каждого кандидата и каждого выбранного запроса — одна пара:
   - `query` — текст этого запроса, не склейка синонимов;
   - `passage` — `CandidateRecord.text`;
   - `passage_id` — `chunk_id`;
   - `pair_id` — `{chunk_id}#{variant_index}` (индекс в выбранном списке; 0 — `category`).
4. Один `infer` на пару документ×вопрос. Вопросы в одном запросе не смешиваются. Ранг шлюза для отбора чанка не используется.
5. Скор чанка после реранка — max `score` по его парам. При `category` пара одна. При `synonyms_rerank` синонимы расширяют реранк; цитаты потом сливаются в один бандл категории.
6. Пара без ответа шлюза чанк не оставляет: запись с `rerank_score is None` в отобранный пакет не входит.
7. `early_exit` только если `context.early_exit_threshold` **больше 0**: максимальный реранк-скор **строго меньше** порога → отобранный пакет пуст. Значение **0** ранний выход выключает. Оператор «строго меньше» взят из комментария конфигурации в спеке поведения.
8. Иначе, если `reranker.score_threshold` **больше 0**, остаются только чанки со скором **строго больше** порога. Равенство порогу чанк не пропускает. Затем из прошедших берутся `top_n` лучших. Чанки с тем же скором, что у границы `top_n`, тоже остаются, даже если их больше `top_n`. Значение **0** порог выключает: шаг порога пропускается, в сборку идут `top_n` лучших плюс ничья на границе. Объём текста в промпте ограничивает сборка контекста (`max_section_tokens`, `max_total_tokens`), а не отбрасывание ничьих.
9. У прошедших записей заполнен `rerank_score`; порядок — по убыванию этого скора. Поля `vector_score`, `bm25_score`, `fused_score`, `text`, `section_path`, `pages` копируются из выхода `search`.
10. Пустой итог шагов 7–8 → `empty_search=true`; непустой → `empty_search=false`.

Норма для незнакомого документа — оба порога **0** и `top_n` (в примере конфига 5). Решение «в документе этого нет» принимает верификатор по тексту, а не шкала реранкера. Ненулевые `early_exit_threshold` и `reranker.score_threshold` остаются в конфиге: оператор подкручивает их под свою модель. При нулевых порогах тест проверяет, что `top_n` уходит в сборку и шлюз не вызывается на пустом поиске.

`RerankResponse` не превращается в `ContextBundle` внутри шлюза.

### 5.1. `reranker.enabled=false`

Шлюз не вызывается. `early_exit` не применяется: сравнивать не с чем, порог раннего выхода калибруется по скорам реранкера, а не по косинусу.

В сборку идут `top_n` записей выхода `search` в его порядке, плюс ничья на границе по тому же ключу порядка (§4, шаг 7). `rerank_score` заполняется числом `n - rank + 1` (`n` — длина уже отобранного списка, больше — лучше), чтобы сборщик мог сортировать секции. Поля поиска копируются как в шаге 9. Пустой `search` по-прежнему даёт `empty_search=true`.

## 6. Инварианты

- `search` детерминирован при тех же чанках, векторах, вопросе и `RetrievalConfig`.
- Каждая ветвь поиска отдаёт не больше `top_k` чанков плюс все чанки со скором на границе отсечения. В пакете одна запись на чанк. Ранг плотный с 1; у выхода `search` поле `rerank_score is None`.
- Синоним не порождает отдельную строку кандидата.
- `category` не попадает в список синонимов; список для бандла копирует сборка контекста.
- Пустой `search` не приводит к вызову `infer`.
- При включённом реранкере каждый запрос в `infer` — ровно один выбранный текст (`category` или один синоним); пассаж — текст кандидата из `search`. При `query_strategy=category` число пар равно числу кандидатов.
- В моделях запроса и ответа нет тензоров.
- Поиск не вызывает LLM и не читает ground truth.
- `persist_candidates` и `debug_dump` независимы: любой из четырёх сочетаний допустим.
- При `debug_dump=false` файлов `{cache}/debug/{doc_id}/{question_id}.retrieval.json` нет.
- Дамп и `candidates.jsonl` не влияют на скоры, порядок и решение `empty_search`.
- При `retrieval.score_threshold == 0` векторная ветвь не отбрасывает чанк из-за косинуса.
- При пороге поиска или реранка больше 0 чанк со скором, равным порогу, не проходит.
- При `reranker.score_threshold == 0` и `early_exit_threshold == 0` в сборку уходят `top_n` лучших после реранка плюс ничья на границе; пустой пакет бывает только если `search` пуст или шлюз не вернул скоры.
- `bm25_weight` и `vector_weight` не меняют состав пула и порядок `search`.
- Нет нужного вектора — пустой `search` и событие `failed` в трассе, без исключения и без `failed` у документа.

## 7. Ошибки

| Ситуация | Поведение |
|---|---|
| `query_strategy` не `max_over_variants` | `ValueError` из `search` |
| `reranker.query_strategy` не `category` и не `synonyms_rerank` | `ValueError` при разборе конфига |
| Нет чанков, либо порог > 0 и ни один чанк его не прошёл | Пустой пакет, не исключение |
| Нет вектора варианта или чанка, нулевая длина вектора | Пустой пакет, событие `failed` в трассе, не исключение; документ не `failed`; следующие вопросы идут |
| Пустой пакет на входе реранка | `infer` не вызывается |
| `infer` бросил исключение | Исключение уходит в `execute` фазы; документ A2 — `failed`, следующие продолжаются. Тихого `empty_search` вместо сбоя шлюза нет |

## 8. Граница со сборкой контекста

Фаза вызывает `ContextAssembler.assemble(doc_id, question, selected, empty_search, chunks)`.

`selected` — пакет после шагов раздела 5 (не сырой выход `search`, если реранкер отработал). `chunks` — уже загруженный `ChunkBatch` документа; сборщик хранилище сам не открывает. `empty_search` истинен тогда и только тогда, когда в `selected` нет записей.

Дальше пороги не пересматриваются. Ранний выход и пустой реранк сборщик сам не вычисляет: он получает уже готовый флаг.

## 9. Каталог тестов

Числовые проверки косинуса и BM25 опираются на §4.1 и §4.2.

| T-RNK-04 | `early_exit_threshold` > 0 и лучший реранк-скор строго меньше его | Пакет для сборки пуст, `empty_search=true`, даже если часть скоров выше `reranker.score_threshold` |

| T-RNK-10 | `reranker.score_threshold` равен скору чанка | Этот чанк не проходит |
| T-RNK-11 | `reranker.enabled=false`, поиск из трёх чанков, `top_n=2`, `early_exit_threshold` > 0 | `infer` не вызывается; в сборке два лучших по порядку `search`; `rerank_score` равен `n - rank + 1`; пакет не пустеет из-за `early_exit` |

| T-RNK-13 | `reranker.query_strategy` не из `{category, synonyms_rerank}` | `ValueError` при разборе конфига |

T-ART-05 и T-ART-06 остаются на фазе ответа: пустой поиск доходит до B уже как бандл, модель на этой паре не вызывается.

## 10. Закрытые вопросы

| ID | Решение |
|---|---|
| Q-RET-1 | Пул — лучшие с каждой ветви. RRF и веса ветвей отбор не делают. `fused_score` равен косинусу |
| Q-RET-2 | При пороге > 0 проход строгий: скор больше порога. Ноль порог выключает |
| Q-RET-3 | Max по вариантам считается внутри ветви, до её top |
| Q-RET-4 | Метрика вектора — косинус |
| Q-RET-6 | Сначала строгий порог, потом `top_n` и ничья на границе. Ноль порог выключает |
| Q-RET-7 | Реранкер выключен: `infer` нет, берутся `top_n` по порядку поиска, `early_exit` не применяется (§5.1) |
| Q-RET-8 | На границе `top_k` / `top_n` забираются все чанки с тем же скором. Весь документ в контекст не кладётся: его режет бюджет сборки |
| Q-RET-9 | Нет вектора — пустой результат этой пары, сигнал в трассу, прогон не останавливается (§4.3) |
