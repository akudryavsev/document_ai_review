# Спецификация: очередь Redis Streams и контракт API — v1.0

Статус: **проект, ждёт утверждения**. Тесты и код по этому документу не писать, пока пользователь его не утвердил.

Связанные документы: [1. top-level-classes.md](1.%20top-level-classes.md) (§4.2, §4.3, §6), [7. llama-gateways.md](7.%20llama-gateways.md) (контейнер `inference`), [8. eval.md](8.%20eval.md) (`EvalReport`).

Документ закрывает открытый пункт про транспорт: **Redis Streams**. RQ не используется. В репозитории клиента RQ нет, единица очереди — целый прогон, одна запись стрима этому соответствует.

`ApiApp` и `WorkerApp` в PoC не запускаются. Контракт нужен, потому что входные точки позже обязаны звать тот же `DocumentAnalysisService`. CLI остаётся на `InlineJobExecutor`.

## 1. Назначение и границы

**Назначение.** Зафиксировать адаптер `JobExecutor` поверх Redis Streams и маршруты `ApiApp` / цикл `WorkerApp`.

**Делает:**

- Принимает тот же `Job`, отдаёт тот же `JobReceipt`, `wait` возвращает `RunSummary` или `EvalReport`.
- Описывает профили compose так, чтобы имя `inference` осталось за llama-server.

**Не делает:**

- Не копирует фазы, шлюзы и формулы eval.
- Не дробит задание на документы и вопросы.
- Не поднимает второй воркер: у контейнера моделей `--models-max 1`.
- Не описывает экран. Профиль `frontend` остаётся заглушкой спеки классов.
- Не меняет PoC-команду `CliApp`.

Пайплайн по-прежнему один: и CLI, и воркер собирают `Application` и вызывают `DocumentAnalysisService`.

## 2. Транспорт

Выбран **Redis Streams** с группой потребителей.

RQ отклонён явно. Отдельной очереди «вопрос» или «документ» нет. Запись стрима — один `Job` (`kind = analyze` или `kind = eval`) целиком, с вложенным `RunRequest` или `EvalRequest`.

Почему одна запись на прогон: модель в llama-server одна на фазу, документы внутри прогона идут последовательно. Параллелить задания на одном GPU нельзя. Воркер берёт следующую запись только после подтверждения предыдущей.

## 3. Имена в compose

Сервис `inference` — это llama-server, профиль `poc`, порт 8080. Так файл `docker-compose.yml` устроен сейчас. Этот сервис не переименовывается и в профиль очереди не переносится.

Профиль очереди называется **`queue`**, не `inference`.

| Профиль | Сервисы | Назначение |
|---|---|---|
| `poc` | `app`, `inference` | CLI и llama-server. Redis нет. GPU только у `inference` |
| `test` | образ `app` без GPU | Тесты на подделках |
| `queue` | `redis`, `worker`, `api` | Очередь и HTTP. Веса моделей не содержат |
| `frontend` | заглушка | В этом документе нет |

Совместный запуск API и моделей — два профиля сразу: `poc` и `queue`. Воркер и API ходят на `http://inference:8080`, как `inference.base_url`. Второго контейнера с тем же именем нет.

Образ `worker` и `api` — тот же Dockerfile, что у `app` (`python:3.11-slim`). Образ Redis — `redis:7`. Группы потребителей Streams в этой ветке есть.

В репозитории сервисов `redis`, `worker`, `api` пока нет. Они появляются в compose вместе с реализацией после утверждения, не этим файлом спецификации.

Секция конфига `queue` нужна процессам API и воркера. У CLI она может отсутствовать.

```yaml
queue:
  redis_url: "redis://redis:6379/0"
  stream: "docqa:jobs"
  group: "docqa-workers"
  consumer: "worker-1"
  result_ttl_sec: 604800
```

`CliApp` к Redis не подключается, даже если секция заполнена.

## 4. Контракт исполнителя

Классы и поля — из спеки классов, без новых обязательных полей `Job`:

| Тип | Поля |
|---|---|
| `Job` | `job_id`, `kind` (`analyze` \| `eval`), `request` (`RunRequest` \| `EvalRequest`) |
| `JobReceipt` | `job_id`, `accepted_at` |
| `JobExecutor` | `submit(Job) -> JobReceipt`, `wait(JobReceipt) -> RunSummary \| EvalReport` |

Производственный адаптер — `RedisStreamsJobExecutor`. Он не содержит фаз: `submit` только пишет стрим и статус, `wait` только читает статус и разбирает результат.

Разбор результата:

- `analyze` и статус успеха — `RunSummary`;
- `eval` и статус успеха — `EvalReport`;
- статус неуспеха — исключение `JobFailed` с коротким текстом, который записал воркер. Частичный отчёт не возвращается.

Успешный `RunSummary` с ненулевым `error_rate` — это успех задания. Сбой отдельных документов живёт внутри сводки. `JobFailed` — только если `run` или `evaluate` бросили исключение.

`InlineJobExecutor` остаётся реализацией для CLI. После спеки eval его `wait` для `kind = eval` вызывает `service.evaluate` и возвращает `EvalReport`. Redis он не трогает.

## 5. Запись в Redis

Стрим — значение `queue.stream` (по умолчанию `docqa:jobs`). Группа — `queue.group`. Один потребитель — `queue.consumer`. Второго потребителя целевая схема не запускает.

Поля записи (строки, как требует стрим):

| Поле | Значение |
|---|---|
| `job_id` | Идентификатор задания |
| `kind` | `analyze` или `eval` |
| `payload` | `Job` в JSON, тот же раундтрип, что в тесте T-JOB-01 |

Хеш `docqa:job:{job_id}`:

| Поле | Значение |
|---|---|
| `status` | `accepted`, затем `running`, затем `succeeded` либо `failed` |
| `accepted_at` | Время квитанции, ISO-8601, UTC |
| `started_at` | Момент, когда воркер взял запись. До старта пусто |
| `finished_at` | Момент конечного статуса |
| `error` | Текст при `failed`, иначе пусто |
| `result` | JSON `RunSummary` или `EvalReport` при `succeeded`, иначе пусто |

`submit`:

1. Проверяет, что `kind` совпадает с типом `request`.
2. Если хеш этого `job_id` уже есть — отказ, запись в стрим не добавляется.
3. Пишет хеш со статусом `accepted` и временем.
4. Добавляет запись в стрим (`XADD`).
5. Возвращает `JobReceipt`.

Порядок «сначала хеш, потом стрим» не даёт второму `submit` пройти проверку, пока первая запись ещё не добавлена. Если процесс API падает после хеша и до стрима, задание остаётся `accepted` без записи. `wait` по нему не завершается успехом. Повторный `submit` с тем же id отвергается. Снятие такого хеша вручную в контракт не входит.

`wait` читает хеш, пока статус не станет `succeeded` или `failed`, либо пока вызывающий не прервёт ожидание своим таймаутом. Таймаут `wait` — аргумент вызывающего API, не часть `Job`. По истечении таймаута API отдаёт текущий статус и результат не подменяет. Сам исполнитель задание из-за таймаута HTTP не отменяет: воркер дочитывает прогон.

Воркер:

1. Читает не больше одной новой записи группы за раз.
2. Разбирает `payload` в `Job`.
3. Если статус уже `succeeded` — подтверждает запись и работу не повторяет. Так повторная доставка после сбоя между записью результата и подтверждением не гоняет прогон заново.
4. Если статус `failed` — тоже подтверждает и не повторяет.
5. Иначе ставит `running` и `started_at`, вызывает `service.run` или `service.evaluate`.
6. При возврате модели пишет `result` и статус `succeeded`, затем подтверждает запись.
7. При исключении пишет `error` и статус `failed`, затем подтверждает. Бесконечной повторной доставки нет: конечный `failed` на шаге 4 будет только подтверждён.

Подтверждение после записи статуса означает: обрыв между записью статуса и подтверждением безопасен из-за шагов 3–4.

Документы внутри `run` воркер не параллелит. `question_parallelism` он не увеличивает. Отдельных сообщений на вопрос он не публикует.

Автоматический съём чужой зависшей записи (`XAUTOCLAIM`) в первый контракт не входит. Пока жив один воркер, зависший `running` после его гибели требует нового запуска воркера; при повторной доставке той же записи шаг 5 выполнит прогон ещё раз, потому что статуса `succeeded`/`failed` ещё нет. Повтор analyze опирается на прежние хеши артефактов. Повтор eval артефакты фаз не пишет.

Срок `result_ttl_sec` обновляется на хеше при конечном статусе. После срока хеш исчезает, `GET` задания отвечает «не найдено».

## 6. ApiApp

Процесс принимает HTTP/JSON и вызывает `RedisStreamsJobExecutor`. Фазы в процессе API не исполняются.

Тело `POST` — модель запроса спеки классов плюс необязательный `job_id`. Если `job_id` не передан, API порождает новый уникальный идентификатор и подставляет его в `Job`.

| Метод и путь | Тело | Ответ |
|---|---|---|
| `POST /v1/jobs/analyze` | `RunRequest`, необязательный `job_id` | `202`, `JobReceipt` |
| `POST /v1/jobs/eval` | `EvalRequest`, необязательный `job_id` | `202`, `JobReceipt` |
| `GET /v1/jobs/{job_id}` | — | `200` и поля статуса: `job_id`, `status`, `accepted_at`, `started_at`, `finished_at`, `error`. Поля `result` в этом ответе нет |
| `GET /v1/jobs/{job_id}/result` | — | `200` и `RunSummary` или `EvalReport`, когда статус `succeeded` |

Коды отказа:

| Ситуация | Код |
|---|---|
| Тело не разбирается или `kind` не совпал бы с телом | `400` |
| Повторный `job_id` | `409` |
| Неизвестный `job_id` | `404` |
| Результат запрошен при `accepted` или `running` | `409`, в теле текущий `status` |
| Результат запрошен при `failed` | `409`, в теле `status` и `error` |

Авторизации в контракте нет: контур локальный. Внешний доступ сюда не проектируется.

## 7. WorkerApp

Процесс:

1. Собирает `Application` из того же `AppConfig`, что CLI.
2. `build` даёт `DocumentAnalysisService` с боевыми шлюзами спеки 7, когда они реализованы. До этого момента воркер в PoC не внедряется: оставлять его на фейках как отдельный продуктовый режим эта спецификация не требует.
3. Создаёт `RedisStreamsJobExecutor`, но цикл чтения пишет воркер сам: `submit` снаружи вызывает API, воркер выполняет шаги раздела 5.
4. На одно задание — один вызов `run` или `evaluate`.
5. Завершение процесса по сигналу: текущее задание дочитывается либо, если оно прервано исключением, пишется `failed`. Новая запись после сигнала не берётся.

Команда процесса — `python main.py worker`. Команда API — `python main.py api`. Обе появляются в разборе argv вместе с реализацией. PoC-справка `CliApp` до этой реализации их не обязана показывать. Спека поведения CLI из-за них не обрастает флагами очереди.

## 8. Что остаётся в PoC

- `python main.py run` и `python main.py eval` идут через `InlineJobExecutor` или прямой вызов фасада, как сейчас устроен CLI для `run`.
- Профиль `poc` поднимает `app` и `inference`. Профиль `queue` для ночного пакетного CLI не нужен.
- Тесты верхнего уровня спеки классов по-прежнему без Redis.

Реализация этого документа после утверждения добавляет адаптер, маршруты и сервисы `queue`. Она не заменяет inline-путь.

## 9. Крайние случаи

- Два `POST` с одним `job_id`: первый `202`, второй `409`, в стриме одна запись.
- `analyze` с падением одного документа внутри сводки: статус задания `succeeded`, `error_rate` внутри `RunSummary`.
- Исключение из `evaluate` (битый gt, недоступный эмбеддер на шаге косинуса): статус `failed`, `result` пуст, `GET .../result` отвечает `409`.
- Повторная доставка при уже записанном `succeeded`: модель второй раз не вызывается, запись подтверждается.
- Воркер не вычитывает вторую запись, пока не подтвердил первую. Поддельный клиент в тесте это видит по одному незакрытому чтению.
- `Job` в payload переживает JSON туда и обратно теми же полями, что T-JOB-01.
- Пустой `redis_url` у процесса воркера — отказ старта, а не тихий переход на inline.

## 10. Каталог тестов

Redis-сервер в unit-тестах не запускается. Поддельный клиент принимает те же операции: добавить запись, прочитать одну неподтверждённую, записать хеш, подтвердить.

| ID | Случай | Ожидание |
|---|---|---|
| T-Q-01 | `submit` analyze | В стриме одна запись, payload разбирается в тот же `Job`, хеш `accepted`, квитанция с этим `job_id` |
| T-Q-02 | Второй `submit` с тем же id | Отказ, вторая запись не появляется |
| T-Q-03 | Воркер забирает analyze | Статусы проходят `accepted` → `running` → `succeeded`, подтверждение одно, результат — `RunSummary` |
| T-Q-04 | Задание eval | Результат `wait` — `EvalReport` |
| T-Q-05 | Две записи в стриме | Вторая не читается, пока первая не подтверждена |
| T-Q-06 | Payload | В JSON есть фазы прогона или путь gt, нет отдельного сообщения на вопрос |
| T-Q-07 | `service.run` бросает | Статус `failed`, подтверждение есть, `wait` бросает `JobFailed`, повторная доставка модель не вызывает |
| T-Q-08 | Повторная доставка при `succeeded` | `run` второй раз не вызывается |
| T-Q-09 | `GET` неизвестного id | Ответ контракта 404 |
| T-Q-10 | `GET` результата в статусе `running` | 409 и статус без тела сводки |
| T-Q-11 | `InlineJobExecutor` | Методы не обращаются к клиенту стрима |
| T-Q-12 | Сводка с `failed` документами и без исключения | Статус задания `succeeded` |

Маршрутные тесты бьют в функции `ApiApp` с тем же поддельным исполнителем, без сокета, если так проще проверить коды. Отдельный боевой Redis в каталог не входит.

## 11. Допущения

- Достаточен Redis 7: стрим, группа потребителей, хеш, срок ключа.
- Имена команд в тексте (`XADD`, группа, подтверждение) описывают поведение. Тест имеет право заменить их поддельным клиентом с теми же исходами.
- Один воркер на группу. Масштаб на несколько GPU этой спецификацией не задаётся.
- Обрыв API-клиента не отменяет уже принятое задание.

## 12. Вне этой спецификации

- Формула `confidence` и учёт `source_sha256` в skip не меняются.
- Автоматический съём зависшего `running` по таймеру не задаётся.
- Состав экрана не задаётся.
- Образ `inference` и его пресеты здесь не переопределяются.
