# Спецификация: хранилище артефактов — v1.0

Статус: **утверждена**. Можно писать тесты и код по этому документу.

Связанные документы: [0. spec.md](0.%20spec.md) (раздел 7), [1. top-level-classes.md](1.%20top-level-classes.md) (§7.2–7.3), [3. chunker.md](3.%20chunker.md), [2. extractor.md](2.%20extractor.md) (`source_sha256`).

## 1. Назначение и границы

**Назначение.** `ArtifactStore` сохраняет и читает артефакты фаз A1/A2/B так, чтобы оркестратор работал только с pydantic-моделями, а повторный прогон мог пропускать фазы по `meta` и хешам.

**Делает:** запись/чтение чанков и их векторов со связкой `chunk_id`+`text_sha256`; кэш эмбеддингов по хешу текста; проверку согласованности текста и вектора; события в `TraceSink`; кандидатов, context-бандлов, meta ответов; атомарную замену набора файлов.

**Не делает:** нарезку текста, поиск, LLM; решение skip/compute (`ArtifactGate`); запись `results/*.jsonl` (`ResultSink`); загрузку моделей.

**Публичная граница** — абстрактный класс `ArtifactStore`. Реализации:

| Класс | Роль |
|---|---|
| `ArtifactStore` | Абстрактные методы save/load |
| `InMemoryArtifactStore` | Словари в RAM для тестов |
| `FileArtifactStore` | Файлы на диске для PoC и боевого CLI |

Фазы зависят только от абстракции. `Application` подставляет файловую или in-memory реализацию.

## 2. Что хранится и где на диске

Корни путей берутся из `AppConfig` / `RunRequest.overrides` (`cache_dir`, каталог index, `contexts_dir`). Ниже — относительная раскладка одной модели. При списках из [10. model-lists.md](10.%20model-lists.md) под корень добавляется префикс из имён файлов, и эта раскладка живёт внутри него. Префикс есть и у списка из одного имени:

- чанки и вопросы — `{embedding_model}/` под `emb/` и под `questions/`;
- кандидаты — `{embedding_model}/{reranker_model}/` под `index_dir`;
- контексты — тот же префикс пары под `contexts_dir`;
- meta ответов — `{embedding_model}/{reranker_model}/{answer_model}/` под `answers/`.

`embed_cache` остаётся общим: ключ уже содержит имя модели.

```text
{cache_dir}/emb/{doc_id}/
    chunks.jsonl          # текстовые поля чанков + text_sha256
    vectors.f16           # матрица эмбеддингов float16
    vectors.index.jsonl   # связка row → chunk_id + text_sha256
    meta.json             # ArtifactMeta фазы A1

{cache_dir}/
    questions.jsonl       # варианты вопросов + text_sha256
    questions.f16
    questions.index.jsonl # связка row → item_id + text_sha256
    questions.meta.json
    embed_cache/          # кэш эмбеддингов по ключу (§3.6)

{index_dir}/{doc_id}/
    candidates.jsonl
    meta.json

{contexts_dir}/{doc_id}/{question_id}.json

{cache_dir}/answers/{doc_id}/meta.json
```

*Почему не parquet в итерации 1: спека поведения называет `chunks.parquet`, но pyarrow — тяжёлая native-зависимость. Логическая схема колонок та же; на диске — JSONL (текст) + сырой float16 (векторы) + JSON (meta). Без pandas/pyarrow. Позже можно добавить `ParquetArtifactStore` с теми же методами.*

Имена `doc_id` / `question_id` в путях — безопасные: только символы, допустимые в имени файла; иначе `ValueError` до записи.

## 3. Форматы файлов

### 3.1. Отпечаток текста (`text_sha256`)

Связка «этот вектор ↔ этот текст» держится не на позиции в файле, а на хеше.

`text_sha256` = нижний регистр hex SHA-256 от UTF-8 байтов поля `text` **как оно ушло в эмбеддер** (без повторной нормализации в store). Тот же алгоритм — для текста варианта вопроса.

*Пример проблемы: переставили две строки в `chunks.jsonl` или подменили текст чанка, оставив старый `vectors.f16`. По одному `chunk_index` это не поймать. По `text_sha256` в индексе векторов — поймать.*

### 3.2. `chunks.jsonl`

Одна строка — один JSON-объект:

| Поле | Тип |
|---|---|
| `chunk_id` | string |
| `text` | string |
| `text_sha256` | string (64 hex) |
| `page_from`, `page_to` | int |
| `section_path` | `null` или массив строк |
| `chunk_index` | int |
| `prev_id`, `next_id` | string или `null` |

Строки упорядочены по возрастанию `chunk_index`. Векторов в JSONL нет. При `save_chunks` store **сам** считает `text_sha256` из `text`, если поле ещё пустое; переданный хеш, не совпадающий с текстом, — `ValueError`.

### 3.3. `vectors.f16` и `vectors.index.jsonl`

`vectors.f16` — сырые little-endian `float16`, без заголовка. Размер = `n_chunks * dim * 2` байт.

`vectors.index.jsonl` — обязательный спутник, по строке на ряд матрицы:

| Поле | Смысл |
|---|---|
| `row` | Индекс строки в `vectors.f16`, с 0 |
| `chunk_id` | Тот же id, что в `chunks.jsonl` |
| `text_sha256` | Хеш текста, **на котором** посчитан этот вектор |

Порядок строк индекса = порядок рядов матрицы. Позиция в файле — удобство хранения; **истина для проверки** — совпадение `(chunk_id, text_sha256)` между `chunks.jsonl` и `vectors.index.jsonl`.

Тензор в оркестратор не возвращается: `load_chunk_vectors` отдаёт оболочку с `chunk_ids`, `text_sha256s`, `dim`, `payload: bytes`.

### 3.4. Проверка связки при чтении

Метод `verify_chunk_embeddings(doc_id) -> EmbeddingBindingReport` (и то же для вопросов) вызывается:

- в конце успешной записи векторов (A1);
- перед гибридным поиском после `load` (A2);
- при желании — отдельной командой/режимом диагностики.

Отчёт:

| Поле | Смысл |
|---|---|
| `ok` | Все проверки прошли |
| `n_chunks` | Число чанков |
| `n_vector_rows` | Число рядов индекса/матрицы |
| `mismatched_ids` | `chunk_id` из индекса, которых нет в chunks, или наоборот |
| `mismatched_hashes` | Пары, где `chunk_id` есть, но `text_sha256` разный |
| `size_error` | Неверный размер `vectors.f16`, если был |

Если `ok is false` — метод **бросает** `EmbeddingBindingError` с кратким текстом; тихий поиск на рассинхроне запрещён.

### 3.5. Наблюдаемость

Каждая проверка и каждая запись векторов пишет в `TraceSink` событие (через `Observed` на методе store/фазы или явный `TraceEvent`):

| `stage` | Когда | `status` | Полезные `counters` / поля |
|---|---|---|---|
| `artifact_vectors_saved` | После `save_chunk_vectors` | `ok` / `failed` | `n_chunks`, `dim`, `doc_id` |
| `artifact_binding_verified` | После `verify_chunk_embeddings` | `ok` | `n_chunks`, `matched=n` |
| `artifact_binding_verified` | Рассинхрон | `failed` | `mismatched_hashes`, `mismatched_ids`; `error` — краткая причина |

В `debug_payload` при DEBUG допустимы первые несколько `chunk_id` из списка расхождений, не вся матрица.

То же для вопросов: стадии `question_vectors_saved` / `question_binding_verified`.

### 3.6. Кэш эмбеддингов (`embed_cache/`)

Как в спеке поведения: ключ = SHA-256 от строки  
`{embedding_model}|{dtype}|{text_sha256}`  
(эквивалент `sha256(model + dtype + normalized_text)`, где нормализация уже сделана до эмбеддинга; store хеширует уже финальный текст).

| Файл | Содержимое |
|---|---|
| `embed_cache/{key}.f16` | Один вектор `dim * 2` байт |
| `embed_cache/{key}.json` | `{text_sha256, model, dtype, dim, created_at}` |

`EmbeddingGateway` (или фаза) перед `infer` спрашивает store: `get_cached_embedding(key)`; при попадании вектор не считает заново. После инференса — `put_cached_embedding`. При `verify` чанков кэш не подменяет проверку индекса документа: индекс документа обязан быть согласован независимо от кэша.

Промахи/попадания кэша — в `TraceEvent` стадии эмбеддинга: counters `embed_cache_hit`, `embed_cache_miss`.

### 3.7. `meta.json` (A1)

| Поле | Обязательность | Смысл |
|---|---|---|
| `schema_version` | да | Версия схемы артефакта |
| `chunking_hash` | да | Хеш параметров чанкинга |
| `embedding_model` | да | Имя модели |
| `embedding_dim` | да | Размерность вектора |
| `embedding_dtype` | да | Всегда `"float16"` в v1 |
| `n_chunks` | да | Число чанков |
| `source_sha256` | да | Отпечаток исходного файла |
| `doc_id` | да | Дубль ключа каталога |
| `vectors_index_sha256` | да после записи векторов | SHA-256 файла `vectors.index.jsonl` целиком — быстрая самопроверка целостности индекса |

`ArtifactGate` в итерации 1 смотрит `schema_version` + `chunking_hash` (+ force). `source_sha256` уже пишется; учёт при skip — доработка extractor §8.

### 3.8. Кандидаты и контексты

`candidates.jsonl` — по строке на `CandidateRecord`. `meta.json` рядом: `schema_version`, `chunking_hash`, `retrieval_config_hash`, `reranker_config_hash`, `source_sha256`.

`contexts/.../*.json` — `ContextBundle` через pydantic, UTF-8, отступ 2.

### 3.9. Кэш вопросов (пакет прогона)

`questions.jsonl`: `question_id`, `variant`, `text`, `text_sha256`, `item_id`.  
`questions.index.jsonl`: `row`, `item_id`, `text_sha256`.  
`questions.f16` + `questions.meta.json` — как у чанков (`n_rows`, `embedding_dim`, …).  
Перед retrieval кэш вопросов проходит тот же `verify_*`.

## 4. Методы `ArtifactStore`

Контракт совпадает с портом и дополняет его явными операциями для векторов (в текущем коде порта их ещё нет — появятся вместе с реализацией после утверждения).

| Метод | Поведение |
|---|---|
| `save_chunks(batch, meta)` | Пишет `chunks.jsonl` (с `text_sha256`) + `meta.json`. Не пишет векторы |
| `save_chunk_vectors(doc_id, rows, dim, payload)` | `rows` — список `(chunk_id, text_sha256)` в порядке рядов; пишет `vectors.f16` + `vectors.index.jsonl`; проверяет размер; затем `verify_chunk_embeddings` |
| `verify_chunk_embeddings(doc_id)` | Сверяет chunks ↔ index ↔ размер f16; пишет TraceEvent; при ошибке — исключение |
| `load_chunks(doc_id)` | `ChunkBatch` или `None` |
| `load_chunks_meta(doc_id)` | `ArtifactMeta` или `None` |
| `load_chunk_vectors(doc_id)` | Оболочка с ids, хешами, dim, payload; перед возвратом — verify |
| `get_cached_embedding` / `put_cached_embedding` | Кэш §3.6 |
| `save_candidates` / `load_*` | A2 |
| `save_context` / `load_context` | JSON бандла |
| `save_questions_cache` / `save_question_vectors` / `verify_question_embeddings` / … | Кэш вопросов с той же схемой связки |
| `save_answers_meta` / `load_answers_meta` | Meta фазы B |

Инварианты:

1. Вектор без строки в `vectors.index.jsonl` не считается валидным артефактом.
2. `save_chunk_vectors` принимает только пары `(chunk_id, text_sha256)`, уже совпадающие с текущим `chunks.jsonl`. Иначе исключение **до** записи f16.
3. Повторный `save_*` заменяет набор файлов атомарно (temp + rename).
4. Отсутствие файла → `None`. Повреждённый JSON / размер / рассинхрон хешей → исключение, не нулевые векторы.
5. Skip A1 по `ArtifactGate` допустим только если на диске есть согласованная тройка chunks + index + f16 (это подтвердит verify на старте A2).

`InMemoryArtifactStore` хранит те же структуры в словарях и выполняет те же verify.

## 5. Кто что вызывает

```text
IndexingPhase
  → save_chunks(batch, meta)              # text_sha256 проставляется
  → для каждого чанка: get_cached_embedding / infer / put_cached_embedding
  → save_chunk_vectors(rows с chunk_id+text_sha256, payload)
  → verify + TraceEvent artifact_binding_verified
  → то же для вопросов

RetrievalPhase
  → load_chunks / load_chunk_vectors      # внутри — verify
  → при failed verify: документ A2 = failed, stage=artifact_binding_verified
  → save_candidates / save_context

AnsweringPhase
  → load_context
  → save_answers_meta
```

`Chunker`, `Extractor`, `Cleaner` хранилище не вызывают. Отладочные `*.extract.md` / `*.clean.md` — не зона `ArtifactStore`.

## 6. Зависимости реализации

| Реализация | Зависимости |
|---|---|
| `InMemoryArtifactStore` | Только stdlib + pydantic (уже в проекте) |
| `FileArtifactStore` | stdlib (`json`, `pathlib`, `os.replace`) + pydantic. **Без** pyarrow, pandas, numpy в обязательном наборе |

Сборка `float16` bytes — ответственность `EmbeddingGateway` (там numpy/torch появятся вместе с моделью). Store принимает уже готовый `bytes`.

## 7. Каталог тестов

| ID | Случай | Ожидание |
|---|---|---|
| T-STO-01 | `save_chunks` + `load_chunks` | Батч совпадает по полям чанков и `doc_id` |
| T-STO-02 | Нет каталога | `load_chunks` / `load_chunks_meta` → `None` |
| T-STO-03 | `meta` с `source_sha256` | После save в `meta.json` поле на месте |
| T-STO-04 | `save_chunk_vectors` с верным размером и совпадающими хешами | `load` + verify `ok`; есть `vectors.index.jsonl` |
| T-STO-05 | `payload` неверного размера | Исключение, файл не считается валидным |
| T-STO-06 | Повторный `save_chunks` | Старые чанки полностью заменены |
| T-STO-07 | `save_context` / `load_context` | Бандл с `empty_search=true` проходит круг |
| T-STO-08 | `save_candidates` jsonl | Число строк = числу кандидатов; скоры на месте |
| T-STO-09 | `InMemoryArtifactStore` те же сценарии 01–03, 06–07 | Семантика как у файла |
| T-STO-10 | `doc_id` с `/` или `..` | `ValueError`, файлы вне корня не создаются |
| T-STO-11 | Векторы сохранены, затем в chunks подменён `text` при том же `chunk_id` | `verify` → `failed`, `mismatched_hashes` не пуст; поиск не вызывается |
| T-STO-12 | `vectors.index` с чужим `chunk_id` | `verify` → `failed`, `mismatched_ids` |
| T-STO-13 | Повторный embed того же текста (тот же model/dtype) | `embed_cache_hit ≥ 1` в TraceEvent; файл кэша на месте |
| T-STO-14 | Смена `text` чанка | Новый `text_sha256`, промах кэша, после save verify `ok` |
| T-STO-15 | Успешный verify | В `RecordingTraceSink` есть `artifact_binding_verified` / `ok` и `n_chunks` |

## 8. Будущие доработки

1. Учёт `source_sha256` в `ArtifactGate` (пересчёт при смене файла).
2. `ParquetArtifactStore` с колонками из раздела 7.2 спеки поведения, если понадобится совместимость с внешними инструментами.
3. Сжатие `contexts` (`gzip`), если включено в конфиге.
4. Удаление артефактов документа одной операцией `purge(doc_id)`.
5. Параллельное чтение нескольких документов (сейчас прогон последовательный).
6. Инвалидация `embed_cache/` при смене `embedding_model` / `dtype` одним манифестом кэша.
