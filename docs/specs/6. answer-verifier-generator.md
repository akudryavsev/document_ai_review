# Спецификация: ответ по контексту — v1.1

Статус: **утверждена**. Можно писать тесты и код по этому документу.

Связанные документы: [0. spec.md](0.%20spec.md) (разделы 6.7, 6.9, 6.10), [1. top-level-classes.md](1.%20top-level-classes.md) (фаза B, T-RUN-03, T-ART-05, T-ART-06), [5. context-assembler.md](5.%20context-assembler.md), [10. model-lists.md](10.%20model-lists.md) (три имени в `AnswerRecord`). Поля тройки из спеки 10 до её утверждения в код не переносятся.

## 1. Назначение и границы

**Назначение.** По готовому `ContextBundle` вызвать LLM и собрать `AnswerRecord`, если поиск уже нашёл фрагменты. Вопрос для модели — всегда `question.category`: в этом поле лежит сам вопрос, не ярлык темы.

Сбор контекста нужен, чтобы модель не перечитывала полный документ на каждый вопрос. Отбор «да / нет / частично» и пометка «частично» на фрагменте в первый запуск не входят: это отложенная оптимизация. Модель ответа сама сопоставляет вопрос и присланные фрагменты.

| Класс | Ответственность |
|---|---|
| `AnswerGenerator` | Запись при пустом поиске без LLM. При непустом бандле — промпт, вызов шлюза, разбор JSON через pydantic, повторы |

**Границы ответственности.**

| Делает | Не делает |
|---|---|
| Пишет ответ пустого поиска и генерирует ответ по фрагментам | Не ищет, не реранжирует и не расширяет секции заново |
| Вызывает уже загруженный фазой `LlmGateway` | Не загружает модель сам |
| | Не фильтрует фрагменты вторым проходом LLM |
| | Не пишет `results/*.jsonl` — это `ResultSink` |
| | Не собирает строки лога; `Observed` вешает фаза |
| | Не вычисляет `confidence`; поле остаётся `None` |
| | Не ограничивает длину ответа. `answer.max_output_tokens` генератор не использует |

**Публичный метод:** `generate(bundle, question, questions=None) -> AnswerRecord`.

Параметр `questions` в v1 на текст вопроса не влияет: генератор не подменяет `category` другой формулировкой из набора. Параметр у метода есть и сохраняется.

Конструктор получает `AnswerConfig` и `RuntimeConfig` (`retries`, `retry_pause_sec`).

## 2. Порядок вызова в `AnsweringPhase`

1. Нет бандла на диске — генератор не вызывается. Фаза сама пишет `AnswerRecord` со `status=failed` и `reason="missing_context"`.
2. `bundle.empty_search=true` — LLM не вызывается. Генератор возвращает системную запись раздела 3.
3. Иначе генератор собирает промпт по всем фрагментам бандла и вызывает LLM.
4. Исчерпание попыток или отсутствие годного ответа — запись `status=failed` по разделу 6, не исключение наружу. Следующий вопрос того же документа обрабатывается (T-RUN-03).

`AnswerVerifier` в первом запуске фаза не вызывает. `verification_skipped` остаётся `false`: шаг не падал, его нет в прогоне. `retrieval.after_verify` равен числу фрагментов бандла.

Несогласованный бандл до генератора не доходит. Это уже ошибка валидации `ContextBundle`: `empty_search=true` вместе с непустыми `candidates`, или `empty_search=false` с пустым списком. Такая пара в ответ не превращается.

## 3. Пустой поиск

Фрагментов нет, потому что так закончились поиск и сборка. Модель об этом не спрашивают и её ответ не подменяют.

Генератор заполняет запись сам и `infer` не вызывает:

| Поле | Значение |
|---|---|
| `found` | `false` |
| `answer` | `В поиске по этому вопросу ничего не найдено.` |
| `explanation` | Строка «Искали по: » и дальше `category`, затем каждый элемент `used_synonyms` через `; ` |
| `reason` | `no_relevant_chunks` |
| `citations` | `[]` |
| `status` | `ok` |
| `prepared_context` | `None` |
| `confidence` | `None` |
| `tokens`, `latency_ms` | нули |
| `model` | имя файла модели ответа этой комбинации; рядом в записи лежат `embedding_model`, `reranker_model` и `answer_model` ([10. model-lists.md](10.%20model-lists.md)) |

`doc_id`, `question_id`, `category`, `used_synonyms` и блок `retrieval` берутся из бандла по таблице раздела 5.1.

Запись с `found=true` при пустом поиске генератор не создаёт. Если такой объект всё же собирают, pydantic-проверка записи падает: пустой поиск и «ответ найден» вместе не сохраняются. Это ошибка сборки, её видно в логе, текст ответа ради неё не переписывается.

## 4. Промпт и ответ модели

Один вызов — один вопрос — один JSON-объект.

### 4.1. Параметры вызова

- `temperature` = `answer.temperature` (в конфигурации 0);
- лимит `max_output_tokens` в запрос не ставится;
- `doc_id` и `question_id` из бандла и вопроса.

### 4.2. Обязательное содержимое промпта

- `category` как вопрос, на который нужен ответ;
- просьба дать ответ и отдельно пояснение с обоснованием;
- схема JSON из раздела 4.3: модель должна вернуть один объект и ничего вокруг него;
- ответ только по фрагментам, без выхода за их пределы;
- если ответа в фрагментах нет — `found=false` и `reason` одна из `not_present`, `insufficient_context`, `ambiguous`;
- фрагменты в порядке возрастания `rank_after_rerank`, в промпте заново с 1;
- заголовок фрагмента: `[n] стр. {from}–{to}, разд. {последний элемент section_path}` при разных страницах; при одной странице — `стр. {page}`; если `section_path is None`, часть `, разд. …` опускается. Страницы — минимум и максимум `pages`. В промпт берётся последний элемент пути целиком;
- при `require_citations=true` — каждый факт со ссылкой `[n]` и цитатой в JSON;
- при `require_citations=false` требование ссылки `[n]` в промпт не добавляется; ограничение «только по фрагментам» остаётся;
- синонимы не задаются отдельными вопросами. Если `used_synonyms` непуст, они видны только в блоке «искали по …» вместе с `category`. Пустой список — в блоке только `category`;
- в конце промпта, после последнего фрагмента, один пример ответа. Это не фрагмент документа и не второй вопрос. Строка `Пример ответа:`, затем один JSON-объект и перевод строки. После закрывающей `}` текста нет. Ограждения \`\`\` нет: пример показывает то тело, которое ждёт раздел 4.3. Объект один и тот же при любом `require_citations`. В нём нет подстроки `Вопрос:` и нет заголовка фрагмента вида `[n]`.

```json
{
  "found": true,
  "answer": "текст ответа на вопрос",
  "explanation": "пояснение и обоснование отдельно от ответа",
  "reason": null,
  "citations": [
    {
      "n": 1,
      "quote": "цитата из фрагмента"
    }
  ]
}
```

Поля сериализуются с отступом в два пробела, `ensure_ascii` выключен, ключи в порядке схемы: `found`, `answer`, `explanation`, `reason`, `citations`. В элементе цитаты сначала `n`, затем `quote`.

Полный текст инструкций сверх этих обязательств не фиксируется. Пример ответа фиксируется. Тест проверяет обязательное содержимое и этот объект, а не побайтовую строку всего промпта.

### 4.3. JSON модели

Тело ответа — один JSON-объект. Пробелы по краям допустимы. Одна ограда markdown вокруг всего текста снимается до `json.loads`. Первая строка после `strip` всего ответа — `` ``` `` или `` ```json ``, регистр букв `json` не важен. Последняя строка — `` ``` ``. Пробелы на этих двух строках допустимы, внутри ограды снова допустимы пробелы по краям. Между оградой и объектом обязателен перевод строки: ограда и JSON на одной строке не снимаются.

Вторая ограда, текст до или после неё, другая метка языка — неудачный разбор. Объект внутри проверяется теми же правилами, что JSON без ограды.

```json
{
  "found": true,
  "answer": "текст ответа на вопрос",
  "explanation": "пояснение и обоснование отдельно от ответа",
  "reason": null,
  "citations": [{"n": 1, "quote": "цитата из фрагмента"}]
}
```

Разбор — pydantic-модель с `extra=forbid`:

| Поле | Тип | Правило |
|---|---|---|
| `found` | `bool` | |
| `answer` | `str` | непустая строка после `strip` |
| `explanation` | `str` | непустая строка после `strip`; пояснение и обоснование, не код причины |
| `reason` | `str \| null` | `found=true` ⇒ `null`. `found=false` ⇒ ровно одно из `not_present`, `insufficient_context`, `ambiguous` |
| `citations` | список | элементы `n: int`, `quote: str` (непустой после `strip`) |

Чужой набор полей, неверный тип, пустые `answer` / `explanation` / `quote`, `reason` не из списка, номер `n` вне `1…число фрагментов` — неудачная попытка. Она идёт в повторы раздела 6. Молчаливой подстановки нет.

`no_relevant_chunks` модель в первом запуске не возвращает: пустой поиск до неё не доходит. Такой код в JSON — неудачный разбор.

`found=true` и пустой `citations` — разобранный JSON, но не ответ «найден». Повтор из-за этого не делается. Генератор отдаёт ту же запись, что в разделе 3: `found=false`, фраза «В поиске по этому вопросу ничего не найдено.», `reason=no_relevant_chunks`, `status=ok`, `citations=[]`. Текст `answer` и `explanation` модели в запись не переносятся. `tokens` и `latency_ms` берутся с этого вызова, `retrieval` — из бандла. `require_citations` на это правило не влияет: флаг только добавляет или не добавляет просьбу о ссылке в промпт.

`found=false` и пустой `citations` остаётся ответом модели со своим `reason`.

## 5. Сборка `AnswerRecord`

### 5.1. Поля системы

| Поле | Источник |
|---|---|
| `doc_id`, `question_id`, `category`, `used_synonyms` | Бандл и вопрос |
| `retrieval.candidates` | `retrieval_meta.top_k`, иначе 0 |
| `retrieval.after_rerank` | `retrieval_meta.after_rerank`, иначе число фрагментов бандла |
| `retrieval.after_verify` | Число `bundle.candidates` |
| `retrieval.sections_used` | Копия `retrieval_meta.sections_used`, иначе `[]` |
| `tokens`, `latency_ms` | Успешный `GenerateResponse`. На пустом поиске — нули |
| `model` | имя файла модели ответа этой комбинации; рядом в записи лежат `embedding_model`, `reranker_model` и `answer_model` ([10. model-lists.md](10.%20model-lists.md)) |
| `status` | `ok`, если запись собрана без отказа модели |
| `confidence` | `None` |
| `verification_skipped` | `false` |
| `prepared_context` | `None` при успехе и при пустом поиске |

Из JSON модели копируются `found`, `answer`, `explanation`, `reason`.

### 5.2. Цитаты

`n` — позиция фрагмента в промпте, счёт с 1. `page_from` / `page_to` и `section_path` берутся из этого фрагмента. `quote` — текст модели.

У цитаты поле `chunk_ids: list[str]`, не один `chunk_id`. В список копируется `chunks_included` этого фрагмента целиком, в том же порядке. И один чанк в фрагменте, и несколько — один и тот же путь: список как в бандле. Подстроку `quote` по текстам чанков генератор не ищет.

`found=true` в сохранённой записи бывает только при непустом `citations`. Пустой список при `found=true` в JSON модели обрабатывается по разделу 4.3.

## 6. Повторы и недоступная модель

`runtime.retries` — сколько всего вызовов LLM, **включая первый**. `retries=2` — два вызова, не три. Значение меньше 1 — ошибка конфигурации на старте, не запись по вопросу.

`runtime.retry_pause_sec` — пауза в секундах между попытками. По умолчанию 0. Перед первым вызовом и после последнего паузы нет. Пауза есть только если следующая попытка ещё будет.

Неудачная попытка:

- исключение или таймаут шлюза;
- пустой текст;
- после снятия одной ограды по разделу 4.3 JSON не разобрался, не прошёл pydantic или правила раздела 4.3.

Успешный разбор останавливает повторы. В запись попадают токены и `latency_ms` этого ответа.

Если годного ответа нет:

| Поле | Значение |
|---|---|
| `status` | `failed` |
| `found` | `false` |
| `reason` | `model_unavailable` |
| `answer` | `Модель недоступна.` |
| `explanation` | `Найденные фрагменты — в prepared_context.` |
| `citations` | `[]` |
| `prepared_context` | `None`. Промпт и сырой текст попыток пишутся только в отладочную папку при `runtime.log_level: DEBUG`, см. [11. user-answer-and-debug.md](11.%20user-answer-and-debug.md) |
| `confidence` | `None` |

Токены и `latency_ms` берутся с последней попытки, которая вернула `GenerateResponse`. Если каждая попытка только бросила исключение — нули. Исключения из `generate` нет.

## 7. Инварианты

- В промпте вопрос для модели — `category`.
- Синоним не является вторым вопросом.
- Пустой поиск не вызывает шлюз и получает текст «В поиске по этому вопросу ничего не найдено.»
- `found=true` вместе с пустым поиском не сохраняется.
- `found=true` в сохранённой записи бывает только вместе с непустым `citations`. Пустые цитаты при `found=true` в JSON дают запись раздела 3.
- У цитаты `chunk_ids` — список всех чанков фрагмента, в порядке `chunks_included`.
- Первый запуск не фильтрует фрагменты верификатором и не хранит пометку «частично».
- Длина ответа конфигурацией не режется.
- `confidence` остаётся `None`.
- `status=ok` и `status=failed` — единственные значения. `found=false` при `status=ok` законен для пустого поиска и для разобранного «ответа в фрагментах нет».
- Генератор не вызывает поиск.

## 8. Ошибки

| Ситуация | Поведение |
|---|---|
| Нет бандла | Генератор не вызывается; фаза пишет `missing_context` |
| Пустой поиск | Системная запись, `status=ok`, шлюз не вызывается |
| `retries < 1` | Ошибка конфигурации до вопросов |
| Все попытки без годного JSON | `status=failed`, `reason=model_unavailable`, `prepared_context is None` |

## 11. Отложено

Шаг `AnswerVerifier` (батч «да / нет / частично», выбрасывание «нет», пометка «частично») в первый запуск не входит. Поля под эту пометку у `ContextCandidate` нет и не добавляется. `verification.enabled` первый запуск не включает.

Одна и та же опора в разных фрагментах, а тем более противоречивые сведения: указать оба места и пояснить расхождение. В первый запуск не входит. Сейчас цитата хранит весь список чанков своего фрагмента и не сверяет тексты между фрагментами.

Формула `confidence` новым вопросом не заводится: она открыта в спеке поведения. Этот документ запрещает подставлять число до её утверждения.

## 12. Закрытые вопросы

| ID | Решение |
|---|---|

| Q-ANS-2 | Пометки «частично» нет. Фильтр верификации отложен. В модель уходят фрагменты сборки, а не весь документ |
