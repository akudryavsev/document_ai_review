# Спецификация: верхние классы — v1.3

Синхронизирована с утверждёнными [2](2.%20extractor.md), [2a](2a.%20cleaner.md), [3](3.%20chunker.md), [3a](3a.%20artifact-store.md), [4](4.%20hybrid-retriever.md), [5](5.%20context-assembler.md), [6](6.%20answer-verifier-generator.md) и с проектами [7](7.%20llama-gateways.md), [8](8.%20eval.md), [9](9.%20job-api.md), [10](10.%20model-lists.md). Спека 10 до утверждения код конфига и цикла моделей не меняет.

Изменения относительно v1.2: шлюзы моделей ходят по HTTP в контейнер llama-server, одна активная GGUF; `EmbedResponse` несёт непрозрачные bytes float16 и `dim`; профиль очереди отделён от сервиса `inference`; пункты про поля эмбеддинга и транспорт Redis закрыты ссылками на спеки 7 и 9. `AnswerVerifier` по-прежнему отложен.

## 1. Назначение и границы

**Делает:** фиксирует, какие классы исполняют поведение из [0. spec.md](0.%20spec.md), какие pydantic-модели пересекают их границы, и какие крайние случаи обязаны быть покрыты тестами до появления кода.

**Не делает:**
- Не повторяет алгоритмы извлечения, чанкинга, ретривала, сборки контекста, верификации, ответа и метрик `eval` — для них отдельные спецификации.
- Не содержит кода, docker-compose и тестов. Каталог тестов описан текстом; реализация тестов — следующий шаг после утверждения этого документа.
- Не проектирует контракт UI. Профиль `frontend` в compose — заглушка.

**Отношение к [0. spec.md](0.%20spec.md):** поведение пайплайна (фазы A1 → A2 → B, CLI, метрики, VRAM) остаётся там. Раскладка артефактов на диске для PoC уточнена в [3a. artifact-store.md](3a.%20artifact-store.md) (JSONL + `*.f16` + meta вместо обязательного parquet). Этот документ отвечает на вопрос «какие классы это делают и чем обмениваются».

**Уже утверждённые дочерние спецификации:** [2. extractor.md](2.%20extractor.md), [2a. cleaner.md](2a.%20cleaner.md), [3. chunker.md](3.%20chunker.md), [3a. artifact-store.md](3a.%20artifact-store.md), [4. hybrid-retriever.md](4.%20hybrid-retriever.md), [5. context-assembler.md](5.%20context-assembler.md), [6. answer-verifier-generator.md](6.%20answer-verifier-generator.md). Ждут утверждения: [8. eval.md](8.%20eval.md), [9. job-api.md](9.%20job-api.md), [10. model-lists.md](10.%20model-lists.md). [7. llama-gateways.md](7.%20llama-gateways.md) утверждена; имена файлов в её пресетах задаёт спека 10. При расхождении с утверждёнными 2–6 по их предметам приоритет у дочернего документа. По eval и очереди до утверждения 8 и 9 код не меняется. Списки имён GGUF до утверждения спеки 10 в код не переносятся. Алгоритм `AnswerVerifier` спецификация ответа откладывает; этот документ его в первый запуск не включает.

## 2. Правила проектирования

1. **Только классы.** Модуль не содержит свободных функций. Константы, разбор argv, вычисление хешей, обёртки логов — методы классов или вложенные типы. Декоратор наблюдаемости — класс с `__call__`, возвращающий дескриптор.
2. **Pydantic на границах.** Публичный метод класса принимает и возвращает pydantic-модели (или их списки). Через границу оркестратора не проходят `dict`, сырые кортежи и тензоры. Исключение: `ArtifactStore` может принимать/отдавать готовые `bytes` матрицы float16 вместе с списком `(chunk_id, text_sha256)` — это не тензор фреймворка, а непрозрачный payload хранилища ([3a](3a.%20artifact-store.md)).
3. **На границе оркестратора нет тензоров.** GPU держит контейнер llama-server. Шлюзы обмениваются с фазами pydantic-моделями. Вектор эмбеддинга на этой границе — непрозрачные `bytes` float16 и `dim`. На диск их пишет фаза через `ArtifactStore` со связкой `chunk_id` + `text_sha256` (и кэшем по хешу текста). `HybridRetriever` считает косинус и BM25 по уже сохранённым векторам: индекс поиска читает bytes хранилища и отдаёт числа по `item_id`.
4. **Спецификация → тесты → код.** Каждый следующий уровень (извлечение, чанкинг, ретривал, ответ, eval, API, модели) получает свою спецификацию с каталогом тестов; код пишется только после неё. Этот документ задаёт верх и перечисляет нижние классы по имени без их алгоритмов.
5. **Один фасад на все контуры.** CLI, будущие API и воркер отличаются только сборкой графа в `Application`, а не копией пайплайна.

## 3. Карта классов

```
CliApp / ApiApp / WorkerApp
        │
        ├─ LlamaModelsIni          списки имён GGUF → текст models.ini
        │                          (команда write-models-ini и сверка до run)
        ▼
   Application  ──собирает──►  DocumentAnalysisService
                                        │
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
              AnalysisRun         EvaluationRun        JobExecutor
                    │                   │              (Inline / Redis)
                    │                   │
                    │  цикл комбинаций  │  группа метрик = одна тройка
                    │  эмбеддер ×       │  из строки ответа
                    │  реранкер ×       │
                    │  модель ответа    │
        ┌───────────┼───────────┐       │
        ▼           ▼           ▼       ▼
 IndexingPhase RetrievalPhase AnsweringPhase
        │           │           │
        │           │           └─ LlmGateway, AnswerGenerator, ResultSink
        │           │              (AnswerVerifier в первый запуск не входит)
        │           └─ HybridRetriever, RerankerGateway,
        │              ContextAssembler, ArtifactStore
        └─ DocumentSource, QuestionSource,
           FormatAwareExtractor (DocxExtractor | PdfExtractor),
           Cleaner, Chunker, EmbeddingGateway, ArtifactStore

 Общие зависимости прогона: GpuLease, ArtifactGate, TraceSink, Observed
```

Списки моделей — не четвёртая фаза и не второй фасад. Имена живут в `AppConfig`. Текст ini собирает `LlamaModelsIni` до фаз. Обход комбинаций делает `AnalysisRun` вокруг тех же трёх фаз. `EvaluationRun` цикл не запускает: он читает тройку, которую фаза B уже записала в строку. Правила имён, ini и каталогов — [10. model-lists.md](10.%20model-lists.md).

Ниже — контракты по слоям. Имена классов стабильны. Код лежит в `src/<роль>/`, импорт совпадает с именем папки (`application`, `phases`, …). Процесс запускается как `python main.py` из корня репозитория. Иерархия извлекателей и формат файлов хранилища — в дочерних спецификациях.

## 4. Точки входа и фасад

### 4.1. `CliApp`

- **Роль:** разбор argv → `RunRequest` или `EvalRequest` → вызов `Application`. Процесс стартует из корневого `main.py`, который вызывает `CliApp.main`.
- **Не содержит** бизнес-логики фаз, работы с GPU и артефактами.
- Команда `write-models-ini` вызывает `LlamaModelsIni` и завершается до фаз. Команда `run` до `DocumentAnalysisService.run` сверяет файл ini с текстом этого класса.
- **Публичные методы:**
  - `main(argv: list[str]) -> int` — код выхода процесса.
  - Внутри: построение `Application` из загруженного `AppConfig` и делегирование `DocumentAnalysisService`.

### 4.2. `ApiApp` (контракт, PoC не реализует)

- Строит `Application`, принимает HTTP/JSON, маппит в `RunRequest` / `EvalRequest` / `Job`, вызывает фасад или `JobExecutor`.
- Детали маршрутов — в [9. job-api.md](9.%20job-api.md). В PoC процесс не запускается.

### 4.3. `WorkerApp` (контракт, PoC не реализует)

- Десериализует `Job`, строит `Application`, вызывает фасад.
- Не параллелит документы и вопросы, пока `runtime.question_parallelism == 1`.

### 4.4. `Application`

- **Роль:** композиционный корень.
- **Вход:** `AppConfig`.
- **Делает:** создаёт конкретные адаптеры зависимостей и передаёт их в `DocumentAnalysisService` (и при необходимости в `JobExecutor`).
- **Публичные методы:**
  - `build() -> DocumentAnalysisService`
  - `build_job_executor() -> JobExecutor` — в PoC возвращает `InlineJobExecutor`.

### 4.5. `DocumentAnalysisService`

Единственный фасад, который вызывают входные точки.

| Метод | Вход | Выход |
|---|---|---|
| `run` | `RunRequest` | `RunSummary` |
| `evaluate` | `EvalRequest` | список `EvalReport`, по отчёту на тройку |

- `run` создаёт `AnalysisRun` и исполняет запрошенные фазы.
- `evaluate` создаёт `EvaluationRun`. Семантическая близость ответов идёт через эмбеддер — первый файл `embedding.models`, отдельной моделью не обрастает.

### 4.6. `AnalysisRun`

- Один пакетный прогон.
- Обходит декартово произведение `embedding.models` × `reranker.models` × `answer.models`. Для одной тройки держит порядок фаз A1 → A2 → B согласно `RunRequest`. Незапрошенная фаза в этой тройке не исполняется.
- На время тройки подставляет в шлюзы имена файлов этой тройки и префиксы каталогов из [10. model-lists.md](10.%20model-lists.md). Фазы по-прежнему не знают про остальные комбинации.
- Между фазами и между комбинациями отпускает GPU через `GpuLease`.
- Пишет один `RunSummary` со списком `combinations` (в т.ч. через `ResultSink`).
- Документы обрабатываются **последовательно** внутри каждой фазы (инвариант [0. spec.md](0.%20spec.md)).

### 4.7. `EvaluationRun`

- Сценарий `python main.py eval`.
- Читает предсказания (`AnswerRecord`) и ground truth через `GroundTruthSource`.
- Возвращает список `EvalReport`: один отчёт на тройку `embedding_model`, `reranker_model`, `answer_model` из строк предсказаний. Формулы и поля — в [8. eval.md](8.%20eval.md). Цикл по спискам конфига здесь не повторяется.

## 5. Фазы

### 5.1. Абстрактный `Phase`

| Метод | Вход | Выход |
|---|---|---|
| `plan` | `PhaseContext` | `PhasePlan` |
| `execute` | `PhasePlan` | `PhaseReport` |

- `plan` — для каждого документа решение `ReuseDecision` (посчитать или пропустить) на основе `ArtifactGate` и `--force-phase`.
- `execute` — исполнение плана; в отчёте счётчики `computed` / `skipped` / `failed`, как в `run_summary` спеки поведения.

`PhaseContext` (pydantic): ссылки на конфиг, список документов прогона, флаги force, пути артефактов, уже загруженные вопросы (если применимо).

### 5.2. `IndexingPhase` (A1)

**Зависимости:** `DocumentSource`, `Extractor` (обычно `FormatAwareExtractor`), `Cleaner`, `Chunker`, `EmbeddingGateway`, `ArtifactStore`. `QuestionSource` / загруженный `QuestionSet` — только если в прогоне нужны эмбеддинги вопросов (см. §7.1).

**Обязанности:**
1. Для каждого документа: Extract → Clean → Chunk → Embed (с `embed_cache` по `text_sha256`) → `ArtifactStore.save_chunks` + `save_chunk_vectors` (+ `verify_chunk_embeddings`). Байты float16 и `dim` приходят в `EmbedResponse`; шлюз хранилище не вызывает. На диске: `chunks.jsonl`, `vectors.f16`, `vectors.index.jsonl`, `meta.json` (в т.ч. `source_sha256`) — см. [3a](3a.%20artifact-store.md) и [7](7.%20llama-gateways.md). Не `chunks.parquet` в PoC.
2. Если в `PhaseContext.questions` есть `QuestionSet` — эмбеддинги вариантов вопросов (`category` + synonyms) в этой же фазе; кэш пакета — `questions.jsonl` / `questions.f16` / `questions.index.jsonl` (+ verify). Идентификаторы вариантов назначает эта фаза, поиск использует те же строки: `{question.id}:category` и `{question.id}:syn:{i}` (`i` с нуля). Если вопросов нет (`None`) — шаг пропускается; разбор документа на чанки от этого не зависит.
3. При `extraction.debug_dump` — отладочные Markdown через `BlockDocumentDebugDump` (не зона `ArtifactStore`).
4. После всех документов — `GpuLease` выгружает эмбеддер.

Цепочка моделей: `DocumentRef` → `ExtractedDocument` (`blocks`, `source_sha256`) → `CleanedDocument` → `ChunkBatch`. Алгоритмы — [2](2.%20extractor.md), [2a](2a.%20cleaner.md), [3](3.%20chunker.md).

### 5.3. `RetrievalPhase` (A2)

**Зависимости:** `HybridRetriever`, `RerankerGateway`, `ContextAssembler`, `ArtifactStore`.

**Обязанности:**
1. Перед поиском по документу: `load_chunks` / `load_chunk_vectors` с **verify** связки текст↔вектор; при рассинхроне документ A2 = `failed`, событие `artifact_binding_verified` / `failed`.
2. Для каждой пары документ × вопрос: `search` по `category` и каждому синониму как по отдельному варианту → один пул → отбор фазы (реранк либо `top_n` без реранкера) → `ContextAssembler.assemble` → один `ContextBundle`. Пороги и `early_exit` применяет фаза, не сборщик. Ноль у порога его выключает. `early_exit` действует только при включённом реранкере и пороге больше 0. Алгоритм — [4](4.%20hybrid-retriever.md) и [5](5.%20context-assembler.md).
3. Пустой пакет после отбора, в том числе из‑за раннего выхода: в сборку уходит `empty_search=true`. Причина бандла всегда `no_relevant_chunks`, отдельного кода раннего выхода нет. Бандл **передаётся в B**. Модель на этой паре не вызывается: запись пишет `AnswerGenerator`.
4. Нет вектора варианта или чанка, либо длина вектора нулевая: `search` возвращает пустой пакет и событие `failed` в трассе, без исключения. Документ A2 из‑за этого не `failed`, фаза переходит к следующему вопросу. Дальше тот же пустой поиск, что в п. 3.
5. Если в отборе есть записи → `empty_search=false`. Синонимы остаются вариантами поиска, не отдельными ответами. Один бандл на категорию; тексты разных секций в один фрагмент не склеиваются.
6. При `retrieval.persist_candidates` (по умолчанию `true`) фаза пишет через `ArtifactStore` пакет **до** реранка (`candidates.jsonl` + meta). При `false` файл не создаётся, прогон в том же процессе не ломается.
7. Отладочные `{question_id}.retrieval.json` и `{question_id}.context.md` пишут `RetrievalDebugDump` и `ContextDebugDump` по флагу `retrieval.debug_dump`. Это не зона `ArtifactStore`.
8. После всех документов — выгрузка реранкера через `GpuLease`.

Индекс BM25 и векторный top-k для документа строятся **в памяти** на загруженных чанках; формат склада на диске поиск напрямую не читает.

### 5.4. `AnsweringPhase` (B)

**Зависимости:** `LlmGateway`, `AnswerGenerator`, `ResultSink`, `ArtifactStore` (чтение контекстов / meta ответов). `AnswerVerifier` в первый запуск не входит и фазой не вызывается.

**Обязанности:**
1. Нет бандла на диске — `AnswerGenerator` не вызывается. Фаза пишет `AnswerRecord` со `status=failed` и `reason=missing_context`. Это не пустой поиск и не тихий пустой ответ.
2. Вопрос для модели = **`category`**. Синонимы в текст вопроса не подставляются. Непустой `used_synonyms` виден только в блоке «искали по …».
3. Если `empty_search=true`: LLM не вызывается. Генератор пишет `found=false`, `reason=no_relevant_chunks`, `status=ok` и фразу «В поиске по этому вопросу ничего не найдено.»
4. Если `empty_search=false`: в промпт идут все фрагменты бандла, без фильтра «да/нет/частично». Ответ модели — один JSON, разбор через pydantic. `found=true` при пустых `citations` не сохраняется как найденный ответ и повтор не запускает: генератор отдаёт ту же системную запись, что в п. 3, со `status=ok`; токены и latency берутся с этого вызова.
5. Нет годного JSON после `runtime.retries` попыток (число включает первый вызов) → `status=failed`, `reason=model_unavailable`, в записи промпт с фрагментами. `retries` меньше 1 — ошибка конфигурации до старта вопросов. Пауза `runtime.retry_pause_sec` есть только между попытками. Исключения наружу нет. Следующие вопросы того же документа продолжаются.
6. `verification_skipped` остаётся `false`: шаг верификации не падал, его нет в прогоне. `retrieval.after_verify` равен числу фрагментов бандла. Длину ответа генератор не ограничивает: `answer.max_output_tokens` в запрос не передаётся. `confidence` остаётся `None`.

## 6. Очередь и задания

Инвариант VRAM из спеки поведения: модель загружается **один раз на пачку документов фазы**. Поэтому единица очереди — прогон фазы по набору документов или целый `AnalysisRun`, а не один документ и не один вопрос.

### 6.1. `Job` (pydantic)

| Поле | Тип | Описание |
|---|---|---|
| `job_id` | `str` | Уникальный идентификатор задания |
| `kind` | `Literal["analyze", "eval"]` | Тип задания |
| `request` | `RunRequest \| EvalRequest` | Дискриминируется по `kind` |

Инвариант: `Job` обязан переживать JSON-раундтрип без потери полей (тест верхнего уровня).

### 6.2. `JobReceipt` (pydantic)

| Поле | Тип |
|---|---|
| `job_id` | `str` |
| `accepted_at` | `datetime` |

### 6.3. `JobExecutor` (абстрактный)

| Метод | Вход | Выход |
|---|---|---|
| `submit` | `Job` | `JobReceipt` |
| `wait` | `JobReceipt` | `RunSummary` либо список `EvalReport` |

### 6.4. `InlineJobExecutor` (PoC)

- Вызывает `DocumentAnalysisService` в том же процессе.
- Поведение CLI совпадает со спекой поведения: синхронный прогон.
- Тип результата `wait` тот же, что обязан вернуть будущий Redis-воркер.

Транспорт — Redis Streams, адаптер и маршруты — в [9. job-api.md](9.%20job-api.md). Верхний контракт от транспорта не зависит. RQ не используется.

### 4.8. `LlamaModelsIni`

- **Роль:** список имён из `AppConfig` → канонический текст `deploy/llama/models.ini` и сверка с уже лежащим файлом.
- **Не вызывает** фазы, шлюзы и `GpuLease`. В контейнер `inference` не ходит.
- **Публичные методы:** собрать текст; записать файл; сравнить файл с текстом. Команды, которые их зовут, — `CliApp` (`write-models-ini` и проверка в начале `run`).
- Ошибка сверки останавливает `run` до `AnalysisRun`. Состав секций и флаги ролей — [10. model-lists.md](10.%20model-lists.md) §4.

## 7. Абстрактные зависимости (подставляются в `Application`)

### 7.1. Источники

| Класс | Назначение | PoC-реализация |
|---|---|---|
| `DocumentSource` | Список `DocumentRef` из каталога (рекурсивно, `.docx` / `.pdf`) | Файловая система |
| `QuestionSource` | Загрузка и валидация файла вопросов → `QuestionSet` | Файловая система + pydantic |
| `GroundTruthSource` | Загрузка `gt.json` → список эталонов | Файловая система + pydantic |

Когда `DocumentAnalysisService` загружает вопросы:

| Запрошенные фазы (`RunRequest.phases`) | Вопросы |
|---|---|
| Только `A1` | Не обязательны. `QuestionSource` не вызывается; в контекст уходит `questions=None`. Extract → Clean → Chunk выполняется без файла вопросов. |
| Есть `A2` и/или `B` (с `A1` или без) | Обязательны. `QuestionSource.load()` до старта фаз. |

Ошибки валидации вопросов (пустой список, дубликат `id`, дубликат `category`) поднимаются **до** старта фаз **только когда загрузка вопросов обязательна** (есть `A2`/`B`) либо когда файл всё же загружают. Для прогона «только A1» отсутствие `questions_file` — не ошибка.

### 7.2. `ArtifactStore`

Персистентность артефактов. Норматив: [3a. artifact-store.md](3a.%20artifact-store.md).

- На границе: pydantic-модели (`ChunkBatch`, `CandidateBatch`, `ContextBundle`, meta) и при необходимости `bytes` float16 + списки `(id, text_sha256)`.
- Обязаны уметь: `save`/`load` чанков и векторов, `verify_*` связки, `embed_cache`, кэш вопросов, кандидатов, контекстов, meta ответов.
- PoC-файлы: JSONL + `*.f16` + `*.index.jsonl` + `meta.json`. Parquet/pyarrow в PoC не требуются.
- Реализации: `FileArtifactStore`, `InMemoryArtifactStore` (тесты).

### 7.3. `ArtifactGate`

Чистый класс без диска и GPU.

| Метод | Вход | Выход |
|---|---|---|
| `decide` | meta артефакта + хешируемые срезы конфига + `force: bool` | `ReuseDecision` |

Позволяет тестировать инвалидацию (`chunking_hash`, `retrieval_config_hash`, `reranker_config_hash`, `schema_version`) отдельно от I/O.

### 7.4. Шлюзы моделей

Каждый шлюз:

| Метод | Описание |
|---|---|
| `load` | Загрузка модели на устройство |
| `infer` | Запрос/ответ — pydantic (`EmbedRequest`/`EmbedResponse`, …) |
| `unload` | Выгрузка + освобождение ресурсов |

- `EmbeddingGateway` — боевой класс `LlamaEmbeddingGateway`, пресет — имя файла из текущей тройки `AnalysisRun`
- `RerankerGateway` — `LlamaRerankerGateway`, пресет — имя файла реранкера этой тройки
- `LlmGateway` — `LlamaLlmGateway`, пресет — имя файла ответа этой тройки

Боевые классы ходят по HTTP в один контейнер llama-server (`--models-max 1`). Контракт, байты float16 и запись в store — в [7. llama-gateways.md](7.%20llama-gateways.md). `Application.build` ставит эти шлюзы и `HybridSearcher`. Имя пресета на шлюзе меняет `AnalysisRun` перед комбинацией. В тестах верхнего уровня фазы по-прежнему собираются на подделках.

### 7.5. `GpuLease`

Инвариант: **не больше одного загруженного шлюза** одновременно. Для боевых шлюзов это ещё и один пресет в llama-server.

| Метод | Поведение |
|---|---|
| `acquire(gateway)` | Если занят другим — `unload` предыдущего, затем `load` нового; событие в `TraceSink`. `load`/`unload` боевого шлюза переключают пресет на сервере |
| `release()` | Выгрузка текущего, если есть. Для боевого шлюза это `POST /models/unload` |

Порядок загрузок внутри одной комбинации A1→A2→B: эмбеддер, затем реранкер, затем LLM. Следующая комбинация начинается после выгрузки предыдущей. Пропуск фазы не загружает её пресет. Процесс приложения torch-веса не загружает.

### 7.6. `ResultSink`

Запись `results/<doc_id>.jsonl`, `results/<doc_id>.md`, `results/run_summary.json`. В jsonl строка с тем же вопросом и той же тройкой моделей заменяется, остальные строки файла остаются. Сводка одна на весь `AnalysisRun` и содержит список комбинаций.

### 7.7. `TraceSink`

Приёмник `TraceEvent`. PoC: structured log. Позже — тот же интерфейс под OTel.

### 8.1. `Observed`

Класс-декоратор: `Observed(stage: str)`.

## 9. Контракты (pydantic) этого уровня

Поведенческие примеры JSON остаются в [0. spec.md](0.%20spec.md). Здесь — поля и инварианты, обязательные для границ классов.

### 9.1. Конфигурация и запросы

**`AppConfig`** — зеркало YAML раздела 5 спеки поведения, включая секции `input`, `extraction`, `chunking`, `embedding`, `retrieval`, `reranker`, `verification`, `context`, `answer`, `phases`, `runtime`. У `embedding`, `reranker` и `answer` список `models` — имена файлов GGUF ([10. model-lists.md](10.%20model-lists.md)). Хешируемые подмножества доступны как методы/вычисляемые поля для `ArtifactGate`.

**`RunRequest`**

| Поле | Описание |
|---|---|
| `config_path` / вложенный `AppConfig` | Источник конфигурации |
| `phases` | Список фаз к исполнению (`A1`, `A2`, `B`) |
| `force_phases` | Множество фаз для принудительного пересчёта |
| `overrides` | Переопределения модели и каталогов (`answer_model`, `reranker_model`, `embedding_model`, `cache_dir`, `contexts_dir`, `results_dir`, …). Имя модели в override — один файл и на этот запуск заменяет список своей роли |

При отсутствии явного списка документов `DocumentSource` читает весь каталог (поведение v1).

**`EvalRequest`**

| Поле | Описание |
|---|---|
| конфиг | `AppConfig` / путь |
| `ground_truth_path` | Путь к `gt.json` |
| `predictions_dir` | Каталог предсказаний |

### 9.2. Планирование и сводка

**`ReuseDecision`:** `action: Literal["compute", "skip"]`, `reason: str` (например `hashes_valid`, `force`, `missing_artifact`, `hash_mismatch`).

**`PhasePlan`:** список элементов `(DocumentRef, ReuseDecision)` (+ агрегаты, нужные фазе).

**`PhaseReport`:** `computed: int`, `skipped: int`, `failed: int`, детали по документам/причинам.

**`RunSummary`:** агрегат прогона; **обязан** содержать счётчики по каждой запрошенной фазе; список комбинаций с тремя именами файлов и счётчиками этой тройки; error rate; средние latency/tokens — по разделу 6.11 спеки поведения и по [10. model-lists.md](10.%20model-lists.md).

**`EvalReport`:** метрики раздела 10 спеки поведения, по одному отчёту на тройку моделей. Структура полей — в [8. eval.md](8.%20eval.md).

### 9.3. Оболочки шлюзов

Тензоров в полях нет.

- `EmbedRequest` / `EmbedResponse` — тексты и идентификаторы на входе. В каждом элементе ответа: `item_id`, `success`, `dim` и непрозрачные `vector: bytes` (little-endian float16, длина `dim * 2`). Ключ кэша шлюз не вычисляет. Фаза сама вызывает `save_chunk_vectors`, `embed_cache` и кэш вопросов. Шлюз в хранилище не пишет.
- `RerankRequest` / `RerankResponse` — пары query×passage (тексты + id), скоры и ранги в ответе. Шлюз не знает порогов отбора и не собирает `ContextBundle`.
- `GenerateRequest` / `GenerateResponse` — промпт/сообщения, текст ответа, usage-токены, latency. Лимит `max_output_tokens` генератор в запрос не ставит. Один `infer` шлюз не повторяет.

Инвариант «нет тензоров на границе» — жёсткий. Поля и HTTP — в [7. llama-gateways.md](7.%20llama-gateways.md).

### 9.4. Артефакты и результаты

- **`AnswerRecord`** — строка `results/<doc_id>.jsonl` (раздел 6.10 спеки поведения).
- **`ContextBundle`** — содержимое `contexts/<doc>/<q>.json` (раздел 7.2).

**Инварианты `ContextBundle`:**
- `empty_search: bool` — `true`, если в сборку ушёл пустой пакет (пустой поиск, порог, ранний выход или отсутствие вектора); `false`, если в отборе есть записи. На паре с `true` фаза B модель не вызывает.
- `empty_search is true` ⇔ `candidates == []` и `reason == "no_relevant_chunks"`. Другого кода причины у пустого поиска нет.
- `empty_search is false` ⇒ в бандле есть хотя бы один фрагмент после расширения секции и `reason is None`. Пороги сборщик заново не применяет.
- поле `category` в бандле — канонический вопрос для фазы B; `used_synonyms` — метаданные поиска и блок «искали по …» в промпте, не отдельные задания на ответ.

**Инварианты файла вопросов (`QuestionSet`):**
- уникальные `id`;
- уникальные `category`;
- пустой список вопросов — ошибка загрузки;
- вопрос без `synonyms` (пустой список) допустим: единственный вариант запроса — `category`.

### 9.5. Нижележащие модели (имена и инварианты границ)

Детальные схемы — в дочерних спецификациях; здесь — то, что обязано совпасть с уже утверждёнными документами 2 / 2a / 3 / 3a:

| Модель | Инвариант на границе |
|---|---|
| `DocumentRef` | `doc_id`, `path`, `suffix` (`.docx` / `.pdf`) |
| `ExtractedBlock` | `kind`, `text`, `page`, `section_path: list[str] \| None`, `heading_level`, `paragraph_index` |
| `ExtractedDocument` | `blocks: list[ExtractedBlock]`, `source_sha256`, `has_text_layer`, `failure_reason`; **нет** дублирующих полей-копий всего текста (`text`/`pages` как хранимые поля) — только методы вроде `joined_text()` |
| `CleanedDocument` | те же `blocks` + скопированный `source_sha256` |
| `ChunkRecord` / `ChunkBatch` | нарезка в памяти; `chunk_id = c_{index:04d}`; `section_path: list[str] \| None`; вектора в модели чанкера нет |
| `CandidateBatch`, `ContextBundle` | как выше и в спеке поведения |
| `Question`, `QuestionSet` | инварианты §9.4 |
| эталоны ground truth | спецификация eval |

`Application` собирает `FormatAwareExtractor` → `DocxExtractor` / `PdfExtractor` (`python-docx`, `pypdf`); фаза видит только абстрактный `Extractor`.

## 11. Контуры в docker-compose

Файл compose появляется вместе с первым кодом, **после** тестов верхнего уровня. Спецификация заранее фиксирует профили.

| Профиль | Сервисы | Назначение |
|---|---|---|
| `poc` | `app`, `inference` | `app` — образ Python без torch, команда `CliApp`. `inference` — llama-server, профиль `poc`, GPU, `--models-max 1`, порт 8080. Тома документов, вопросов, `./models`, `.cache`, `index`, `contexts`, `results`. Redis не нужен |

| `queue` | `redis`, `worker` (`WorkerApp`), `api` (`ApiApp`) | Тот же `Job` и тот же фасад. Транспорт — Redis Streams. Сервиса с именем `inference` в этом профиле нет |
| `frontend` | заглушка | Контракт UI здесь не проектируется; достаточно будущего API над `DocumentAnalysisService` |

Сейчас в `docker-compose.yml` есть `app` и `inference` (профиль `poc`). Сервисы профиля `queue` добавляются вместе с реализацией [9. job-api.md](9.%20job-api.md).
